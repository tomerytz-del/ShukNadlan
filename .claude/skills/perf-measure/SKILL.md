# מדידת ביצועים לפני/אחרי

## הכלל היחיד שחשוב כאן

**מכשיר המדידה הזה מחזיר מספר גם כשהוא שבור.** אין שגיאה, אין אזהרה —
יוצאת טבלה סבירה למראה עם מסקנה הפוכה. זה מה שמבדיל את הבדיקה הזו
מבדיקת CI שנופלת ברעש.

ב-19.9.2026, בהוצאת הקוד של ה-CRM לקובץ נפרד, המכשיר הזה החזיר **ארבע
תשובות שגויות** לפני שהחזיר את הנכונה:

| מה נעשה | מה יצא | מה באמת קרה |
| --- | --- | --- |
| `ctx.route("**/*")` כדי לפקק את ה-CDN | "‏0% שיפור, אותם 510KB בשני התרחישים" | **יירוט ב-Playwright מכבה את מטמון ה-HTTP של Chromium כולו** |
| ספירת בייטים מאירוע ה-`response` | אותה מסקנה שגויה מכיוון אחר | פגיעת מטמון ו-304 נספרים כהורדה מלאה |
| שרת בלי `Cache-Control` | אפס תשובות 304 | בלי הכותרת הדפדפן אינו שומר את התשובה בכלל |
| סדרה אחת של תשע דגימות | "‏+4% ב-FCP — רעש" | ‏+30ms, אמיתי. שתי סדרות נוספות הראו זאת |

התשובה הראשונה היא החמורה: היא שללה את **כל ההצדקה** לעבודה. מי שעוצר
שם מסיק שאין שום רווח, וגונז שינוי שבפועל חוסך 60% מזמן הטעינה.

## שני התרחישים, ולמה "ביקור ראשון" לבד משקר

**הדפדפן מצייר מתוך זרם ה-HTML תוך כדי הורדה.** לכן מסמך של 400KB אינו
מעכב את הציור הראשון, ומדידת ביקור ראשון בלבד תראה שהוצאת קוד לקובץ
נפרד "לא עשתה כלום" — וזו מסקנה נכונה לתרחיש הלא נכון.

| תרחיש | איך נמדד | מה הוא עונה |
| --- | --- | --- |
| **ביקור ראשון** | טעינה אחת, מטמון ריק | האם זה הזיק |
| **פריסה שנגעה רק ב-HTML** | טעינה לחימום, ואז אותה כתובת עם `?v=2` | האם זה הועיל |

התרחיש השני הוא הרלוונטי כאן: האתר מתפרסם תוך שניות מכל מיזוג, ורוב
ה-PR-ים נוגעים במבנה הדף ולא בכל הקוד שבו. ה-`?v=2` הוא בדיוק זה —
‏HTML חדש (כתובת שאינה במטמון) מול assets שלא זזו.

## ההרצה

**‏`before.html` יושב מחוץ לריפו, וזו לא קפדנות.** בדיקות ה-CI סורקות
כל `*.html` בשורש — קובץ עזר שנשכח שם ייבדק על GTM, ‏PWA ואימות גוגל,
ובמקרה הרע ייכנס לקומיט עם `git add -A`. השרת מוצא את הריפו לפי מיקומו
שלו, ולכן אפשר להריץ אותו מכל מקום:

```sh
REPO=$(git rev-parse --show-toplevel)
mkdir -p /tmp/perf && cd /tmp/perf

# 1. גרסת ה"לפני" — מה שיושב ב-main
git -C "$REPO" show origin/main:index.html > before.html

# 2. השרת: מגיש את הריפו, ו-before.html מהתיקייה הנוכחית
python "$REPO/.claude/skills/perf-measure/server.py" 8741 &

# 3. המדידה
pip install --quiet playwright     # הדפדפן כבר מותקן ב-/opt/pw-browsers
python "$REPO/.claude/skills/perf-measure/measure.py" \
       --before /before.html --after /index.html --samples 9
```

שני הקבצים בתיקיית הסקיל כבר נושאים את כל מה שכתוב למטה. **אין לכתוב
גרסה משלך** — כל אחד מארבעת המוקשים נכנס בדיוק כך, כי הקוד שמכיל אותם
נראה תקין לגמרי.

## מה שהשרת חייב, ולמה

‏`_headers` בשורש קובע ש-HTML/JS/CSS **אינם** מקבלים מטמון ארוך — שמות
הקבצים אינם נושאים חתימת תוכן, ולכן מה שיש הוא אימות מחדש מול `ETag`
שמחזיר `304`. שרת המדידה חייב לחקות בדיוק את זה:

```
Cache-Control: public, max-age=0, must-revalidate
ETag: "…"          + תשובת 304 ל-If-None-Match
Content-Encoding: gzip (רמה 6)
```

‏`gzip` ולא `brotli`: ‏Netlify מגיש brotli למי שתומך, והוא קטן ב-15–20%.
‏gzip הוא הקירוב **השמרני**, כלומר המדידה מטה לכיוון "פחות רווח".

## שלוש סדרות, לא אחת

סדרה אחת אינה מדידה. הפלט מציג `חציון [מינימום–מקסימום]` לכל גרסה, ואת
המבחן היחיד שקובע:

* **הטווחים אינם נחתכים** → ההפרש אמיתי.
* **הטווחים נחתכים** → הריצו עוד סדרה לפני שקובעים משהו.

כך נתפס ההפרש ב-FCP שדווח בטעות כרעש: סדרה של ‎-4ms‎ נראתה כמו אפס, ושתי
סדרות נוספות (9 ו-15 דגימות) נתנו ‎+28‎ ו-‎+32ms‎, עם פיזור של 80ms מול
32ms. ה-`load` באותה מדידה היה ‎-207ms‎ עם טווחים שאינם נחתכים — וזה
ההבדל בין השניים.

## מה לדווח

**את שני הכיוונים.** מדידה שמדווחת רק את הרווח היא שכנוע, לא מדידה.
הוצאת הקוד של דף הבית, למשל, מדווחת כך:

```
                            FCP      load   ירד מהרשת
  ביקור ראשון      לפני   1,280ms   2,354ms     377KB
                   אחרי   1,240ms   2,399ms     378KB
  פריסה רק ב-HTML  לפני     876ms   1,202ms     170KB
                   אחרי     908ms     995ms      90KB
```

‏17% בזמן ו-47% בבייטים — **ו-30ms שנוספו לציור הראשון**. זה עסק טוב,
אבל **עסק ולא שיפור נקי**, ומי שיחליט על הדף הבא צריך את שני המספרים.

## מה שכבר נמדד, ואין צורך למדוד שוב

* **הוצאת JS לקובץ ב-`assets/`** — משתלמת בביקור החוזר, בשלושה דפים
  שנמדדו: ‏`crm.html` ‏2,372→953ms ו-407→109KB, ‏`index.html`
  ‏1,202→995ms ו-170→90KB, ‏`property.html` ‏852→829ms ו-77→38KB.
  **בביקור הראשון התוצאה שונה בכל דף** (ללא שינוי · ‎-36ms‎ · ‎-156ms‎),
  ואין כלל שמנבא אותה — לכן מודדים. הכלל ב-CLAUDE.md.
* **מיקום הסקריפט בתוך ה-body** — **אינו** משפיע. נבדק ב-`property.html`
  עם וריאנט שלישי: אותם בתים מוטבעים בסוף ה-body במקום באמצעו נתנו FCP
  זהה (‏984ms מול 984ms). זה ההסבר המתבקש לפער בביקור הראשון, והוא נשלל.
* **הוצאת CSS** — **לא**. נוסתה ב-`crm.html`, הציור הראשון עלה מ-916ms
  ל-1,432ms, והוחזרה. ‏`<link rel="stylesheet">` חוסם ציור עד שהקובץ
  מגיע; CSS מוטבע מגיע עם תחילת המסמך.

הפירוט המלא: `docs/agent-dashboard.md`.

## המגבלה שצריך לומר בקול

זו מדידה **מקומית**. אין בה את ה-CDN של Netlify, אין רשת אמיתית, ואין
את הזמן שהולך ל-Supabase. היא טובה להשוואה **יחסית** בין שתי גרסאות של
אותו דף על אותו מכשיר — וזו השאלה שהיא נועדה לענות עליה. ממצאי
‏`slow_ttfb` של הסוכן התפעולי, לעומת זאת, מודדים את השרת החי, ועליהם
היא אינה אומרת דבר.
