# המסלול לפרודקשן

מיזוג ל-`main` מפעיל עד שלושה מסלולים נפרדים: האתר ב-Netlify (שניות),
מיגרציות ב-`supabase_migrations.yml` ו-Edge Functions ב-`supabase_functions.yml`
(דקות). כל אחד נדלק רק מהקבצים שלו. ‏`docs/netlify-usage.md` הוא המסמך המלא.

## 1. דיפלוי ב-Netlify עולה כסף, ולכן הוא מבוקר

כל דיפלוי לפרודקשן עולה 15 קרדיטים, ובספטמבר-אוקטובר 2026 הצריכה הייתה כ-
‏2,000 קרדיטים ביום (‏$260-290 בחודש מעבר לתוכנית).

**‏`scripts/netlify_ignore.sh` מדלג על דיפלוי כשהשינוי כולו מחוץ לאתר:**
‏`docs/`, ‏`.claude/`, ‏`supabase/`, ‏`scripts/`, ‏`.github/`, המנועים, ‏`*.md` ו-
‏`*.py` בשורש. ‏`*.html`, ‏`assets/`, ‏`vendor/`, ‏`netlify/`, ‏`_headers`,
‏`_redirects` ושאר קובצי השורש **בונים**. בספק הוא בונה.

לכן, כשמציעים למשתמש/ת מה לעשות:

- **אין להציע "דיפלוי" או "לפרסם את האתר" על שינוי שכולו תיעוד, סקילים,
  מיגרציות, פונקציות Supabase או בדיקות.** הוא אינו מגיע ל-Netlify בכלל.
  מיגרציה ופונקציה עולות ב-Actions, ותיעוד אינו עולה לשום מקום.
- **שינוי קטן באתר שאינו דחוף מצטרף ל-PR פתוח** של אותו נושא, ולא נפתח PR
  נפרד שימוזג לבד. כל מיזוג שנוגע באתר הוא דיפלוי.
- **תיקון שעבודה של גולשים תלויה בו נכנס מיד.** החיסכון אינו סיבה לעכב תקלה.
- **לא מוסיפים תיקייה לרשימת הדילוג בלי שורה ב-`scripts/netlify_ignore_test.sh`**,
  ולא מוסיפים תיקייה שהאתר מגיש או שפונקציות ה-edge מייבאות ממנה (הן מייבאות
  מ-`assets/`). דיפלוי שדולג בטעות שקט לגמרי: האתר פשוט נשאר על הקוד הישן.
- **‏`[deploy]` בהודעת הקומיט** מכריח דיפלוי כשבאמת צריך לפרסם בלי שינוי.

## 2. הסדר: האתר עולה לפני המסד

האתר באוויר תוך שניות, והמיגרציה רצה דקה עד שלוש אחריו. בחלון הזה הקוד
החדש מדבר עם הסכימה הישנה. שלוש פעמים זה כבר הפיל דף ("עמודה לא קיימת").

| השינוי | הסדר |
| --- | --- |
| קוד שקורא עמודה, טבלה, view או RPC חדשים | או שהקוד סובל את היעדרם (שגיאה מטופלת, לא דף ריק), או **מיגרציה קודם** ב-PR משלה, ורק אחרי שה-workflow ירוק - הקוד |
| ‏`drop column`, ‏`rename`, שינוי חתימה של RPC | **הקוד קודם** (מפסיק להשתמש), המיגרציה אחריו |
| דף שקורא ל-Edge Function חדשה | הפונקציה נפרסת ב-Actions אחרי המיזוג. אותו כלל: סובלנות או פיצול |
| מיגרציה שהקוד הקיים אינו נוגע בה | ‏PR אחד, בלי חשש |

‏PR של מיגרציה בלבד אינו עולה דיפלוי ב-Netlify, ולכן הפיצול הזה חינם.

**אחרי מיזוג שכולל מיגרציה או פונקציה - מבט אחד ב-Actions.** ‏workflow אדום
שם הוא תקלת פרודקשן ולא רעש CI: ה-HTML כבר באוויר, והסכימה לא. אם הרשומה
שחוסמת נוצרה מהחלה מחוץ לצינור של מיגרציה שקיימת כקובץ, ה-workflow מיישר
אותה בעצמו ומדווח באזהרה; בכל מקרה אחר הוא נכשל ומדפיס את ה-DDL של הרשומה.
הסיפור המלא: `docs/supabase-migrations.md`.

## 3. לא לדרוס PR אחר

כמה סשנים עובדים במקביל, וכל אחד יצא מ-`main` של רגע אחר. שני קבצים תקינים
כל אחד לבדו יכולים למחוק זה את זה במיזוג, בלי שגיאה.

### לפני מיזוג

```sh
git fetch origin main
git merge origin/main          # מיזוג, לא rebase - על ענף של מישהו אחר בוודאי
# ‏הבדיקות של ה-PR שוב, ואז: ההבדל מול main הוא רק מה שה-PR שינה
git diff --stat origin/main...HEAD
```

**באמצע מיזוג אסור `git checkout HEAD -- <קובץ>`:** זה מחזיר את הגרסה של
הענף ומוחק בשקט את מה שהמיזוג הביא מ-`main` לאותו קובץ. כדי להתחיל מחדש:
‏`git merge --abort`, ומיזוג נקי. ובסוף, הבדיקה שהמיזוג לא איבד דבר:

```sh
B=$(git merge-base <ראש-ה-PR-המקורי> origin/main)
diff <(git diff --name-only origin/main HEAD | sort) <(git diff --name-only $B <ראש-ה-PR-המקורי> | sort)
```

### מספר מיגרציה שנתפס

‏`check_migration_versions.py` תופס version כפול רק מול ה-`main` שה-PR ראה.
‏PR אחר שמוזג אחרי שה-PR שלכם עבר ירוק יכול לקחת אותו מספר (‏`20261225090000`
נתפס כך, ‏25 שניות לפני המיזוג). לכן כשיש עוד PR פתוח שנוגע במיגרציות:

```sh
git fetch origin main && python3 scripts/check_migration_versions.py --base-ref origin/main
```

כשהמספר נתפס, מעבירים את הקובץ ב-`git mv` למספר שגדול מהאחרון ב-`main`,
ואז מחפשים את **המספר הישן** בכל הריפו (‏`git grep -n "<המספר הישן>"`). **לא
מחליפים בעיוורון:** המספר הכפול שייך גם למיגרציה של `main`, וחלק מההפניות
הן שלה (ב-#702 ‏`20270416090000` היה גם `mfa_enforcement` וגם
‏`property_view_counts`). בודקים כל הפניה בהקשר, או מחליפים רק בקבצים
שה-PR עצמו הוסיף או שינה.

### רשימה סגורה ופונקציה שמוחלפת

אילוץ `check (x in (...))` ופונקציה ב-`create or replace` נכתבים כולם מחדש
בכל מיגרציה, ומי שממוזג שני מוחק את מה שהראשון הוסיף. מוסיפים למה שקיים
(‏`notification_types_add`), ולפני מיזוג בודקים שאין מיגרציה חדשה ב-`main`
שמגדירה את הפונקציה מחדש. הפירוט: הסקיל `new-migration`, כלל 8.

### הגנת הענף

הכללים שלמעלה נאכפים רק אם `main` דורש אותם. ב-GitHub → Settings → Branches:
הבדיקות `גרסאות מיגרציה` ו-`הרשאות פונקציות` נדרשות, ו-*Require branches to
be up to date before merging* מסומן. זו הגדרה ידנית של בעל/ת הריפו - אם היא
חסרה, לומר את זה ולא להניח שהיא קיימת.
