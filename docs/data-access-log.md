# יומן גישה למידע

‏`data_access_log` עונה על "מי ניגש לאיזה מידע, מתי, ומאיפה", כולל ניסיונות
שנדחו. זו הדרישה של **תקנה 10 לתקנות הגנת הפרטיות (אבטחת מידע), תשע"ז-2017**
למאגר ברמת אבטחה בינונית ומעלה. היומן משלים את `security_audit_log`
(`docs/security-audit-log.md`): שם נרשם מי **שינה** הרשאות, וכאן מי **קרא**.

## איך הוא מתמלא

טריגר לא יכול לעשות את זה: הוא אינו רואה `SELECT`, ו-PostgREST מריץ GET
בטרנזקציה לקריאה בלבד.

את המידע הזה כבר רושם שער ה-API של Supabase, על כל בקשה:

- **מי:** ה-`auth_user` מה-JWT, ה-`session_id` והתפקיד.
- **מה:** הטבלה או הפונקציה, והסינון (`?id=eq.…`).
- **התוצאה:** קוד התשובה.
- **מאיפה:** כתובת IP ומדינה.

הבעיה היחידה היא ש-Supabase שומרת את היומן **7 ימים**.

לכן `scripts/access_log_sync.py` רץ כל שעה (`.github/workflows/access_log.yml`).
הוא שואל את ה-Management API (`/analytics/endpoints/logs`, ‏SQL של ClickHouse)
על החלון שמאז הריצה הקודמת, וכותב ל-`data_access_log`.

| מה | איך |
| --- | --- |
| סמן | `data_access_log_sync.synced_until`. כל ריצה מתחילה 15 דקות לפניו, כי שורות לוג מגיעות באיחור |
| כפילות | `log_id` (המזהה של Supabase) הוא מפתח ראשי, ולכן החפיפה אינה מכפילה שורות |
| תקרת 1,000 שורות לשאילתה | חלון שהחזיר 1,000 מתפצל לשניים עד שהוא נכנס. אחרת השורות שמעבר לתקרה היו נעלמות בשקט |
| ריצה שלא יצאה | הריצה הבאה ממשיכה מהסמן, עד 6 ימים אחורה |
| מגבלת קצב (429) | חלונות של 3 שעות והפסקה של 2 שניות בין בקשות. ‏429 שנשאר אחרי ההמתנות עוצר את הריצה **ירוקה עם אזהרה** והסמן נשאר במקום שאליו הגיעה. הריצה הבאה ממשיכה משם. ‏429 לפני החלון הראשון הוא כישלון |
| סודות | `SUPABASE_LOGS_TOKEN` (ראו "הטוקן" למטה) ו-`SUPABASE_DB_URL` |

## הטוקן

ה-Management API דורש הרשאת `analytics_logs_read`. הטוקן שפורס את הפונקציות
(`SUPABASE_ACCESS_TOKEN`) אינו נושא אותה. הריצה הראשונה (13.10.2026) נכשלה
ב-403 בגלל זה.

**הפתרון:** טוקן נפרד בסוד `SUPABASE_LOGS_TOKEN`.

1. ב-Supabase, ב-Account ← Access Tokens, ליצור טוקן עם הרשאת קריאה ליומנים
   (Analytics / Logs read) על הפרויקט.
2. ב-GitHub, ב-Settings ← Secrets and variables ← Actions, להוסיף אותו בשם
   `SUPABASE_LOGS_TOKEN`.

ה-workflow לוקח את `SUPABASE_LOGS_TOKEN` אם הוא קיים, ואחרת את הישן.

**ההרשאה המינימלית** (נוצר כך ב-21.10.2026): ‏Resource access ← Project, רק
‏`shuknadlan-marketplace`. ‏Permissions ← Preset · **No access**, ואז תחת
‏Project רק השורה **Logs ← Read**. ‏הסקריפט קורא כתובת אחת בלבד. ה-Preset
‏Read-only נותן גם קריאת SQL למסד, וזה לא נחוץ לטוקן שיושב ב-GitHub.

**ההשבתה הראשונה:** מ-13.10 עד 21.10.2026 הסוד לא היה קיים, וכל 45 הריצות
נכשלו ב-403. ‏בזמן הזה היומנים של 13-14.10 כבר נמחקו אצל Supabase. ההשלמה
התחילה מ-15.10.

## מה נכנס

- **בקשות של משתמשים מחוברים:** כל בקשה של משתמש/ת מחובר/ת (`authenticated`)
  או של `service_role`. זה כולל REST, ‏Storage, ‏Functions ו-GraphQL.
- **בקשות שנדחו:** כל בקשה שנדחתה (401/403), גם בלי התחברות. זה הניסיון
  לגשת שהתקנה מבקשת לתעד.
- **אירועי Auth:** כניסה, יציאה, שחזור סיסמה (`kind = 'auth'`).
  ‏`auth.audit_log_entries` במסד ריק: Supabase כותבת אותם רק ליומן.

**מה לא נכנס, ולמה:**

| מה | למה |
| --- | --- |
| בקשות אנונימיות שהצליחו | גולשים באתר הציבורי. ‏RLS מבטיח שהם רואים רק מידע ציבורי |
| טבלאות עזר ציבוריות ונכסים ציבוריים | שכונות, רחובות, ערים, `*_public`, תמונות נכסים. אין בהם מידע על אדם, והם כ-40% מהתעבורה. הרשימה ב-`EXCLUDED_PATHS` |

**מי שמוסיף/ה טבלה לרשימת ההחרגה מוודא/ת קודם שאין בה שדה של אדם.** טבלה
שמחזיקה שם, טלפון, מייל או הערה נשארת ביומן.

## כמה זמן

**3 שנים** (החלטת הבעלים, 13.10.2026). התקנה דורשת לפחות 24 חודשים, והשנה
הנוספת היא מרווח לחקירת אירוע ישן. ‏`data_access_log_purge()` רצה כל לילה
(cron ‏`data-access-log-purge`, 03:41 UTC) ומוחקת מה שישן יותר.

**גודל:** כ-5,200 שורות ביום, כלומר כ-5.7 מיליון שורות בשלוש שנים. זה
בערך 2GB במסד.

## מי רואה

- **מי:** מנהל/ת פלטפורמה בלבד (RLS).
- **איפה:** ב-CRM, בפאנל "יומן ביקורת אבטחה", תחת "גישה למידע".
- **מה מוצג:** סיכום לפי משתמש/ת ויום: בקשות, דחיות, כמה טבלאות שונות,
  וכמה כתובות IP. הסיכום מגיע מ-`data_access_summary(p_days)` (עד 90 ימים).
- **פירוט מלא:** בשאילתה על הטבלה, עם `user_id`, `path` ו-`query`.

**מה לחפש בסקירה:**

- **משתמש/ת עם הרבה יותר בקשות מהרגיל:** יכול להעיד על ייצוא או גריפה.
- **הרבה כתובות IP ביום אחד:** session שנגנב.
- **דחיות (401/403) חוזרות:** ניסיון לגשת למה שאסור.

## כשהיומן עומד

הסוכן התפעולי בודק את הסמן בכל סריקה (`access_log_stale` ב-
`ops_agent/probes/pipeline.py`):

| כמה זמן בלי ריצה מוצלחת | חומרה | למה |
| --- | --- | --- |
| 6 שעות | גבוהה | |
| 4 ימים | חמורה | נשארים פחות מ-3 ימים עד שהתיעוד נמחק אצל Supabase ואובד |

הבדיקה היא על הסמן ולא על מספר השורות, **כי יומן שהפסיק להתמלא נראה בדיוק
כמו שבוע שקט**.

**הטיפול:**

1. לפתוח את `access_log.yml` בלשונית Actions.
2. לקרוא את השגיאה. היא נשמרת גם ב-`data_access_log_sync.last_error`.
3. להריץ ידנית (`workflow_dispatch`).
