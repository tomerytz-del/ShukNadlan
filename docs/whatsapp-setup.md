# העוזר האישי בוואטסאפ (Meta WhatsApp Cloud API)

סוכן/ת שולח/ת הודעה בוואטסאפ — טקסט, תמונות או הקלטה קולית — והעוזר מטפל
בנכסים, בקובץ הלקוחות, בהתאמות ביניהם, מכין קישור והודעה מוכנה על נכס,
מפיק דוח שוק ומידע תכנוני, קובע פגישות ותזכורות ביומן
(ראו [`agent-agenda.md`](agent-agenda.md)), וקורא עבורו/ה את ההסכמים, הלידים וההתראות. הוא מזהה מי שלח לפי מספר הטלפון, מבצע את הפעולה במסד ומשיב
בוואטסאפ. ומהכיוון ההפוך: **התראות הפעמון יכולות לצאת אליו/ה בוואטסאפ**,
לפי סוגים שהוא/היא מסמן/ת. **ומייל שהסוכן/ת מעביר/ה לכתובת האישית שלו/ה
נכנס לאותה שיחה** — לקוח/ה שפנה/תה במייל נכנס/ת לקובץ, והתשובה מגיעה
בוואטסאפ ([`email-intake.md`](email-intake.md)).

> **לעוזרת יש שם: גבריאלה.** היא מדברת על עצמה בלשון נקבה, ומציגה את עצמה
> בשם בתשובה הראשונה **פעם אחת לכל סוכן/ת**. ההיסטוריה כאן אינה מתאפסת,
> ולכן "היסטוריה ריקה" הייתה מציגה אותה רק לסוכנים חדשים; ‏`index.ts` בודק
> במקום זה ביומן (`whatsapp_messages`) אם השם כבר נאמר, ומעביר
> `conv.introduce` ל-`sessionContext`. אותו שם גם לבוט הציבורי
> ([`whatsapp-public-bot.md`](whatsapp-public-bot.md)).
>
> **והשם מופיע גם באתר:** הקטגוריה ב-CRM ("גבריאלה - העוזרת האישית
> בוואטסאפ", ובניווט "גבריאלה בוואטסאפ"), הכרטיס שפותח את הצ'אט, שלב החיבור
> במדריך ההתחלה, השורות ב-`pricing.html` וב-`assets/tiers.js` (ולכן גם
> המפתחות ב-`scripts/check_tier_gates.py`), `privacy.html`, והכפתור בדף הבית
> במסך אפס התוצאות. שינוי שם עתידי עובר בכל המקומות האלה יחד.

## איך זה עובד

```

      │
      ▼
Meta WhatsApp Cloud API  ──Webhook (POST)──►  Edge Function: whatsapp-webhook

                                     1. אימות חתימת HMAC מול App Secret
```

## שלב 1 — הגדרה ב-Meta for Developers

1. היכנסו ל-[developers.facebook.com](https://developers.facebook.com/) עם חשבון שמקושר ל-Meta Business.
2. **Create App** → סוג **Business** → הוסיפו את המוצר **WhatsApp**.
3. במסך **WhatsApp → API Setup** תמצאו:
   - **Phone number ID** — המזהה של המספר העסקי (לא המספר עצמו). זה `WHATSAPP_PHONE_NUMBER_ID`.
   - **Temporary access token** — טוקן ל-24 שעות, טוב לבדיקות בלבד.
4. **טוקן קבוע (חובה לפרודקשן):** Business Settings → **System Users** → צרו System User עם תפקיד Admin →
   **Add Assets** → שייכו את ה-WhatsApp Account → **Generate New Token** עם ההרשאות
   `whatsapp_business_messaging` ו-`whatsapp_business_management`. הטוקן הזה לא פג. זה `WHATSAPP_TOKEN`.
5. **App Secret:** App Settings → Basic → **App Secret** → Show. זה `WHATSAPP_APP_SECRET`.

> בזמן פיתוח, Meta מרשה לשלוח רק למספרים שנוספו ידנית תחת **API Setup → To**.
> כדי לשלוח לכל סוכן/ת צריך להעביר את האפליקציה ל-Live ולעבור Business Verification.

> הפונקציה חשופה בלי JWT, וחתימת ה-HMAC היא שכבת האימות היחידה שלה.

## שלב 3 — חיבור הוובהוק

כתובת הוובהוק:

```
https://obookujgolazrwycsiyn.supabase.co/functions/v1/whatsapp-webhook
```

ב-Meta: **WhatsApp → Configuration → Webhook → Edit**

- **Callback URL** — הכתובת למעלה
- **Verify token** — אותה מחרוזת שהגדרתם ב-`WHATSAPP_VERIFY_TOKEN`
- לחצו **Verify and save** (Meta שולחת GET; הפונקציה מחזירה את ה-challenge)
- תחת **Webhook fields** — סמנו **messages**

הפונקציה כבר פרוסה עם `verify_jwt = false`. אם פורסים מחדש מה-CLI:

```bash
supabase functions deploy whatsapp-webhook --no-verify-jwt
```

## שלב 4 — זיהוי הסוכנים

הבוט מזהה את הסוכן/ת לפי `agency_members.phone`. כל סוכן/ת מגדיר/ה את המספר בעצמו/ה:

**דשבורד הסוכן (`crm.html`) → "גבריאלה בוואטסאפ" → מספר הוואטסאפ שלי**

אפשר גם ידנית:

```sql
update public.agency_members set phone = '050-1234567' where id = '<agent-uuid>';
```

הנרמול נעשה אוטומטית בעמודה המחושבת `phone_e164`, שמטפלת בכל הפורמטים הנפוצים:

| מה שהוזן | `phone_e164` |
|---|---|
| `0521112222` | `972521112222` |
| `+972-52-333-4444` | `972523334444` |
| `521112222` | `972521112222` |
| `00972501234567` | `972501234567` |
| `04-6512345` | `97246512345` |

יש אינדקס ייחודי על `phone_e164` — שני סוכנים לא יכולים לחלוק מספר, אחרת אי אפשר
לדעת בשם מי לפעול. ניסיון לשמור מספר תפוס מחזיר שגיאה ברורה בדשבורד.

**מספר שלא מזוהה מקבל:** "סליחה, איני מזהה את מספר הטלפון שלך כמורשה במערכת."
— אלא אם **הבוט הציבורי** דלוק, ואז אותו מספר מגיע לענף אחר לגמרי: בוט
קריאה-בלבד שמחפש נכסים במאגר וממליץ על משרדים. הוא חולק את המספר ואת
הוובהוק הזה ותו לא — לא את הכלים, לא את ההוראות ולא את ההרשאות.
הפרטים, כולל המתג: [`whatsapp-public-bot.md`](whatsapp-public-bot.md).

### ואיך הסוכן/ת יודע/ת לאן לשלוח

עד שנשאלה השאלה, לא היה לזה שום מקום במוצר: הקטגוריה אמרה "שולחים הודעה
למספר של שוק נדל״ן" ולא אמרה מהו, והמספר היחיד שהיה כתוב ישב בתיעוד הזה —
מסמך שסוכן/ת לא רואה לעולם. סוכן/ת חדש/ה שמר/ה את המספר שלו/ה ונשאר/ה בלי
לאן לשלוח.

לכן בראש הקטגוריה יש עכשיו כרטיס עם **המספר עצמו** וכפתור **"פתיחת צ'אט עם
העוזר"** (`wa.me`), והוא קודם לטופס: "מול איזה מספר אני עובד/ת" היא השאלה
הראשונה, לא האחרונה.

שלוש החלטות בכרטיס הזה:

- **‏`wa.me` ולא "העתיקו את המספר".** בטלפון זה פותח את הצ'אט הנכון בלחיצה,
  ומונע את שתי הטעויות שאי אפשר לאתר אחר כך — ספרה שהוקלדה לא נכון, ושליחה
  ממכשיר אחר מזה שרשום במערכת.
- **הכפתור מושבת עד שנשמר מספר**, ואומר "קודם שמרו את המספר שלכם למטה".
  הודעה ממספר שאינו רשום מקבלת "איני מזהה את מספר הטלפון שלך" — חוויה
  ראשונה גרועה שאפשר פשוט למנוע. כפתור שנעלם נראה כמו באג; כפתור שאומר מה
  חסר הוא הוראה.
- **הקישור נושא הודעת פתיחה** (`?text=`). לא קישוט: היא חוסכת את "מה כותבים
  לבוט" ברגע שבו רוב האנשים סוגרים את החלון, **והיא פותחת את חלון 24 השעות
  של Meta** — מה שמאפשר להתראות לצאת כטקסט חופשי מלא ובחינם במקום כתבנית.

המספר יושב ב-`ASSISTANT_WA_NUMBER` ב-`crm.html` ולא ב-Secrets: הוא מזהה
ציבורי שמודפס על כל הודעה שהעוזר שולח, ולא סוד. **מספר שמוחלף ב-Meta מתעדכן
בשתי נקודות בלבד** — השורה ההיא, וטבלת המזהים למטה במסמך הזה.

## מה העוזר יודע לעשות

שלושים ואחד כלים בשמונה תחומים. ל-LLM אין גישה ל-SQL — **כל כלי מקבע בעצמו
את `agent_id`**, ולכן הוא אינו יכול לגעת בנכס או בלקוח/ה של סוכן/ת אחר/ת גם
אם ינסה.

### הקלטת שיחה ומסמכים

סוכן/ת שולח/ת לגבריאלה **קובץ** - הקלטת שיחה מהטלפון, או מסמך - והיא מסכמת
ומציעה מה לעשות איתו. ‏`media-intake.ts`.

| מה נשלח | איך נקרא |
|---|---|
| הודעה קולית (מיקרופון בוואטסאפ, ‏`audio.voice = true`) | כמו תמיד - תמלול, ומשם **הוראה** של הסוכן/ת |
| קובץ שמע (‏`audio` בלי `voice`, או `document` שהוא שמע) | **הקלטת שיחה**: תמלול עם אוצר המילים של הסוכן/ת (הערים והשכונות, כמו במספר הווירטואלי) |
| PDF | ‏Claude (‏`MEDIA_EXTRACT_MODEL`, ברירת מחדל `claude-sonnet-5`) מעתיק לטקסט - גם סריקה, עד 100 עמודים |
| Word ‏(‎.docx‎), ‏PowerPoint, ‏ODT | חילוץ בקוד (‏fflate), טבלה כשורות עם " \| " |
| Excel ‏(‎.xlsx/.xls/.ods‎) | ‏SheetJS, כל גיליון כ-CSV, עד 2,000 שורות לגיליון |
| CSV / טקסט | ‏UTF-8, ואחרת Windows-1255 (‏CSV מאקסל ישן בעברית) |
| תמונה שנשלחה כקובץ | כמו תמונה רגילה |
| ‏‎.doc‎ ישן, ‏AMR, ‏zip וכו' | תשובה שאומרת מה לשנות (לשמור כ-PDF; לשנות את פורמט המקליט ל-M4A) |

**שלושה דברים ששומרים על זה:**

* **הכול הופך לטקסט לפני הרצף**, ולא נשלח כבלוק מסמך לתור. הרצף מריץ רק
  את ההודעה האחרונה בו, ובלוק שנבנה בהודעה שאינה האחרונה ("PDF" ואחריו
  "תוסיפי אותו") היה נעלם.
* **התוכן נכתב בידי אחרים**, ולכן הוא עטוף בסימון (‏`[הקלטת שיחה - תמלול...]` /
  ‏`[מסמך שהתקבל...]` ... ‏`[סוף הקובץ]`, וסוגריים מרובעים בתוכו הופכים
  לעגולים), והתור שקורא אותו מקבל רק את `MEDIA_TOOLS` - כלי קריאה. גבריאלה
  מסכמת ומציעה, ו"כן" של הסוכן/ת בתור הבא מבצע עם כל הכלים. זה אותו עיקרון
  כמו במייל מועבר (‏`EMAIL_TOOLS`), בלי שום כתיבה.
* **בהיסטוריה נשמרים רק 2,500 התווים הראשונים** של התוכן (‏`mediaForHistory`),
  בלי ההנחיות. מה שמבוצע אחרי "כן" נלקח מהסיכום של גבריאלה, שנשמר בשלמותו.

הקובץ עצמו אינו נשמר. ביומן (‏`whatsapp_messages.body`) נכתב התמלול של
הקלטה, ושם הקובץ של מסמך. ‏`privacy.html`, "עיבוד בבינה מלאכותית".

**התמלול משותף עם המספר הווירטואלי** (‏`_shared/whisper.ts`): הקלטות מאנדרואיד
מגיעות במעטפת 3gp או כ-aac, ו-Whisper דוחה אותן ב-`Invalid file format` כשהשם
נגזר מהסוג. ב-11.10.2026 קובץ ‏`AUD-...` נדחה כך בוואטסאפ - הסיומת נגזרה מ-
‏`mime_type` בלבד, בלי הניסיון החוזר וההחלפה של המותג שכבר עבדו ב-`twilio-voice`.
מי שמשנה את התמלול משנה אותו שם, לשני הצרכנים.

**זמן:** הקלטה של חצי שעה היא כ-30-60 שניות ב-Whisper, ו-PDF ארוך עוד כמה
עשרות שניות ב-Claude, לפני התור עצמו. זה רץ ברקע (‏`waitUntil`), בתוך מגבלת
הזמן של ה-Edge Function.

### נכס מקישור לקטלוג וואטסאפ

סוכן/ת מדביק/ה קישור לפריט בקטלוג של חשבון וואטסאפ ביזנס
(`https://wa.me/p/27819896911014194/972542540007`), וגבריאלה מציגה טיוטת נכס.
אין כאן כלי חדש: הקישור נקרא ב-`index.ts` **לפני** הרצף, והמודל מקבל את
הפריט כבלוק `[פריט מקטלוג וואטסאפ ...]` שמודבק להודעה.

**מה הקישור נותן, ומה לא.** ה-API של Meta אינו חושף קטלוג של עסק אחר, אבל
הדף ציבורי ונושא תגיות תצוגה מקדימה. נבדק מהשרת של Supabase (‏`pg_net`) ב-4.10.2026:

| תגית | מה יש בה |
|---|---|
| `og:title` | `<שם הפריט> from <שם העסק> on WhatsApp.` - שם הפריט הוא לרוב "למכירה", בלי ערך |
| `og:description` | התיאור, ואחרי `·` אחרון המחיר: `₪1,100,000.00` |
| `og:image` | **תמונה אחת**, 600x600, ב-`fbcdn.net` עם חתימה שפגה תוך כמה ימים |

אין בגוף הדף תמונות נוספות ואין JSON-LD. הכול מקודד כישויות ומלא בסימני
כיוון, ובבקשה בעברית הנוסח מתהפך (`... של <עסק> ב-WhatsApp.`, `1,100,000.00 ₪`).
הבקשה מבקשת אנגלית, והמפרק תומך בשניהם.

**ההחלטות:**

- **טיוטה ואישור, לא יצירה מיידית.** הכלל הרגיל ("סוג, עסקה ומחיר = יוצרים")
  אינו חל: התיאור נכתב למכירה ולא לטופס, "3 חדרי שינה" אינו 3 חדרים, ומספר
  בית, קומה ושטח כמעט תמיד חסרים. ההוראה ב-`SYSTEM_STATIC`.
- **הטקסט הוא נתונים.** הוא נכתב בידי בעל/ת הקטלוג, מאותה סיבה שלתור מייל
  יש רשימת כלים סגורה. סוגריים מרובעים בתיאור מוחלפים בעגולים, כדי שתיאור
  לא יוכל לסגור את הבלוק ולפתוח "הוראה".
- **התמונה נשמרת אצלנו מיד**, כי הכתובת ב-CDN פגה. היא מורדת רק מ-`fbcdn.net`
  / `whatsapp.net` ב-https, והכתובת של הדף נבנית מחדש מהמספרים בקישור. שום
  טקסט חופשי מההודעה אינו מגיע ל-`fetch`.
- **התמונה מצטרפת לממתינות רק אחרי שהרצף נאסף**, ורק כשיש בתור פריט אחד.
  התמונות הממתינות הן מאגר אחד שמתחבר כולו לנכס הבא, ולכן שני פריטים ברצף
  אחד היו מחברים את שתי התמונות לנכס הראשון. בשניים ומעלה אף תמונה אינה
  מצטרפת, וגבריאלה מבקשת לשלוח אחד בכל פעם. מאותה סיבה נקרא רק הקישור
  הראשון בכל הודעה.
- **שורת התמונה נספרת רק כשהיא צמודה לסגירת הבלוק ובתיקייה של אותו/ה
  סוכן/ת** (`<agent_id>/whatsapp/`). שורה שנראית אותו דבר בתוך התיאור אינה תמונה.
- **"לא המספר של הסוכן/ת".** המספר שבקישור הוא של העסק. כשהוא אינו המספר של
  השולח/ת, גבריאלה שואלת על בלעדיות לפני שיוצרים. טריגר הכפילות במסד
  (‏[`property-status-exclusivity.md`](property-status-exclusivity.md)) חל
  ממילא, כמו על כל נכס.

**ה-Edge Function חסומה, המסד לא.** בניסיון האמיתי הראשון (4.10.2026, 17:45)
‏`wa.me` ענה **400** לבקשה מהפונקציה, ובאותה דקה אותו קישור עם אותן כותרות
החזיר 200 ואת כל הפריט מהמסד דרך `pg_net`. ההבדל הוא מאיפה הבקשה יוצאת. לכן:

1. בקשה ישירה, עם ה-User-Agent של סורק התצוגה המקדימה של Meta
   (`facebookexternalhit`). כישלון נרשם בלוג עם הסטטוס ו-300 התווים הראשונים.
2. אם היא נכשלה או שלא חזר בה פריט - `catalogPageViaDb`:
   ‏`whatsapp_catalog_fetch_start(product, phone)` שולח את הבקשה מהמסד
   (‏`pg_net` אסינכרוני), ו-`whatsapp_catalog_fetch_result(id)` נשאל כל 0.7
   שניות עד 12 שניות. הכתובת נבנית במסד מספרות בלבד, ושתי הפונקציות
   ל-`service_role` בלבד (מיגרציה `20270217090000`).

**התמונה אין לה גיבוי כזה**: ‏`pg_net` שומר את התשובה כטקסט, ותמונה נחתכת
בבית האפס הראשון. אם גם `fbcdn.net` חוסם את הפונקציה, הטיוטה עוברת בלי
תמונה ("לא הצלחתי לשמור את התמונה מהקטלוג"), והלוג אומר `catalog image fetch failed`.

**כשל** (הדף לא נטען, 404, פריט שהוסר) מגיע למודל כ-`[קישור לקטלוג וואטסאפ -
לא הצלחתי לקרוא את הפריט: ...]`, וההוראה היא לבקש את הפרטים ולא לנחש.

**הבדיקה:** `node --experimental-strip-types scripts/catalog_link_test.ts`, ב-CI
בתוך `edge_types.yml`. הדף מדומה בצורה של הדף האמיתי, כי `wa.me` אינו זמין
מ-CI (וגם לא מסביבת הפיתוח בענן - שם הבדיקה החיה נעשתה דרך `pg_net`).

### הפרופיל האישי - דף הסוכן/ת באתר

| כלי | מה זה עושה |
|---|---|
| `profile_get` | הפרופיל כפי שהוא בדף (`/agent?slug=`), ומה חסר בו |
| `update_profile` | שם, ביו, אזורי פעילות (רק מרשימת האזורים, `service_markets`), השכלה/הסמכות, ותק ותחומי התמחות; ותמונה שנשלחה בשיחה כתמונת פרופיל (`photo=profile`). אין תמונת נושא אישית: `photo=cover` מחזיר `cover_is_agency` והסבר, כי הרצועה היא תמונת המשרד. `default_city` שומרת עיר קבועה לנכס חדש (דרך `city_id_for_name`); מחרוזת ריקה מוחקת |

**עיר ברירת מחדל לנכס.** `default_city` ב-`update_profile` נשמרת ב-
`agency_members.default_city_id` אחרי `city_id_for_name` (כולל כינויים). זו
אינה `service_area` ואינה עיר ברירת המחדל של טופס לידים. נכס חדש בלי עיר
נופל אליה, ורק אם אין - לעיר המשרד. לפני שהמיגרציה רצה הקריאה נכשלת בשקט
(`42703` או `PGRST204`) והיצירה נשארת על עיר המשרד. העיר לפרומפט נלקחת
ממה שכבר נטען עם הפרופיל באותו תור, בלי שאילתה נוספת. מנהל/ת משרד אינו/ה
משנה את העיר של סוכן/ת אחר/ת: הטריגר מחזיר את הערך הקודם כשזה לא העדכון
העצמי. `anon` אינו כותב לטבלה. כמה נכסים שנוצרים באותו תור יוצאים עם כפתור
"עריכה ב-CRM" אחד אל רשימת הנכסים, לא כפתור לכל נכס. נכס יחיד נשאר עם
הכפתור שלו.

**רשימה סגורה של שדות, וזה הגבול היחיד.** הבוט רץ כ-service_role, ו-
`protect_sensitive_agency_member_fields` מדלגת על service_role לגמרי: מסלול,
יתרה, רישיון וסגירת חשבון היו נכתבים כמו כל שדה. לכן `update_profile` בונה
את ה-patch רק מ-`PROFILE_TEXT_FIELDS` ומהשדות המפורשים שאחריו, ולעולם לא
מהקלט כפי שהוא. **טלפון אינו נערך כאן** - לפיו הבוט מזהה את הסוכן/ת, ושינוי
שלו מהצ'אט היה מנתק את השיחה עצמה. גם מספר רישיון לא.

- **תמונה.** נלקחת מהרשימה הממתינה (‏`whatsapp_pending_images_take`), כך שאותה
  תמונה לא תגיע גם לנכס. כמה תמונות - האחרונה נבחרת והשאר חוזרות לרשימה.
  אותו bucket של ה-CRM (‏`property-images`), ולכן אין העתקה.
- **תחומי התמחות.** אותו אוצר מילים סגור של `SPECIALTY_OPTIONS` ב-`crm.js`,
  עד ארבעה.

### התזכורת על פרופיל חסר

כשחסר בפרופיל אחד מחמשת הפריטים שגולש/ת מחפש/ת (תמונה, ביו של משפט לפחות,
אזור, תחומי התמחות, ותק - `profileGaps`), התשובה של הבוט מסתיימת בשורה:

> 💡 בדף הסוכן/ת שלך באתר עדיין חסר: תמונת פרופיל, אזור פעילות. אפשר פשוט
> לשלוח לי את זה כאן - למשל תמונה שלך עם הכיתוב "תמונת פרופיל".

| החלטה | למה |
| --- | --- |
| השורה נכתבת **בקוד** (`profileNudge` ב-`index.ts`) ולא מבוקשת מהמודל | הוראה בפרומפט הייתה חוזרת בכל תשובה או נשכחת, ואין דרך לדעת איזה מהשניים |
| פעם בשבוע לכל היותר | ‏`whatsapp_profile_nudge_claim` (מיגרציה `20270115098000`) - עדכון מותנה אחד, כך שאלבום של בקשות מקבילות אינו מזכיר פעמיים |
| לא בתור שבו הסוכן/ת כבר עוסק/ת בפרופיל | ‏`profile_touched` על השיחה, לתור הנוכחי בלבד |
| הפרופיל נקרא **אחרי** התור | מה שנשלח בתור עצמו לא יוזכר כחסר |
| תמונת נושא אינה ברשימה | היא של המשרד, ומנהל/ת המשרד קובע/ת אותה לכל הסוכנים |

החסרים נכנסים גם להקשר של המודל (`sessionContext`), כדי ש"אני 12 שנה בתחום"
אחרי התזכורת ייקרא כעדכון פרופיל ולא כשיחה.

### החיפוש מכסה את כל האזור, לא רק את המלאי שלי

עד 5.10.2026 לסוכן/ת לא היה חיפוש חופשי. ‏`list_properties` מחפש רק בנכסים
של הסוכן/ת, ו-`client_matches` דורש לקוח/ה בקובץ ומכסה משרד ושיתופים בלבד.
סוכן שכתב "אני מחפש דירה 4 חדרים בעפולה מ-800 אלף עד 1.2 מיליון" קיבל "אין
לך עדיין נכסים במערכת" - כשבאזור היו ארבע כאלה (אחת ששותפה עם המשרד ושלוש
של מתווכים אחרים).

* **`market`** = כל הנכסים **הפעילים** בערים שה-`market_slug` שלהן הוא של
  עיר המשרד (‏`agencies.city_id`). אלה אותם נכסים שכל גולש רואה באתר, ולכן
  מספר הבית שלהם מוסתר גם כאן - המתווך/ת המפרסם/ת הוא/היא הכתובת לפרטים.
* **הסינון משותף עם הבוט הציבורי** (‏`property-search.ts`): שכונה מנורמלת
  וכינויים, סוג נכס בהתאמה חלקית. ההבדל בין הבוטים הוא המאגר, לא הסינון.
* **נכס `market` אינו נכנס למיניסייט** - `agent_showcase_add_properties`
  מקבל רק נכסי המשרד ומה ששותף איתו. הדרך היא תיאום עם המתווך/ת ושיתוף.
* **`or` אחד בבקשה.** המאגרים, הערים וסוגי הנכס הם שלוש קבוצות "או", והן
  נכתבות כ-`and(or(...),or(...))` בפרמטר יחיד (נבדק מול המסד החי).

### דרישה מפורשת היא חובה - ושואלים לפני שמוותרים

סוכנים התלוננו (‏11.10.2026) שלקוח/ה שביקש/ה ממ״ד ומעלית קיבל/ה מגבריאלה
נכסים בלי אחד מהם: ב-`client_matches` מאפייני החובה היו ניקוד בלבד (‏‎-8‎
למאפיין), ונכס בלי שניהם קיבל 84.

* **`client_matches`** - מאפייני החובה של הכרטיס הם סינון קשיח ב-
  `client_property_match` (‏`docs/client-matching.md`, "ויתור על מאפיין חובה").
* **`search_properties`** - ‏`features` הם סינון קשיח (‏`contains`), כמו קודם;
  ההוראה ב-`SYSTEM_STATIC` אומרת שדרישה מפורשת בשאלה ("עם ממ״ד") נכנסת לשם.
* **כשאין אף נכס עם הכול** - שני הכלים מחזירים `without_required`: כמה
  נכסים יש בלי הדרישה, ולפי איזה מאפיין חסר (‏`by_feature`). גבריאלה
  **שואלת** ("יש 3 בלי מעלית - להציג?") ולא מציגה מעצמה. אחרי "כן":
  `client_matches` עם `waive_features`, או `search_properties` בלי המאפיין,
  וליד כל נכס כזה כתוב מה חסר בו (`missing_required`).
* **הוויתור אינו נשמר בכרטיס.** דרישה שירדה באמת = `update_client`. דרישה
  שהסוכן/ת אישר/ה כחובה ("דני צריך ממ״ד") נכנסת ל-`required_features`
  לפני `client_matches`. מאפיין שעולה רק מההערות נשמר ב-`preferred_features`
  (דירוג), ורק כשההערות נשלחו באותו עדכון. עדכון של טלפון או סטטוס לא
  גוזר אותן מחדש ולא שואל שוב על עסקה, עיר או תקציב.
* `create_showcase` בלי `property_ids` לוקח רק התאמות מלאות; אחרי ויתור -
  עם `property_ids` של מה שהוצג.

### הקישור לנכס — הבוט מכין, הסוכן/ת שולח/ת

‏`property_link` מחזיר שלושה דברים: את הקישור לדף הנכס, **הודעה מוכנה**
(כותרת, כתובת, חדרים, שטח, מחיר וקישור), וכתובת `wa.me` שפותחת את וואטסאפ
עם ההודעה כבר בפנים. עם `client_id` מקובץ הלקוחות ההודעה נפתחת בפנייה בשם,
ו-`wa.me` מכוון ישירות לצ'אט של אותו/ה לקוח/ה.

**הבוט אינו שולח ללקוח/ה**, ומאותה סיבה בדיוק ש-`agreement_sign_links` אינו
שולח: ההודעה יוצאת מהמספר של הסוכן/ת, נקראת אישית ולא כהודעת מערכת, ומי
שמחליט/ה למי היא נשלחת הוא/היא מי שמכיר/ה את הצדדים. זו גם אותה תבנית של
כפתור "💬 שליחה בוואטסאפ" בכל מקום בדשבורד — `window.open('https://wa.me/…')`
ולא קריאה לשרת.

**קישור לנכס שאינו `active` חוזר עם אזהרה.** ה-policy על `properties`
מחזירה לגולש/ת אנונימי/ת נכסים פעילים בלבד, ולכן קישור לנכס בארכיון ייפתח
אצל הסוכן/ת ויראה דף ריק אצל הלקוח/ה. הכלי אומר את זה במקום שזה יתגלה אחרי
השליחה.

### דוח השוק והמידע התכנוני — למה הם עברו למסד

‏`cma_report` ו-`property_planning_public` גוזרות את זהות הסוכן/ת מ-`auth.uid()`.
זו ההחלטה הנכונה לדפדפן, ובדיוק הסיבה שהבוט לא יכול לקרוא להן: הוא מזהה
לפי מספר טלפון ורץ עם `service_role`, כך ש-`auth.uid()` שלו הוא `null`.
אותה בעיה של הלקוחות וההתאמות ב-`20261029090000`, ואותו פתרון —
‏`agent_cma_report(p_agent_id, p_property_id)` ו-
‏`agent_property_planning(p_agent_id, p_property_id)`, מוענקות ל-`service_role`
בלבד.

**כל ההיגיון של ה-CMA עבר דירה ולא הועתק.** ‏`cma_report` נשארה בדיוק באותה
חתימה ועם אותם קודי שגיאה (‏`crm.html` ממפה אותם להודעות), והיא עכשיו עוטפת
את `agent_cma_report` עם `current_agent_id()`. שני עותקים של הרחבת הרדיוס
ושל חישוב המחיר למ״ר היו מתפצלים תוך חודש, והסוכן/ת היה/הייתה מקבל/ת
בוואטסאפ מספר אחר מזה שבמסך.

**המידע התכנוני מצונזר לפי בעלות ולא לפי ערוץ.** על הנכס של הסוכן/ת חוזר
המידע המלא — גוש, חלקה ושטח החלקה — זה מה שהוא/היא רואה ממילא בפאנל "מידע
תכנוני" ב-CRM. על נכס של עמית/ה במשרד, או כל נכס פעיל אחר, חוזר בדיוק מה
ש-`property_planning_public` מגישה לגולש/ת אנונימי/ת. הגבול נשאר ב-SQL ולא
עבר ל-Edge Function מאותה סיבה שהוא לא בצד הלקוח: רשימת שדות אסורים
שמתוחזקת בשני מקומות מתפצלת בסוף מעצמה. הפרטים: `docs/land-planning.md`.

**התשובה בצ'אט אינה הדוח.** ‏`cma_report` בצ'אט מחזיר תקציר — ממוצע, חציון,
טווח, מחיר למ״ר, הפער מהמחיר המבוקש, וחמש העסקאות הקרובות ביותר. הדוח המלא,
זה שמודפס ונשלח ללקוח/ה, נשאר בדשבורד: רשימה של כל העסקאות ברדיוס בהודעת
וואטסאפ אינה נקראת ורק מסתירה את השורה החשובה.

### מה מכוון ולא באג

- **אין מחיקה אמיתית.** "תמחק נכס" מעביר ל-`archived`, בדיוק כמו בדשבורד.
  ו"תמחק לקוח/ה" מעביר ל-`closed` — הרשומה נשארת בקובץ.
- **הבוט לא יוצר כפילות.** לפני יצירת נכס רצה אותה בדיקה שרצה בטופס בדשבורד
  (‏`findDuplicateProperty` ב-`agent.ts`): אותה עיר, רחוב ומספר בית אחרי נרמול,
  ורק כשמספר החדרים, הקומה וסוג העסקה מתאימים — אחרת זו דירה אחרת באותו בניין.
  נמצאה התאמה (גם נכס שנמכר או בארכיון) — `create_property` **לא** יוצר, אלא
  מחזיר `duplicate` עם מספר המודעה והסטטוס, והבוט שואל: להחזיר ולעדכן את
  הקיימת, או לפרסם מודעה נוספת? החזרה = `update_property` + `set_property_status`
  ל-`active` (בוואטסאפ זה כפתור, לא פרסום מיידי); מודעה נוספת = `create_property`
  שוב עם `force_new: true`, וגם היא נשמרת unpublished עד לאישור. הדגל הזה
  אינו שדה במסד — `pickWritable` מסננת אותו החוצה.

- **נכס חדש לא עולה לבד.** `create_property` כותב `unpublished`. האתר, החיפוש,
  ה-sitemap, נכסים משותפים והתראות ההתאמה מסתכלים על `active` בלבד, ולכן
  הטיוטה לא נראית ולא מצלצלת. בוואטסאפ יוצאת רשימת יעד (`dst:`): אתר,
  רשתות (תור, לא פוסט), שת״פ למשרדים עד תקרה, או רק מאגר. בלי לחיצה הנכס
  נשאר unpublished. `confirm=true` מפרסם לאתר רק כשאין רשימה.
  `gabriela_ask_before_publish=0` מחזיר את הפרסום המיידי.
  שגיאת יצירה או פרסום יוצאת בלי טקסט של המסד (הגולמי נרשם בשרת).
  טיוטה מול מודעה של משרד אחר מקבלת אזהרה בלי שם, והחסימה נשארת בפרסום.
  כפתור שפג אחרי שש שעות משאיר את הנכס `unpublished`, והתזכורת השבועית
  (כשהיא דלוקה) בוחרת אותו לפי `unpublished_at`, לא לפי כפתור פתוח.
  ייבוא מקובץ אינו עובר בשאלה הזו.
  אם `whatsapp_pending_actions` עוד לא עלתה (הפונקציה לפני
  `20271029160000` ו-`20271029180000`), גבריאלה לא מפרסמת ולא נופלת:
  היא אומרת לפרסם מאזור האישי. שגיאת בלעדיות של משרד אחר יוצאת בלי שם.
- **אלבום מקבל תשובה אחת, ואף תמונה אינה הולכת לאיבוד.** וואטסאפ שולחת אלבום
  כהודעות נפרדות שמגיעות לוובהוק **במקביל**. עד מיגרציה `20270115095000` כל בקשה
  קראה את רשימת התמונות הממתינות, הוסיפה את שלה וכתבה הכול בחזרה - והבקשה
  המקבילה דרסה אותה. ב-30 יום נמדדו 24 אלבומים כאלה: 7 תמונות נשלחו ו-1 הגיעה
  לנכס, 10 → 5, 17 → 11; תשע תשובות "התמונה נוספה" תוך ארבע שניות, ש-Meta
  חסמה (‏131056); ו-7 תמונות בלי נכס פעיל שלא קיבלו אף מילה.
  עכשיו: כל שינוי ברשימה ובנכס הוא פקודה אטומית אחת במסד
  (‏`whatsapp_pending_image_add` / `_take`, ‏`property_images_append`), ו-
  `saveConversation` אינה כותבת את הרשימה בכלל. בסימולציה של 200 אלבומים
  מקבילים: לפני - 3.9 מתוך 7 נשמרו בממוצע ו-7 תשובות; אחרי - 7 מתוך 7,
  תשובה אחת.
- **רצף הודעות הוא תור אחד - לא רק אלבום** (מיגרציה `20270115099000`). מודעה
  שמועברת מקבוצה מגיעה כתיאור, תמונות ו"מחיר 4,000,000 תפרסם" בהודעות נפרדות.
  כל טקסט הריץ תור משלו במקביל, וב-22.9 זה נתן שתי תשובות סותרות באותה שנייה:
  "רק חסר מחיר" ו"חסר לי סוג הנכס". עכשיו כל הודעה - טקסט, תמונה, הקלטה
  מתומללת - מוסיפה את עצמה לרצף (‏`whatsapp_burst_add`) ומקבלת מספר רץ,
  ממתינה 4 שניות (‏`BURST_WAIT_MS`), ורק זו שהמספר שלה עדיין האחרון עונה: כל
  הטקסטים מחוברים לתור אחד עם התמונות שנאספו, ורצף של תמונות בלבד מצורף לנכס
  האחרון בשיחה או מקבל שאלה לאיזה נכס.
  **למה 4 שניות:** ב-30 יום 190 הודעות הגיעו 0-4 שניות אחרי הקודמת, **אף
  אחת** בין 4 ל-5, ומשם רק הקלדה ידנית. החלון נמדד מההודעה האחרונה, ולכן גם
  אלבום של 17 תמונות שנפרש על 6 שניות נאסף שלם.
  **וטקסט מוקלד - 1.5 שניות** (‏`QUICK_BURST_WAIT_MS`, 14.10.2026): ההמתנה
  הייתה רבע מזמן התגובה, וב-98% מהטקסטים לא הגיע אחריהם דבר. מתוך 50 שכן,
  29 הגיעו תוך 1.5 שניות. תמונה, מסמך, הודעה מועברת, ורצף שכבר יש בו תמונות
  ממתינות - ממשיכים לחכות 4 שניות.
  **ותמונה - 3 שניות** (‏`IMAGE_BURST_WAIT_MS`, 17.10.2026): 661 מתוך 662 פערים
  בין תמונות באותו אלבום (30 יום) היו עד 2.5 שניות, והארוך מתחת ל-3. המחיר:
  טקסט שמגיע 3-4 שניות אחרי התמונה האחרונה (3 בחודש) נענה בנפרד. מועבר ומסמך - 4.
- **הודעת `unsupported` לא מקבלת תשובה.** ‏Meta שולחת אחת כזו לפני כל אלבום
  (24 מתוך 24, כולן תוך 10 שניות מתמונה). עד עכשיו הבוט ענה עליה "אני יודע
  לקבל טקסט, תמונות והקלטות" - בדיוק כשהסוכן/ת שלח/ה תמונות, וזה נשמע כמו
  סירוב. היא נרשמת ב-`whatsapp_messages` ולא יותר.
- **גיאוקוד רק בעפולה.** מבוסס על שכבת הכתובות של העירייה. נכס בעיר אחרת נוצר בלי
  פין על המפה, וזה לא חוסם את הפרסום.
- **הסוכן/ת רואה רק את הנכסים שלו/ה.** כל כלי מקבע `agent_id` בעצמו — ה-LLM לא יכול
  לגעת בנכס של סוכן/ת אחר/ת גם אם ינסה.
- **ליד שטרם נפתח נשאר מוסתר גם כאן.** ‏`list_leads` קורא מ-`leads_masked`,
  ה-view שמחליף שם, טלפון והודעה בגרסה מוסתרת (‏`א***`, ‏`05-****1`) כל עוד
  ‏`status='masked'`. ‏`service_role` עוקף RLS אבל **לא** את ה-view, וזה
  בדיוק מה שמונע מהצ'אט להיות הדלת האחורית למאגר הלידים.
- **ספירה היא שאילתה ולא קריאה של רשימה.** זה נלמד מכשל: לשאלה "כמה נכסים
  מסחריים יש לי" הבוט קרא ל-`list_properties`, קיבל את מלוא החלון, וענה
  "מתוך 50 האחרונים, כ-42 מסחריים". התשובה נשמעה מוסמכת והייתה שגויה
  בשורש. לכן יש `property_stats` (שאילתת ספירה אחת במסד), לכן שני כלי
  הרשימה מחזירים ספירה אמיתית לצד החלון, וההוראה בפרומפט מפורשת: לשאלת
  "כמה" — כלי ספירה, לא ספירה של רשימה.

### הרשימה היא חלון — ולמה החיפוש חשוב יותר מהתקרה

לסוכן/ת אחד/ת בפרודקשן יש **57 נכסים**, והתקרה של `list_properties` הייתה
‏50. התוצאה לא הייתה רק "חסרות שבע שורות": הכלי נועד למצוא מזהה נכס מתוך
תיאור במילים — *"הדירה באבן גבירול"* — ו**לא היה לו שדה חיפוש כלל**. הוא
החזיר את ה-N החדשים, והמודל היה אמור לסרוק אותם. נכס שלא נכנס לחלון פשוט
לא היה קיים מבחינת הבוט, והבוט היה מודיע לסוכן/ת שהוא רואה עד 50 — כלומר
מדווח על מגבלה טכנית פנימית כאילו היא עובדה על העסק.

**התיקון העיקרי הוא `query`, לא המספר.** החיפוש רץ במסד על **כל** הנכסים של
הסוכן/ת ולא על החלון, ולכן עשרים שורות מספיקות כדי למצוא נכס יחיד בקובץ של
חמש מאות. הוא מכסה כותרת, רחוב, כתובת ועיר — ומספר מודעה כשהחיפוש מספר שלם
(`listing_number` הוא `bigint`, ולכן `ilike` עליו הוא שגיאת טיפוס ולא "אפס
תוצאות").

**התקרה עלתה ל-200** עבור המקרה השני, "תראה לי את כל הנכסים שלי", ולא עבור
החיפוש.

#### ולמה לא להסיר אותה לגמרי

לא בגלל המסד — שם `agent_id` מאונדקס והשאילתה זולה. הסיבה היא **שתוצאת הכלי
נכנסת ל-`messages` ונשלחת מחדש בכל סבב של לולאת הכלים** (עד 8), ואין כאן
prompt caching:

| שורות | גודל התוצאה | בערך, בטוקנים | ובתור עם 4 סבבים |
|---|---|---|---|
| 20 | ~5KB | ~2.6K | ~10K |
| 50 | ~13KB | ~6.5K | ~26K |
| 200 | ~53KB | ~26K | ~105K |

(שורה שוקלת ~260 תווים בפועל, נמדד על הטבלה.)

והשיקול השני אינו עלות: **רשימה ארוכה של שורות כמעט זהות מורידה את הדיוק של
בחירת הנכס הנכון, לא מעלה אותו.** 200 דירות באותה עיר, שחלקן באותו רחוב, הן
בדיוק המצב שבו "הדירה באבן גבירול" נפתר בניחוש. חיפוש שמחזיר שלוש שורות
עדיף על רשימה שמחזירה מאתיים.

#### `total` הוא מה שמונע את הניחוש

עד עכשיו חזר `count: data.length` בלבד — כלומר **גודל החלון**, בלי שום דרך
לדעת שזה חלון. עכשיו חוזרים `returned`, ‏`total` (ספירה אמיתית ב-`head: true`,
בלי להעביר שורות) ו-`truncated`, וההוראות אוסרות לדווח על גודל הרשימה כאילו
הוא מספר הנכסים.

#### `list_clients` — אותה תקרה, ושני הבדלים

גם קובץ הלקוחות עלה מ-50 ל-200. שם `query` (שם או טלפון) כבר היה, וגם
‏`total_active`/`total_all` — אבל שני דברים היו חסרים, ואחד מהם משנה מספרים:

**‏`total_matching`.** ‏`total_active` ו-`total_all` עונים על *"כמה לקוחות יש
לי"* ואינם מושפעים מהסינון, ולכן אי אפשר להסיק מהם אם הרשימה חתוכה: חיפוש
שמצא שלושה מתוך מאה אינו רשימה חתוכה. ‏`total_matching` נספר על **אותם
תנאים** שהוחזרו, והוא זה שקובע את `truncated`.

**‏`notes` נגזם בחלון גדול.** שורת לקוח/ה שוקלת ~460 תווים מול ~260 של נכס
(נמדד): ‏`needs` מורכב משמונה־עשר שדות, ו-`notes` הוא טקסט חופשי בלי גבול
עליון. ‏200 לקוחות הם ~92KB — כמעט פי שניים מ-200 נכסים, באותה לולאה
שנשלחת מחדש בכל סבב.

הגיזום מבחין בין שני מצבי השימוש: מעל 20 שורות זהו **עיון ברשימה**, ואיש
אינו קורא שישים הערות מלאות בוואטסאפ, ולכן ההערה נחתכת ב-240 תווים ומסומנת
ב-`notes_truncated`. חיפוש לפי שם מחזיר שורות בודדות — ושם ההערה חוזרת
שלמה, כי זו בדיוק השאלה שנשאלה. ההוראות אוסרות לצטט הערה חתוכה כאילו היא
מלאה; הדרך לקבל אותה שלמה היא `query` על השם.

## המודל והעלות

### מה נשלח בכל קריאה — והחלק שחוזר על עצמו

לכל הודעת וואטסאפ יש **תוכן סטטי של ~29,000 תווים**: 29 הגדרות הכלים
(~19.6K) והוראות המערכת (~9.4K). הוא נשלח מחדש **בכל סבב של לולאת הכלים**,
עד שמונה סבבים להודעה. בתור עם שלושה סבבים אותם בתים בדיוק נשלחים — ומשולמים
— שלוש פעמים.

זה גם הרוב המוחלט של הקלט: התשובות בוואטסאפ קצרות, והפלט זניח לעומת הקלט.

### ‏Prompt caching — הידית הראשונה, ובלי מחיר באיכות

‏`cache_control` על סוף ההוראות הופך את כל התחילית הזו לקריאה מהמטמון
(~0.1 מהמחיר; כתיבה עולה ~1.25). סדר הרינדור של ה-API הוא
**`tools` → `system` → `messages`**, ולכן נקודת שבירה אחת בסוף ה-system
תופסת **גם את הגדרות הכלים** שלפניה.

| | מחיר ל-1M על התחילית הסטטית |
|---|---|
| ‏Opus 5 בלי מטמון | $5.00 |
| ‏Sonnet 5 בלי מטמון | $2.00 |
| **‏Opus 5 עם מטמון** | **~$0.50** |

כלומר המטמון שווה כאן יותר מהחלפת המודל, והשניים מצטרפים.

#### מה חסם את זה — והתיקון

‏Caching הוא **התאמת תחילית**: כל בית שמשתנה מבטל את כל מה שאחריו. הפרומפט
נבנה כמחרוזת אחת שכללה את **שם הסוכן/ת, שם המשרד, תאריך היום ומצב השיחה** —
כלומר הוא היה שונה אצל כל אחד/ת ובכל שיחה, ולכן לא היה ניתן למטמון כלל.

עכשיו הוא מפוצל לשניים לפי מה שהתוכן משתנה איתו:

- **‏`SYSTEM_STATIC`** — ההוראות. זהות לכולם, ולכן **המטמון משותף בין כל
  הסוכנים** ולא רק בין ההודעות של אותו אדם.
- **‏`sessionContext()`** — השם, המשרד, התאריך ומצב השיחה. מאות תווים, יושב
  אחרי נקודת השבירה ולכן אינו מבטל את מה שלפניו.

⚠️ **אסור להכניס ל-`SYSTEM_STATIC` דבר שמשתנה בין קריאות** — לא תאריך, לא
שם, לא מזהה ולא ספירה. שורה כזו לא תישבר ולא תיראה שבורה; היא פשוט תאפס את
המטמון בשקט.

#### נקודת שבירה שנייה, מתגלגלת

תוצאות הכלים מקבלות נקודת שבירה משלהן בכל סבב, כי גם הן נשלחות שוב בכל סבב
שאחריהן — ו-`list_properties` יכול להחזיר מאתיים שורות.

**הסימון הקודם נמחק לפני שמסומן החדש**, וזה לא ניקיון: ל-API יש תקרה של
**ארבע נקודות שבירה לבקשה**, וסימון מצטבר היה עובר אותה בסבב הרביעי ומפיל
את הבקשה — כלומר תור ארוך היה נשבר דווקא אחרי שכבר נעשתה עבודה. הסרת הסימון
הקודם אינה מאבדת את המטמון: התחילית הקצרה יותר עדיין תקפה, והחדשה מרחיבה
אותה. הסימון נעשה רק כשעומדים לקרוא שוב, כדי שתור חד-סבבי לא ישלם על כתיבה
שאיש לא יקרא.

#### איך יודעים שזה עובד

כל קריאה מדפיסה שורה ל-`function_logs`:

```
llm claude-opus-5 iter=0 in=412 cache_read=11840 cache_write=0 out=96
```

**‏`cache_read` אפס לאורך זמן הוא התקלה** — משהו משתנה נכנס ל-`SYSTEM_STATIC`
או להגדרות הכלים. הכול ימשיך לעבוד; רק החשבון יגדל.

### החלפת המודל

```
Supabase → Edge Functions → Secrets
WHATSAPP_BOT_MODEL = claude-sonnet-5
```

ברירת המחדל של עוזר הסוכנים נשארת `claude-opus-5` בקוד בכוונה: **החלפת מודל
היא החלטת איכות**, והיא לא אמורה לקרות בשקט בפריסה. בפרודקשן הסוד
`WHATSAPP_BOT_MODEL` כבר `claude-opus-5-5` והוא גובר על ברירת המחדל. המתג
קיים כדי שאפשר יהיה למדוד ולחזור אחורה בלי לגעת בקוד — אותה תבנית שכבר
קיימת ב-`property-description` וב-`property-marketing-publish` (שתיהן על Sonnet).

הבוט הציבורי נפרד: ברירת המחדל בקוד שלו היא `claude-opus-5-5`. סוד
`WHATSAPP_PUBLIC_BOT_MODEL` גובר עליה. ראו `whatsapp-public-bot.md`.

מרווח בין הודעות לאותו נמען (Meta 131056): `WHATSAPP_PAIR_GAP_MS`, ברירת
מחדל 1500. בין הבוט לבין `notification-push` המרווח נשמר ב-`whatsapp_pair_reserve`.

**‏שני דברים לדעת לפני שמחליפים:**

1. **מטמון הוא לפי מודל.** החלפה מאפסת אותו, והקריאות הראשונות אחריה ישלמו
   מחיר מלא עד שיתחמם מחדש. זה נראה כמו רגרסיה בעלות ואינו כזה — למדוד אחרי
   שהתייצב.
2. **‏מספר הטוקנים עשוי להשתנות, לא רק המחיר.** לדורות שונים של מודלים
   טוקנייזרים שונים, וההפרש יכול להגיע ל-1.35× — בעברית זה יכול לנוע לכל
   כיוון. הדרך לדעת היא `count_tokens` על פרומפט אמיתי מול שני המודלים.

**ומה שכדאי למדוד באיכות:** עם 29 כלים, ההחלטות שנוטות להישבר ראשונות הן
הבחירה בין `client_matches` ל-`property_matches`, "קודם למצוא את המזהה", והסדר
`property_video_info` → אישור → הפקה. השלישי מוגן ממילא — ‏`confirm` נבדק
**בשרת** ולא רק בהוראות — ולכן מודל שידלג עליו ייעצר ולא יחייב ארנק.

### הכנת הסכם מהצ'אט

"תכין הזמנת תיווך לרונית על הדירה בעלייה 20, 2% עמלה" מייצר הסכם אמיתי:
הלקוח/ה נלקח/ת מקובץ הלקוחות, הנכסים מצורפים לפי מה שהסוכן/ת ביקש/ה,
והמסמך נבנה ונשמר. מה שחוזר לצ'אט הוא **קישור החתימה האישי של כל חותם/ת**.

**אותו קישור משמש לשתי הדרכים**, ולכן אין מה לבחור מראש: לחתימה מרחוק
מעבירים אותו לחותם/ת, ולחתימה פנים מול פנים פותחים אותו על המכשיר של
הסוכן/ת ומושיטים. לכל חותם/ת אסימון משלו/ה — בני זוג מקבלים שני קישורים
נפרדים, כמו בדשבורד.

#### ארבע החלטות ביכולת הזו

**1. אותו נוסח ואותו קוד, ולא עותק שני.** הטקסט המשפטי יושב ב-
`assets/agreement-templates.js` וה-HTML נבנה ב-`assets/agreement-doc.js`,
ושלושת הדפים באתר טוענים את שניהם. ‏Edge Function אינה יכולה לייבא מחוץ
ל-`supabase/functions` — ה-CLI בונה את הבאנדל מהתיקייה הזו בלבד — ולכן יש
עותק **זהה בייט-בייט** ב-`supabase/functions/_shared/`,
ו-`scripts/check_agreement_assets.py` חוסם ב-CI כל PR שמשאיר פער.

הבדיקה הזו אינה זהירות יתר. פער בין שני עותקים של נוסח משפטי אינו נראה
בשום מקום: הדף ייראה תקין, המסמך ייבנה, הלקוח/ה יחתום/תחתום — ורק כשתוגש
תביעת דמי תיווך יתגלה שהסעיף שנחתם אינו הסעיף שבתיק. זו טעות שאי אפשר
לתקן למפרע.

**2. חסר נתון — ההסכם לא נוצר.** ‏`prepare_agreement` מריץ את אותה בדיקה
שהאשף מריץ (`agrValidate` ↔ `missingForAgreement`): ת.ז. לכל חותם/ת, עמלה,
ותקופת בלעדיות בטופסי בלעדיות. חסר משהו — חוזר `missing` ולא נוצרת שורה,
והבוט מבקש את מה שחסר. הזמנה בלי אלה אינה הזמנה בכתב כדין, וטופס חסר
שנחתם גרוע מטופס שלא נוצר: הוא נראה תקין עד הרגע שבו צריך אותו.

> ת.ז. שהסוכן/ת מוסר/ת בצ'אט נשמרת גם בכרטיס הלקוח/ה, כדי שההסכם הבא לא
> ייעצר באותו מקום. אותה התנהגות כמו ההשלמה המהירה באשף.

**3. יצירה — כן. תיקון וביטול — לא.** גוף המסמך ננעל בטריגר
(`agreements_freeze_body`) ברגע שההסכם יוצא מ-`draft`, וכל ערכה הראייתי של
החתימה האלקטרונית תלוי בזה. הדרך לתקן הסכם היא הדרך שהנייר מכיר: לבטל
ולהוציא חדש — באשף שבדשבורד, שבו יש תצוגה מקדימה מלאה של מה שהלקוח/ה
יראה/תראה. זה בדיוק מה שאי אפשר להראות בהודעת וואטסאפ, ולכן זה נשאר שם.

**4. הסטטוס נשאר `draft`.** מה שמסמן `sent` הוא השליחה דרך `agreement-sign`
בדשבורד, שגם שולחת את המייל — לא העתקת קישור. אותו כלל שכבר חל על
‏`agreement_sign_links`, ומאותה סיבה: העברת קישור אינה אירוע שהמערכת ראתה.

### שני גבולות שנשמרים בכוונה

**הבוט אינו שולח ללקוח/ה.** לא את קישור החתימה, לא את קישור הנכס ולא את
העותק החתום. הכול חוזר לצ'אט של הסוכן/ת, ומשם יוצא **מהמספר שלו/ה** בלחיצה
שלו/ה — בדיוק כמו כפתור "💬 וואטסאפ" בדשבורד. שתי סיבות: ההודעה נקראת
אישית ולא כהודעת מערכת, ומי שמחליט/ה למי היא נשלחת הוא/היא מי שמכיר/ה את
הצדדים.

**אין פתיחת ליד.** ‏`claim_lead` מעבירה כסף או צורכת מכסה, והיא נעולה מאחורי
`lead-claim` שגוזרת את הזהות מ-JWT מאומת. זיהוי לפי מספר טלפון הוא ראיה
חלשה יותר, ופעולה שמוציאה כסף לא נשענת עליה. ‏`list_leads` מחזיר את
`unlock_where` — קישור ישר לקטגוריית הלידים בדשבורד.

### הפקת הסרטון — הפעולה היחידה כאן שמוציאה כסף

היא **כן** נמצאת בבוט, למרות הגבול שמעליה, ולא בסתירה אליו: ליד הוא רכישת
פרטים של אדם שלישי, והסרטון הוא שירות שהסוכן/ת מזמין/ה לעצמו/ה על נכס
שהוא/היא הבעלים שלו. מה שנשמר הוא לא האיסור אלא מה שעומד מאחוריו — שלא
ירד כסף ממי שלא אמר/ה "כן".

בדשבורד זה מסודר מאליו: הכפתור אינו מוצג למי שאינו זכאי/ת, המחיר כתוב בעמוד
המחירים, ולחיצה היא פעולה מכוונת. **בצ'אט אין כפתור שאפשר להסתיר**, ו-₪25
יורדים מהארנק ברגע שהבקשה נפתחת. לכן:

1. **‏`property_video_info` קודם, תמיד.** הוא אינו כותב שורה ואינו מחייב,
   והוא היחיד שיודע את המחיר, את המכסה החודשית שנותרה ואת יתרת הארנק. הוא
   מחזיר גם `price_text` מנוסח — *"כלול במסלול Elite (נשארו 6 הפקות החודש)"*
   או *"₪25 מיתרת הארנק (יתרה: ₪140)"* — כדי שהמשפט שנאמר לפני החיוב לא
   יהיה ניסוח חופשי של המודל.
2. **‏`confirm: true` הוא פרמטר חובה**, ו**הכלי דוחה בלעדיו בשרת** ולא רק
   בהוראות. הוראה היא בקשה מהמודל; זו פעולה שמורידה כסף.
   ‏*"תעשה לי סרטון"* היא הבקשה, לא האישור.
3. **‏`replace_existing` הוא אישור שני ונפרד.** הסרטון שכבר על הנכס עשוי
   להיות סיור שהסוכן/ת צילם/ה בעצמו/ה, והוא אינו נדרס בלי שנשאל/ה.

אותו כלל בדיוק שנשמר ב-`consent_agent_contact` של הבוט הציבורי
(‏[`whatsapp-public-bot.md`](whatsapp-public-bot.md)): הסכמה היא פרמטר
מפורש, לא ברירת מחדל ולא מסקנה מכך שמישהו טרח לכתוב.

**והבוט אינו מודיע בעצמו שהסרטון מוכן** — הוא לעולם אינו יוזם הודעה. הסיום
מגיע כהתראה רגילה (`marketing_copy`), ומשם לוואטסאפ דרך `notification-push`
כמו כל התראה אחרת. ההוראות אוסרות על הבוט להבטיח שיכתוב בעצמו.

## ההתראות שיוצאות בוואטסאפ

הפעמון ב-CRM מדווח על אירועים בזמן אמת — אבל רק למי שהדשבורד פתוח מולו/ה.
מכאן כל סוג התראה יכול לצאת **גם** כהודעה מהעוזר.

**ההדלקה היא פר סוג, ולא מתג אחד:** בדשבורד → "התראות והודעות", המתג
"💬 גם בוואטסאפ" בכל שורה. אפשר גם מתוך הצ'אט ("תעדכן אותי כאן על לידים
חדשים" → `whatsapp_alerts`).

**הערוץ מגודר לאותם מסלולים כמו השיחה — PROFESSIONAL ו-Elite.** זה אותו
עוזר בכיוון ההפוך: אותו מספר, אותה זהות, ואין הגיון שהודעה **ממנו** תצא
למי שאינו יכול לכתוב **אליו**. האכיפה במסד, ב-
`notification_push_due_agents`, ועם אותם שלושה תנאים שכל יכולת בתשלום
בפרויקט נשענת עליהם (כמו `property_description_tier_ok`): מסלול, פעילות
ו-`billing_status`.

הדשבורד מכבה את התיבות ואומר את הסיבה עם קישור לדף המסלולים; הבדיקה שם היא
על `tier` בלבד, כי `billing_status` אינו נטען לדפדפן — אותה תבנית כמו כפתור
דוח ה-CMA, שבה התצוגה מרמזת וה-DB אוכף.

**סימון שנשמר לא נמחק בירידת מסלול.** ההודעות פשוט מפסיקות לצאת, ושדרוג
מחזיר אותן בלי לסמן מחדש. מחיקת בחירה בגלל שינוי מסלול היא איבוד מידע שאיש
לא ביקש.

> ערוץ הוואטסאפ של **התזכורות** (`docs/agent-reminders.md`) הוא מנגנון אחר
> ואינו מגודר — הוא אינו העוזר, אינו מריץ LLM, ושולח דייג'סט שבועי של מצב
> המודעות. הגידור כאן הוא על העוזר ועל מה שיוצא בשמו.

### דלוק כברירת מחדל (מאז 20270303090000)

עד 3.2027 ‏`whatsapp_types` הייתה רשימת **מאושרים**: שום סוג לא יצא
בוואטסאפ עד שסומן, מחשש לדירוג האיכות של המספר מול Meta. ההחלטה העסקית
התהפכה - **וואטסאפ הוא ערוץ ברירת המחדל של הסוכנים**, ומייל (בתזכורות)
הוא ערוץ שמוסיפים.

מה שקובע עכשיו הוא `whatsapp_off_types`, רשימת **כבויים** - אותה תבנית של
`muted_types` שבכל שאר הפרויקט: היעדר שורה = הכול דלוק. "הכול" נגזר מ-
‏`notifications_type_check` עצמו (‏`notification_known_types()`), ולכן סוג
התראה שייכנס בעתיד דלוק בוואטסאפ אוטומטית, בלי רשימה שנייה שתתפצל.
‏`whatsapp_types` נשארה בטבלה בלי קורא.

מה ששומר על דירוג האיכות לא השתנה: שער המסלול, הקיבוץ להודעה אחת, שעות
השקט, התקרה היומית (12), גג הכשלים, וכיבוי מיידי אחרי 131050.

### שבע החלטות במנגנון

1. **הודעה אחת מקבצת את כל ההתראות הפתוחות.** שלוש הודעות ברצף הן הדרך
   המהירה ביותר לחסימה של המספר. מרווח הקיבוץ הוא
   ‏`notif_push_gap_minutes` (ברירת מחדל 10 דקות), וה-cron רץ כל חמש.
2. **התראה שנקראה בדשבורד אינה נשלחת.** ‏`notifications.read` הוא התנאי,
   ולכן מי שעבד/ה בדשבורד עכשיו לא מקבל/ת תקציר של מה שהרגע ראה/תה. זה מה
   שהופך את הערוץ מ"עוד עותק" ל"מה שפספסת".
3. **חלון מבט לאחור של 12 שעות** (`notif_push_lookback_hours`). התראה שלא
   נקראה שלושה ימים אינה "מה שפספסת" אלא הצטברות, ושם התזכורות
   (`docs/agent-reminders.md`) עושות עבודה טובה יותר.
   החריג: הסוגים שבעדיפות (סעיף 5) נשמרים 72 שעות
   (`notif_push_priority_lookback_hours`) - שקט משישי בערב עד ראשון בבוקר
   הוא 60 שעות.
   ‏וחריג שני: לסוגים שב-`notification_push_quiet_wait_types()` (היום
   ‏`marketing_copy` - הרילס היומי, הסרטון והתיאור השיווקי) **זמן השקט אינו
   נספר בחלון** (`notification_push_quiet_hold`, ‏`20270902090000`). בלי זה
   רילס שנשמר בשישי, בשבת או בחמישי אחרי 21:00 לא הגיע לוואטסאפ בכלל, כי
   יום שקט מלא ארוך מ-12 שעות; עכשיו הוא יוצא כשהשקט נגמר, ו-12 השעות
   מתחילות משם. תקרה של 7 ימים.
4. **שעות השקט הן של האדם ולא של סוג ההודעה.** נלקחות מאותה שורה
   ב-`agent_reminder_preferences` שמשרתת את התזכורות (ברירת מחדל 21→8), כי
   מי שקבע/ה שקט עד 8:00 לא התכוון/ה שזה חל על התזכורות בלבד.
5. **תקרה ומרווח אינם חוסמים מה שאדם מחכה לו בצד השני.**
   ‏`notification_push_priority_types()` - ‏`agenda_reminder`, ‏`showcase_meeting`
   (בקשת סיור מהמיניסייט) ו-`new_lead` - יוצאים גם כשהמרווח לא עבר וגם אחרי
   12 ההודעות של היממה, ונספרים בתקרה כרגיל. שעות השקט חלות עליהם, חוץ מ-
   ‏`agenda_reminder` בחצי השעה הראשונה שלה (`notif_push_urgent_fresh_minutes`,
   ‏`20270422090000`) - תזכורת ישנה יותר מחכה לבוקר. בלי הסייג הזה, שתי
   תזכורות מאחר הצהריים שהתקרה חסמה יצאו ב-02:05 בלילה של 12.10.2026. עד `20270420090000` תקרה מלאה הוציאה את הסוכן/ת מהרשימה
   לכל שאר היממה: ב-11.10.2026 בקשת סיור מ-13:10 ושתי תזכורות "לחזור לליד"
   לא יצאו לעולם, אחרי 12 הודעות עד 12:10 - חמש מהן "מתווך/ת חדש/ה".
6. **רקע אינו מעיר שליחה.** "נכס חדש שותף איתך" (‏`system` על נכס של משרד
   אחר) ו-`platform_signup` הם רקע (`notification_push_is_ambient`). הם
   מצטרפים להודעה הבאה שיש בה משהו אחר, ואם אין כזו - יוצאים כתקציר כשהוותיק
   מביניהם מחכה `notif_push_ambient_digest_minutes` (‏180). בהודעה עצמה כל
   סוג רקע מתקפל לשורה אחת ("12 נכסים חדשים שותפו איתך"), והסוגים שבעדיפות
   עולים לראש - כדי שחיתוך האורך (‏4000 בטקסט, 900 בתבנית) לא יפגע בהם
   (‏`arrange` ב-notification-push). הסיבה: ב-11.10.2026 נכתבו 678 התראות
   שיתוף ביום אחד, ו-15 סוכנים הגיעו לתקרה.
7. **בין שתי תבניות לאותו/ה סוכן/ת - ארבע שעות.** מחוץ לחלון 24 השעות
   ההודעה יוצאת כתבנית, והתבנית מסווגת שיווק. ‏Meta מגבילה כמה הודעות
   שיווק אדם אחד מקבל, ומה שמעבר נדחה ב-131049 ("healthy ecosystem
   engagement") - אחרי ש-"sent" כבר נרשם, כך שההתראות שבתוכה אובדות.
   ב-25.10.2026: תקציר שיתופים ב-13:40, ‏match_digest ב-14:10, ו-10 מ-18
   הודעות ה-14:10 נדחו (27 מ-29 הכשלים של השבוע היו 131049).
   ‏`notif_push_template_gap_minutes` (‏240) מאז התבנית הקודמת, ובתוכו - רק
   הסוגים שבעדיפות (סעיף 5). השאר מחכה ומצטרף לתבנית הבאה. בתוך החלון
   (טקסט חופשי) אין שינוי. ‏`20270825090000_notification_push_template_gap.sql`.

וסוג שכובה בפעמון לא ייווצר במסד מלכתחילה (הטריגר
`notifications_apply_preferences` מחזיר `null`), ולכן גם לא יישלח. הדשבורד
מכבה ומנקה את תיבת הוואטסאפ יחד עם הפעמון, והכלי בצ'אט מחזיר
`muted_conflict` ואומר את זה במשפט.

### שורת יומן שלא יצאה אינה מבליעה את ההתראות שבתוכה

‏`notification_push_claim` רושמת את שורת היומן **לפני** השליחה, וזה נכון —
זה מה שמונע הודעה כפולה. אבל הקריאה אליה נכשלת מדי פעם ב-504 מה-gateway,
ו-504 אומר שה-gateway ויתר, לא שה-`INSERT` לא נסגר. השורה שנשארת מכילה
`notification_ids`, וה-`not exists` שמונע כפילות היה מסתכל על *קיום* השורה
בלבד — כלומר ההתראות שבתוכה לא היו נכללות בשום הודעה עתידית. **לנצח.**

מאז `20261101090000` הפרדיקט הוא `notification_push_log_holds`: שורה חוסמת
רק אם היא `sent`, או `pending` בתוך חסד של 30 דקות
(`notif_push_pending_grace_minutes`). שורה שנכשלה, או שנתקעה מעבר לחסד,
משחררת את ההתראות שבתוכה לסבב הבא.

שלוש נקודות שקל לפספס:

- **אותו פרדיקט בדיוק ב-`notification_push_ready`.** אילו התנאי של ה-cron
  היה רחב מזה של ה-claim היינו מעירים Edge Function לשווא; אילו היה צר
  ממנו, ה-cron היה שותק כשיש עבודה.
- **החסד הוא זמן ולא סטטוס.** אחרת: שורה תקועה חוסמת → `ready()` מחזירה
  false → ה-cron לא מעיר → ה-`reconcile` שאמור לשחרר לא רץ לעולם.
  ‏`notification_push_reconcile()` רצה בפתיחת כל claim, אבל לרישום בלבד.
- **‏`max(created_at)` ב-`notification_push_due_agents` נשאר על כל השורות**,
  בשונה מהתזכורות. המרווח כאן הוא עשר דקות, ושורה תקועה שמעכבת עשר דקות
  היא בדיוק ההפוגה שרצינו בין שני ניסיונות. רק התקרה היומית מסוננת, כדי
  שכשלים לא יאכלו את שתים-עשרה ההודעות המותרות — ו-`notif_push_max_failures_24h`
  (3) עוצר ערוץ ששבור באמת.

זולה יותר ואינה כפופה להסכמה שיווקית.

**המסווג האוטומטי של Meta סירב, שלוש פעמים.** הדיאלוג "הקטגוריה לא
תואמת" הופיע עם `Recommended: שיווק` ועם האזהרה "תבנית הודעה זו תידחה",

2. ‏`🔔 {{1}}, יש עדכונים חדשים בחשבון שלך…` — עדיין אימוג'י ושם מותג בפתיח
3. ‏`שלום {{1}}, עדכון על הפעילות בחשבון הסוכן/ת שלך:` — בלי אימוג'י ובלי
   שם מותג, וגם זה לא עבר

מי שמגיע לכאן ומתפתה לנסות ניסוח רביעי: **נוסו כבר שלושה, כולל אחד נקי
לגמרי.** דייג'סט מקובץ נקרא למסווג כעדכון תקופתי ולא כאירוע עסקה יחיד,
וזה כנראה הגבול האמיתי.

**מה שנשאר לשים לב אליו ב-Marketing:** בוואטסאפ אפשר לבחור "הפסק לקבל
הודעות קידום מכירות", וזה חוסם תבניות שיווק ומשאיר Utility. סוכן/ת שיעשה
זאת יפסיק/תפסיק לקבל את ההתראות. זה **אינו כשל שקט**: ‏Meta מחזירה 131050,
‏`notification-push` מכבה את הערוץ באותו רגע ורושמת את הסיבה ב-
`notification_push_log.last_error` (ראו "ביטול מול Meta הוא ביטול" למטה).
מי שיראה ערוץ שכבה לבדו — שם התשובה.

### ביטול מול Meta הוא ביטול

| `{{2}}` | `מתווך/ת` |

## בדיקה בלי Meta

`scripts/whatsapp_webhook_test.py` בונה payload בפורמט של Cloud API, חותם אותו
ב-HMAC-SHA256 בדיוק כמו Meta, ושולח אותו לפונקציה. זה מאפשר לבדוק את כל הזרימה
עוד לפני שהוובהוק מחובר. ספריית התקן של פייתון בלבד — אין מה להתקין.

מגדירים ב-`.env` את `SUPABASE_URL`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`
ו-`WA_TEST_FROM` (ראו `.env.example`), ואז:

```bash
# רצף בדיקות בטוח: לחיצת יד, דחיית חתימה שגויה, מספר לא מוכר, "שלום"
python scripts/whatsapp_webhook_test.py all --check

# בדיקה אמיתית של יצירת נכס
python scripts/whatsapp_webhook_test.py text "תעלה נכס באבן גבירול 10, 3 חדרים, 1.8 מליון" --check
```

**דגל `--check` הוא העיקר.** הפונקציה מחזירה 200 מיד וממשיכה לעבד ברקע, אז קוד
200 לבדו לא מוכיח כלום. עם `--check` הסקריפט קורא את `whatsapp_messages` ומראה
מי זוהה, מה הבוט ענה ואיפה זה נפל. הוא דורש `SUPABASE_SERVICE_ROLE_KEY` ב-`.env`.

| פקודה | מה נבדק |
|---|---|
| `verify` | לחיצת היד (GET) שמבצעת Meta בהגדרת הוובהוק |
| `badsig` | חתימה שגויה חייבת לחזור 401 — שכבת האבטחה היחידה של הפונקציה |
| `unknown` | מספר שאינו רשום → "איני מזהה את מספר הטלפון שלך" (או הבוט הציבורי, אם המתג דלוק) |
| `text "…"` | זרימה מלאה: זיהוי → LLM → כלים → תשובה |
| `image --media-id X` | דורש media id **אמיתי** — הפונקציה מורידה את הקובץ מ-Graph API |
| `all` | הרצף הבטוח, בלי יצירת נכסים |

שימו לב: `text` פועל מול הפרויקט החי. בקשה ליצירת נכס באמת תיצור נכס.

### "נשלח" אינו "הגיע" — עמודת `status`

‏`error` ריק פירושו ש-Meta קיבלה את ההודעה, **לא** שהיא נמסרה. ההבחנה הזו
עלתה ב-16.9.2026 בבדיקת העוזר הציבורי: הבוט ענה נכון, היומן הראה שש שורות
יוצאות נקיות, והמכשיר שבדק לא קיבל דבר. לא הייתה שום דרך להבדיל בין "נשלח
ולא נמסר" לבין "נמסר והמשתמש פספס".

לכן הודעה יוצאת שומרת עכשיו את `wa_message_id` שמטא מחזירה, ואירועי
ה-`statuses` שהוובהוק כבר קיבל — ועד אז זרק — נרשמים עליה:

| `status` | מה זה אומר |
|---|---|
| `sent` | מטא קיבלה. זה כל מה שהיה לנו קודם |
| `delivered` | הגיעה למכשיר |
| `read` | נפתחה |
| `failed` | **לא הגיעה.** ‏`status_detail` נושא את הקוד והכותרת מ-Meta |

השאילתה שעונה על "למה הוא לא קיבל":

```sql
select created_at, wa_phone, status, status_detail, left(body, 60)
  from public.whatsapp_messages
 where direction = 'out'
   and created_at > now() - interval '1 hour'
 order by created_at desc;
```

‏`status` ריק בהודעה יוצאת = נשלחה לפני שהמעקב נוסף, או שמטא לא החזירה
מזהה. הדירוג מתקדם רק קדימה (`sent < delivered < read < failed`), כי
האירועים מגיעים בסדר לא מובטח — הפרטים במיגרציה
`20261117090000_whatsapp_delivery_status.sql`.

  ל-`low` ולהצר את רשימת הכלים, לא לוותר על הדיוק.

  (אחרי שהכלי רץ, בעיקר ניסוח) `low`, דרך הודעת מאמץ ב-`messages` (בטא
  `mid-conversation-output-config-2026-07-01`) ולא דרך `output_config`
  בבקשה - שינוי שם מבטל את המטמון של ההודעות. חזרה: `WHATSAPP_AGENT_LOOP_EFFORT=medium`.

  ולכן חינמית**. מחוץ לחלון זו הודעת תבנית, חסומה מלמעלה ב-
  `notif_push_max_per_day` (ברירת מחדל 12 ליום, וזה תקרה ולא צפי).
- **OpenAI Whisper:** רק על הקלטות קוליות.
