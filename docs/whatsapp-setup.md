# העוזר האישי בוואטסאפ (Meta WhatsApp Cloud API)

סוכן/ת שולח/ת הודעה בוואטסאפ — טקסט, תמונות או הקלטה קולית — והעוזר מטפל
בנכסים, בקובץ הלקוחות, בהתאמות ביניהם, מכין קישור והודעה מוכנה על נכס,
מפיק דוח שוק ומידע תכנוני, וקורא עבורו/ה את ההסכמים, הלידים וההתראות. הוא מזהה מי שלח לפי מספר הטלפון, מבצע את הפעולה במסד ומשיב
בוואטסאפ. ומהכיוון ההפוך: **התראות הפעמון יכולות לצאת אליו/ה בוואטסאפ**,
לפי סוגים שהוא/היא מסמן/ת.

## איך זה עובד

```
סוכן/ת בוואטסאפ
      │
      ▼
Meta WhatsApp Cloud API  ──Webhook (POST)──►  Edge Function: whatsapp-webhook
                                                      │
                                     1. אימות חתימת HMAC מול App Secret
                                     2. 200 מיידי ל-Meta, עיבוד ברקע
                                     3. זיהוי הסוכן/ת לפי agency_members.phone_e164
                                     4. תמונה → Supabase Storage ‏(property-images)
                                        הקלטה → OpenAI Whisper → טקסט
                                     5. Claude עם 24 כלים (נכסים · ניתוח ומידע ·
                                        לקוחות · התאמות · הסכמים · לידים ·
                                        התראות)
                                     6. תשובה חזרה דרך Graph API

                              — והכיוון ההפוך —

notifications (טריגר במסד)  ──►  pg_cron כל 5 דק׳  ──►  notification-push
                                  (רק כשיש מה לשלוח)         │
                                                    הודעה מקובצת אחת,
                                                    לפי whatsapp_types
```

## שלב 1 — הגדרה ב-Meta for Developers

1. היכנסו ל-[developers.facebook.com](https://developers.facebook.com/) עם חשבון שמקושר ל-Meta Business.
2. **Create App** → סוג **Business** → הוסיפו את המוצר **WhatsApp**.
3. במסך **WhatsApp → API Setup** תמצאו:
   - **Phone number ID** — המזהה של המספר העסקי (לא המספר עצמו). זה `WHATSAPP_PHONE_NUMBER_ID`.
   - **Temporary access token** — טוקן ל-24 שעות, טוב לבדיקות בלבד.
4. **טוקן קבוע (חובה לפרודקשן):** Business Settings → **System Users** → צרו System User עם תפקיד Admin →
   **Add Assets** → שייכו את ה-WhatsApp Account → **Generate New Token** עם ההרשאות
   `whatsapp_business_messaging` ו-`whatsapp_business_management`. הטוקן הזה לא פג. זה `WHATSAPP_TOKEN`.
5. **App Secret:** App Settings → Basic → **App Secret** → Show. זה `WHATSAPP_APP_SECRET`.

> בזמן פיתוח, Meta מרשה לשלוח רק למספרים שנוספו ידנית תחת **API Setup → To**.
> כדי לשלוח לכל סוכן/ת צריך להעביר את האפליקציה ל-Live ולעבור Business Verification.

## שלב 2 — הגדרת הסודות ב-Supabase

Dashboard → Project Settings → **Edge Functions → Secrets** (או `supabase secrets set`):

| סוד | חובה? | מה זה |
|---|---|---|
| `WHATSAPP_TOKEN` | ✅ | טוקן הגישה הקבוע של ה-System User |
| `WHATSAPP_PHONE_NUMBER_ID` | ✅ | מזהה המספר העסקי מ-API Setup |
| `WHATSAPP_APP_SECRET` | ✅ | App Secret — משמש לאימות חתימת הוובהוק |
| `WHATSAPP_VERIFY_TOKEN` | ✅ | מחרוזת אקראית שאתם ממציאים; חייבת להיות זהה למה שתזינו ב-Meta |
| `ANTHROPIC_API_KEY` | ✅ | מפתח API מ-[console.anthropic.com](https://console.anthropic.com/) — מפעיל את הבוט |
| `OPENAI_API_KEY` | ⬜ | לתמלול הקלטות קוליות (Whisper). בלעדיו הבוט יבקש טקסט במקום |
| `SITE_BASE_URL` | ⬜ | כתובת הבסיס של האתר, למשל `https://shuknadlan.co.il` — בלעדיה אין קישור לנכס, ו-`agreement_sign_links` מסרב לבנות קישור חתימה |
| `WHATSAPP_GRAPH_VERSION` | ⬜ | ברירת מחדל `v23.0` |
| `WHATSAPP_NOTIFY_TEMPLATE` | להתראות | שם התבנית המאושרת לדחיפת התראות הפעמון. בלעדיה נשלח טקסט חופשי, שעובד רק בתוך חלון 24 השעות |
| `WHATSAPP_NOTIFY_TEMPLATE_LANG` | ⬜ | ברירת מחדל `he` |
| `ALERT_CRON_SECRET` | להתראות | אימות הקורא הפנימי של `notification-push` (אותו סוד של שאר ה-cron) |

`SUPABASE_URL` ו-`SUPABASE_SERVICE_ROLE_KEY` מוזרקים אוטומטית — אין צורך להגדיר.

> **בלי `WHATSAPP_APP_SECRET` הפונקציה מסרבת לעבד כל בקשה ומחזירה 500.** זה מכוון:
> הפונקציה חשופה בלי JWT, וחתימת ה-HMAC היא שכבת האימות היחידה שלה.

## שלב 3 — חיבור הוובהוק

כתובת הוובהוק:

```
https://obookujgolazrwycsiyn.supabase.co/functions/v1/whatsapp-webhook
```

ב-Meta: **WhatsApp → Configuration → Webhook → Edit**

- **Callback URL** — הכתובת למעלה
- **Verify token** — אותה מחרוזת שהגדרתם ב-`WHATSAPP_VERIFY_TOKEN`
- לחצו **Verify and save** (Meta שולחת GET; הפונקציה מחזירה את ה-challenge)
- תחת **Webhook fields** — סמנו **messages**

הפונקציה כבר פרוסה עם `verify_jwt = false`. אם פורסים מחדש מה-CLI:

```bash
supabase functions deploy whatsapp-webhook --no-verify-jwt
```

## שלב 4 — זיהוי הסוכנים

הבוט מזהה את הסוכן/ת לפי `agency_members.phone`. כל סוכן/ת מגדיר/ה את המספר בעצמו/ה:

**דשבורד הסוכן (`crm.html`) → "העוזר בוואטסאפ" → מספר הוואטסאפ שלי**

אפשר גם ידנית:

```sql
update public.agency_members set phone = '050-1234567' where id = '<agent-uuid>';
```

הנרמול נעשה אוטומטית בעמודה המחושבת `phone_e164`, שמטפלת בכל הפורמטים הנפוצים:

| מה שהוזן | `phone_e164` |
|---|---|
| `0521112222` | `972521112222` |
| `+972-52-333-4444` | `972523334444` |
| `521112222` | `972521112222` |
| `00972501234567` | `972501234567` |
| `04-6512345` | `97246512345` |

יש אינדקס ייחודי על `phone_e164` — שני סוכנים לא יכולים לחלוק מספר, אחרת אי אפשר
לדעת בשם מי לפעול. ניסיון לשמור מספר תפוס מחזיר שגיאה ברורה בדשבורד.

**מספר שלא מזוהה מקבל:** "סליחה, איני מזהה את מספר הטלפון שלך כמורשה במערכת."
— אלא אם **הבוט הציבורי** דלוק, ואז אותו מספר מגיע לענף אחר לגמרי: בוט
קריאה-בלבד שמחפש נכסים במאגר וממליץ על משרדים. הוא חולק את המספר ואת
הוובהוק הזה ותו לא — לא את הכלים, לא את ההוראות ולא את ההרשאות.
הפרטים, כולל המתג: [`whatsapp-public-bot.md`](whatsapp-public-bot.md).

### ואיך הסוכן/ת יודע/ת לאן לשלוח

עד שנשאלה השאלה, לא היה לזה שום מקום במוצר: הקטגוריה אמרה "שולחים הודעה
למספר של שוק נדל״ן" ולא אמרה מהו, והמספר היחיד שהיה כתוב ישב בתיעוד הזה —
מסמך שסוכן/ת לא רואה לעולם. סוכן/ת חדש/ה שמר/ה את המספר שלו/ה ונשאר/ה בלי
לאן לשלוח.

לכן בראש הקטגוריה יש עכשיו כרטיס עם **המספר עצמו** וכפתור **"פתיחת צ'אט עם
העוזר"** (`wa.me`), והוא קודם לטופס: "מול איזה מספר אני עובד/ת" היא השאלה
הראשונה, לא האחרונה.

שלוש החלטות בכרטיס הזה:

- **‏`wa.me` ולא "העתיקו את המספר".** בטלפון זה פותח את הצ'אט הנכון בלחיצה,
  ומונע את שתי הטעויות שאי אפשר לאתר אחר כך — ספרה שהוקלדה לא נכון, ושליחה
  ממכשיר אחר מזה שרשום במערכת.
- **הכפתור מושבת עד שנשמר מספר**, ואומר "קודם שמרו את המספר שלכם למטה".
  הודעה ממספר שאינו רשום מקבלת "איני מזהה את מספר הטלפון שלך" — חוויה
  ראשונה גרועה שאפשר פשוט למנוע. כפתור שנעלם נראה כמו באג; כפתור שאומר מה
  חסר הוא הוראה.
- **הקישור נושא הודעת פתיחה** (`?text=`). לא קישוט: היא חוסכת את "מה כותבים
  לבוט" ברגע שבו רוב האנשים סוגרים את החלון, **והיא פותחת את חלון 24 השעות
  של Meta** — מה שמאפשר להתראות לצאת כטקסט חופשי מלא ובחינם במקום כתבנית.

המספר יושב ב-`ASSISTANT_WA_NUMBER` ב-`crm.html` ולא ב-Secrets: הוא מזהה
ציבורי שמודפס על כל הודעה שהעוזר שולח, ולא סוד. **מספר שמוחלף ב-Meta מתעדכן
בשתי נקודות בלבד** — השורה ההיא, וטבלת המזהים למטה במסמך הזה.

## מה העוזר יודע לעשות

עשרים וארבעה כלים בשישה תחומים. ל-LLM אין גישה ל-SQL — **כל כלי מקבע בעצמו
את `agent_id`**, ולכן הוא אינו יכול לגעת בנכס או בלקוח/ה של סוכן/ת אחר/ת גם
אם ינסה.

### נכסים

| כלי | מה זה עושה |
|---|---|
| `create_property` | יוצר נכס חדש במצב `active`, מצרף תמונות ממתינות, ומנסה למצוא קואורדינטות |
| `update_property` | מעדכן שדות בנכס קיים |
| `set_property_status` | `active` / `sold` / `rented` / `archived` |
| `list_properties` | מחפש נכס לפי מה שהסוכן/ת מתאר/ת במילים |
| `attach_images` | מצרף תמונות שהגיעו בשיחה לנכס קיים |
| `property_stats` | ספירות מדויקות: סטטוס, קטגוריה, סוג עסקה, ופעילים בלי תמונות |
| `property_link` | הקישור לדף הנכס, והודעת וואטסאפ מוכנה להעברה |
| `property_performance` | צפיות (סך הכול · 7 ימים · 30 יום), פניות, קידום, הקפצה, שת״פ ותמונות |

### ניתוח ומידע על נכס

| כלי | מה זה עושה |
|---|---|
| `cma_report` | דוח השוואת שוק: עסקאות בסביבה, ממוצע, חציון, מחיר למ״ר, והפער מהמחיר המבוקש |
| `planning_info` | ייעוד קרקע, אחוזי בנייה, יחידות וקומות מותרות, סטטוס החלקה והתוכניות החלות |

### קובץ הלקוחות

| כלי | מה זה עושה |
|---|---|
| `list_clients` | הקובץ, עם שורת הדרישות של כל לקוח/ה ומספר ההתאמות הפתוחות |
| `create_client` | מוסיף לקוח/ה. די בשם; בודק כפילות בשם ובטלפון |
| `update_client` | פרטים ודרישות. מערך ריק = ביטול דרישה |
| `set_client_status` | `active` / `paused` / `closed` |

### התאמות — שני הכיוונים

| כלי | מה זה עושה |
|---|---|
| `client_matches` | מה מתאים ללקוח/ה, מול שלושת המאגרים (שלי · המשרד · שותף איתי) |
| `property_matches` | למי מהלקוחות מתאים נכס מסוים — הכיוון שלא היה קיים בדשבורד |
| `list_match_alerts` | התראות ההתאמה שנפתחו מעצמן על נכס חדש או ירידת מחיר |

### הסכמים

| כלי | מה זה עושה |
|---|---|
| `list_agreements` | סוג, סטטוס, ומי מהחותמים כבר חתם/ה. ‏`expiring_soon` — בלעדיות שנגמרת |
| `agreement_details` | הסכם אחד במלואו: עמלה, תקופת בלעדיות, נכסים, לקוחות, חותמים, וקישור לעותק החתום |
| `agreement_sign_links` | קישור החתימה האישי של כל חותם/ת שטרם חתם/ה |
| `prepare_agreement` | **מכין הזמנת תיווך** ללקוח/ה מהקובץ, מצרף את הנכסים, ומחזיר קישור חתימה |

### לידים והתראות

| כלי | מה זה עושה |
|---|---|
| `list_leads` | הלידים של הסוכן/ת, דרך `leads_masked` — ליד סגור נשאר מוסתר |
| `list_notifications` | מה ממתין בפעמון |
| `whatsapp_alerts` | הדלקה/כיבוי של סוגי ההתראה שיוצאים בוואטסאפ |

| "תשלח לי את הקישור של דני" | ‏`agreement_sign_links` — הקישור האישי, להעברה על ידי הסוכן/ת |
| "כמה עמלה סיכמנו עם דני? עד מתי הבלעדיות?" | ‏`agreement_details` |
| "איזו בלעדיות נגמרת לי?" | ‏`list_agreements` עם `expiring_soon` |
| "מה חדש?" | ‏`list_notifications` |
| "תעדכן אותי כאן על לידים חדשים" | ‏`whatsapp_alerts` עם `enable: [new_lead]` |

### הקישור לנכס — הבוט מכין, הסוכן/ת שולח/ת

‏`property_link` מחזיר שלושה דברים: את הקישור לדף הנכס, **הודעה מוכנה**
(כותרת, כתובת, חדרים, שטח, מחיר וקישור), וכתובת `wa.me` שפותחת את וואטסאפ
עם ההודעה כבר בפנים. עם `client_id` מקובץ הלקוחות ההודעה נפתחת בפנייה בשם,
ו-`wa.me` מכוון ישירות לצ'אט של אותו/ה לקוח/ה.

**הבוט אינו שולח ללקוח/ה**, ומאותה סיבה בדיוק ש-`agreement_sign_links` אינו
שולח: ההודעה יוצאת מהמספר של הסוכן/ת, נקראת אישית ולא כהודעת מערכת, ומי
שמחליט/ה למי היא נשלחת הוא/היא מי שמכיר/ה את הצדדים. זו גם אותה תבנית של
כפתור "💬 שליחה בוואטסאפ" בכל מקום בדשבורד — `window.open('https://wa.me/…')`
ולא קריאה לשרת.

**קישור לנכס שאינו `active` חוזר עם אזהרה.** ה-policy על `properties`
מחזירה לגולש/ת אנונימי/ת נכסים פעילים בלבד, ולכן קישור לנכס בארכיון ייפתח
אצל הסוכן/ת ויראה דף ריק אצל הלקוח/ה. הכלי אומר את זה במקום שזה יתגלה אחרי
השליחה.

### דוח השוק והמידע התכנוני — למה הם עברו למסד

‏`cma_report` ו-`property_planning_public` גוזרות את זהות הסוכן/ת מ-`auth.uid()`.
זו ההחלטה הנכונה לדפדפן, ובדיוק הסיבה שהבוט לא יכול לקרוא להן: הוא מזהה
לפי מספר טלפון ורץ עם `service_role`, כך ש-`auth.uid()` שלו הוא `null`.
אותה בעיה של הלקוחות וההתאמות ב-`20261029090000`, ואותו פתרון —
‏`agent_cma_report(p_agent_id, p_property_id)` ו-
‏`agent_property_planning(p_agent_id, p_property_id)`, מוענקות ל-`service_role`
בלבד.

**כל ההיגיון של ה-CMA עבר דירה ולא הועתק.** ‏`cma_report` נשארה בדיוק באותה
חתימה ועם אותם קודי שגיאה (‏`crm.html` ממפה אותם להודעות), והיא עכשיו עוטפת
את `agent_cma_report` עם `current_agent_id()`. שני עותקים של הרחבת הרדיוס
ושל חישוב המחיר למ״ר היו מתפצלים תוך חודש, והסוכן/ת היה/הייתה מקבל/ת
בוואטסאפ מספר אחר מזה שבמסך.

**המידע התכנוני מצונזר לפי בעלות ולא לפי ערוץ.** על הנכס של הסוכן/ת חוזר
המידע המלא — גוש, חלקה ושטח החלקה — זה מה שהוא/היא רואה ממילא בפאנל "מידע
תכנוני" ב-CRM. על נכס של עמית/ה במשרד, או כל נכס פעיל אחר, חוזר בדיוק מה
ש-`property_planning_public` מגישה לגולש/ת אנונימי/ת. הגבול נשאר ב-SQL ולא
עבר ל-Edge Function מאותה סיבה שהוא לא בצד הלקוח: רשימת שדות אסורים
שמתוחזקת בשני מקומות מתפצלת בסוף מעצמה. הפרטים: `docs/land-planning.md`.

**התשובה בצ'אט אינה הדוח.** ‏`cma_report` בצ'אט מחזיר תקציר — ממוצע, חציון,
טווח, מחיר למ״ר, הפער מהמחיר המבוקש, וחמש העסקאות הקרובות ביותר. הדוח המלא,
זה שמודפס ונשלח ללקוח/ה, נשאר בדשבורד: רשימה של כל העסקאות ברדיוס בהודעת
וואטסאפ אינה נקראת ורק מסתירה את השורה החשובה.

### מה מכוון ולא באג

- **אין מחיקה אמיתית.** "תמחק נכס" מעביר ל-`archived`, בדיוק כמו בדשבורד.
  ו"תמחק לקוח/ה" מעביר ל-`closed` — הרשומה נשארת בקובץ.
- **הבוט לא יוצר כפילות.** לפני יצירת נכס רצה אותה בדיקה שרצה בטופס בדשבורד
  (‏`findDuplicateProperty` ב-`agent.ts`): אותה עיר, רחוב ומספר בית אחרי נרמול,
  ורק כשמספר החדרים, הקומה וסוג העסקה מתאימים — אחרת זו דירה אחרת באותו בניין.
  נמצאה התאמה (גם נכס שנמכר או בארכיון) — `create_property` **לא** יוצר, אלא
  מחזיר `duplicate` עם מספר המודעה והסטטוס, והבוט שואל: להחזיר ולעדכן את
  הקיימת, או לפרסם מודעה נוספת? החזרה = `update_property` + `set_property_status`
  ל-`active`; מודעה נוספת = `create_property` שוב עם `force_new: true`. הדגל הזה
  אינו שדה במסד — `pickWritable` מסננת אותו החוצה.
- **תמונה בלי כיתוב לא מייצרת תשובה.** וואטסאפ שולחת אלבום כהודעות נפרדות; תשובה לכל
  תמונה הייתה מציפה את הסוכן/ת ועלולה ליצור נכס כפול. התמונות נשמרות בצד ומתחברות
  לנכס הבא שנוצר (או לנכס האחרון בשיחה, ואז נשלח אישור קצר אחד).
- **גיאוקוד רק בעפולה.** מבוסס על שכבת הכתובות של העירייה. נכס בעיר אחרת נוצר בלי
  פין על המפה, וזה לא חוסם את הפרסום.
- **הסוכן/ת רואה רק את הנכסים שלו/ה.** כל כלי מקבע `agent_id` בעצמו — ה-LLM לא יכול
  לגעת בנכס של סוכן/ת אחר/ת גם אם ינסה.
- **ליד שטרם נפתח נשאר מוסתר גם כאן.** ‏`list_leads` קורא מ-`leads_masked`,
  ה-view שמחליף שם, טלפון והודעה בגרסה מוסתרת (‏`א***`, ‏`05-****1`) כל עוד
  ‏`status='masked'`. ‏`service_role` עוקף RLS אבל **לא** את ה-view, וזה
  בדיוק מה שמונע מהצ'אט להיות הדלת האחורית למאגר הלידים.
- **ספירה היא שאילתה ולא קריאה של רשימה.** זה נלמד מכשל: לשאלה "כמה נכסים
  מסחריים יש לי" הבוט קרא ל-`list_properties`, קיבל 50 שורות (התקרה של
  הכלי), וענה "מתוך 50 האחרונים, כ-42 מסחריים". התשובה נשמעה מוסמכת והייתה
  שגויה בשורש. לכן יש `property_stats` (שאילתת ספירה אחת במסד), ולכן
  ‏`list_clients` מחזיר גם `total_active` וגם `total_all` נפרד מהחלון שהוחזר,
  וההוראה בפרומפט מפורשת: לשאלת "כמה" — כלי ספירה, לא ספירה של רשימה.

### הכנת הסכם מהצ'אט

"תכין הזמנת תיווך לרונית על הדירה בעלייה 20, 2% עמלה" מייצר הסכם אמיתי:
הלקוח/ה נלקח/ת מקובץ הלקוחות, הנכסים מצורפים לפי מה שהסוכן/ת ביקש/ה,
והמסמך נבנה ונשמר. מה שחוזר לצ'אט הוא **קישור החתימה האישי של כל חותם/ת**.

**אותו קישור משמש לשתי הדרכים**, ולכן אין מה לבחור מראש: לחתימה מרחוק
מעבירים אותו לחותם/ת, ולחתימה פנים מול פנים פותחים אותו על המכשיר של
הסוכן/ת ומושיטים. לכל חותם/ת אסימון משלו/ה — בני זוג מקבלים שני קישורים
נפרדים, כמו בדשבורד.

#### ארבע החלטות ביכולת הזו

**1. אותו נוסח ואותו קוד, ולא עותק שני.** הטקסט המשפטי יושב ב-
`assets/agreement-templates.js` וה-HTML נבנה ב-`assets/agreement-doc.js`,
ושלושת הדפים באתר טוענים את שניהם. ‏Edge Function אינה יכולה לייבא מחוץ
ל-`supabase/functions` — ה-CLI בונה את הבאנדל מהתיקייה הזו בלבד — ולכן יש
עותק **זהה בייט-בייט** ב-`supabase/functions/_shared/`,
ו-`scripts/check_agreement_assets.py` חוסם ב-CI כל PR שמשאיר פער.

הבדיקה הזו אינה זהירות יתר. פער בין שני עותקים של נוסח משפטי אינו נראה
בשום מקום: הדף ייראה תקין, המסמך ייבנה, הלקוח/ה יחתום/תחתום — ורק כשתוגש
תביעת דמי תיווך יתגלה שהסעיף שנחתם אינו הסעיף שבתיק. זו טעות שאי אפשר
לתקן למפרע.

**2. חסר נתון — ההסכם לא נוצר.** ‏`prepare_agreement` מריץ את אותה בדיקה
שהאשף מריץ (`agrValidate` ↔ `missingForAgreement`): ת.ז. לכל חותם/ת, עמלה,
ותקופת בלעדיות בטופסי בלעדיות. חסר משהו — חוזר `missing` ולא נוצרת שורה,
והבוט מבקש את מה שחסר. הזמנה בלי אלה אינה הזמנה בכתב כדין, וטופס חסר
שנחתם גרוע מטופס שלא נוצר: הוא נראה תקין עד הרגע שבו צריך אותו.

> ת.ז. שהסוכן/ת מוסר/ת בצ'אט נשמרת גם בכרטיס הלקוח/ה, כדי שההסכם הבא לא
> ייעצר באותו מקום. אותה התנהגות כמו ההשלמה המהירה באשף.

**3. יצירה — כן. תיקון וביטול — לא.** גוף המסמך ננעל בטריגר
(`agreements_freeze_body`) ברגע שההסכם יוצא מ-`draft`, וכל ערכה הראייתי של
החתימה האלקטרונית תלוי בזה. הדרך לתקן הסכם היא הדרך שהנייר מכיר: לבטל
ולהוציא חדש — באשף שבדשבורד, שבו יש תצוגה מקדימה מלאה של מה שהלקוח/ה
יראה/תראה. זה בדיוק מה שאי אפשר להראות בהודעת וואטסאפ, ולכן זה נשאר שם.

**4. הסטטוס נשאר `draft`.** מה שמסמן `sent` הוא השליחה דרך `agreement-sign`
בדשבורד, שגם שולחת את המייל — לא העתקת קישור. אותו כלל שכבר חל על
‏`agreement_sign_links`, ומאותה סיבה: העברת קישור אינה אירוע שהמערכת ראתה.

### שני גבולות שנשמרים בכוונה

**הבוט אינו שולח ללקוח/ה.** לא את קישור החתימה, לא את קישור הנכס ולא את
העותק החתום. הכול חוזר לצ'אט של הסוכן/ת, ומשם יוצא **מהמספר שלו/ה** בלחיצה
שלו/ה — בדיוק כמו כפתור "💬 וואטסאפ" בדשבורד. שתי סיבות: ההודעה נקראת
אישית ולא כהודעת מערכת, ומי שמחליט/ה למי היא נשלחת הוא/היא מי שמכיר/ה את
הצדדים.

**אין פתיחת ליד.** ‏`claim_lead` מעבירה כסף או צורכת מכסה, והיא נעולה מאחורי
`lead-claim` שגוזרת את הזהות מ-JWT מאומת. זיהוי לפי מספר טלפון הוא ראיה
חלשה יותר, ופעולה שמוציאה כסף לא נשענת עליה. ‏`list_leads` מחזיר את
`unlock_where` — קישור ישר לקטגוריית הלידים בדשבורד.

## ההתראות שיוצאות בוואטסאפ

הפעמון ב-CRM מדווח על אירועים בזמן אמת — אבל רק למי שהדשבורד פתוח מולו/ה.
מכאן כל סוג התראה יכול לצאת **גם** כהודעה מהעוזר.

**ההדלקה היא פר סוג, ולא מתג אחד:** בדשבורד → "ניהול התראות", תיבת
"💬 גם בוואטסאפ" בכל שורה. אפשר גם מתוך הצ'אט ("תעדכן אותי כאן על לידים
חדשים" → `whatsapp_alerts`).

**הערוץ מגודר לאותם מסלולים כמו השיחה — PROFESSIONAL ו-Elite.** זה אותו
עוזר בכיוון ההפוך: אותו מספר, אותה זהות, ואין הגיון שהודעה **ממנו** תצא
למי שאינו יכול לכתוב **אליו**. האכיפה במסד, ב-
`notification_push_due_agents`, ועם אותם שלושה תנאים שכל יכולת בתשלום
בפרויקט נשענת עליהם (כמו `property_description_tier_ok`): מסלול, פעילות
ו-`billing_status`.

הדשבורד מכבה את התיבות ואומר את הסיבה עם קישור לדף המסלולים; הבדיקה שם היא
על `tier` בלבד, כי `billing_status` אינו נטען לדפדפן — אותה תבנית כמו כפתור
דוח ה-CMA, שבה התצוגה מרמזת וה-DB אוכף.

**סימון שנשמר לא נמחק בירידת מסלול.** ההודעות פשוט מפסיקות לצאת, ושדרוג
מחזיר אותן בלי לסמן מחדש. מחיקת בחירה בגלל שינוי מסלול היא איבוד מידע שאיש
לא ביקש.

> ערוץ הוואטסאפ של **התזכורות** (`docs/agent-reminders.md`) הוא מנגנון אחר
> ואינו מגודר — הוא אינו העוזר, אינו מריץ LLM, ושולח דייג'סט שבועי של מצב
> המודעות. הגידור כאן הוא על העוזר ועל מה שיוצא בשמו.

### למה זו רשימת מאושרים ולא רשימת מושתקים

בכל הפרויקט העדפות ההתראות הן רשימת **מושתקים** (ראו
`docs/notifications-center.md`): היעדר שורה = קבלת הכול, וסוג חדש מגיע
לכולם אוטומטית. ‏`whatsapp_types` הוא החריג המכוון, והסיבה ספציפית: זה ערוץ
**יוצא** שעולה כסף, ושחסימה אחת בו מייקרת אותנו אצל כל הנמענים העתידיים
דרך דירוג האיכות של Meta. ערוץ כזה לא נדלק לאיש בלי בקשה מפורשת. התוצאה:
סוג התראה חדש שייכנס בעתיד יופיע בפעמון של כולם — ובוואטסאפ רק אצל מי
שיסמן אותו.

**חריג אחד, ומסומן ככזה:** שני הסוגים של מנהל/ת הפלטפורמה —
‏`platform_signup` (מי הצטרף/ה) ו-`platform_upgrade` (מי עבר/ה למסלול
בתשלום, או ביקש/ה) — נדלקים מראש במיגרציה, ל**מנהלי הפלטפורמה בלבד**,
שהם הנמענים היחידים שלהם ושלבקשתם הם נבנו. סוכן/ת רגיל/ה אינו/ה מקבל/ת אותו כלל, ולכן
ההדלקה אינה פותחת ערוץ לאיש שלא ביקש. הפרטים:
`docs/notifications-center.md` → "הצטרפות חדשה".

### ארבע החלטות במנגנון

1. **הודעה אחת מקבצת את כל ההתראות הפתוחות.** שלוש הודעות ברצף הן הדרך
   המהירה ביותר לחסימה של המספר. מרווח הקיבוץ הוא
   ‏`notif_push_gap_minutes` (ברירת מחדל 10 דקות), וה-cron רץ כל חמש.
2. **התראה שנקראה בדשבורד אינה נשלחת.** ‏`notifications.read` הוא התנאי,
   ולכן מי שעבד/ה בדשבורד עכשיו לא מקבל/ת תקציר של מה שהרגע ראה/תה. זה מה
   שהופך את הערוץ מ"עוד עותק" ל"מה שפספסת".
3. **חלון מבט לאחור של 12 שעות** (`notif_push_lookback_hours`). התראה שלא
   נקראה שלושה ימים אינה "מה שפספסת" אלא הצטברות, ושם התזכורות
   (`docs/agent-reminders.md`) עושות עבודה טובה יותר.
4. **שעות השקט הן של האדם ולא של סוג ההודעה.** נלקחות מאותה שורה
   ב-`agent_reminder_preferences` שמשרתת את התזכורות (ברירת מחדל 21→8), כי
   מי שקבע/ה שקט עד 8:00 לא התכוון/ה שזה חל על התזכורות בלבד.

וסוג שכובה בפעמון לא ייווצר במסד מלכתחילה (הטריגר
`notifications_apply_preferences` מחזיר `null`), ולכן גם לא יישלח. הדשבורד
מכבה ומנקה את תיבת הוואטסאפ יחד עם הפעמון, והכלי בצ'אט מחזיר
`muted_conflict` ואומר את זה במשפט.

### שורת יומן שלא יצאה אינה מבליעה את ההתראות שבתוכה

‏`notification_push_claim` רושמת את שורת היומן **לפני** השליחה, וזה נכון —
זה מה שמונע הודעה כפולה. אבל הקריאה אליה נכשלת מדי פעם ב-504 מה-gateway,
ו-504 אומר שה-gateway ויתר, לא שה-`INSERT` לא נסגר. השורה שנשארת מכילה
`notification_ids`, וה-`not exists` שמונע כפילות היה מסתכל על *קיום* השורה
בלבד — כלומר ההתראות שבתוכה לא היו נכללות בשום הודעה עתידית. **לנצח.**

מאז `20261101090000` הפרדיקט הוא `notification_push_log_holds`: שורה חוסמת
רק אם היא `sent`, או `pending` בתוך חסד של 30 דקות
(`notif_push_pending_grace_minutes`). שורה שנכשלה, או שנתקעה מעבר לחסד,
משחררת את ההתראות שבתוכה לסבב הבא.

שלוש נקודות שקל לפספס:

- **אותו פרדיקט בדיוק ב-`notification_push_ready`.** אילו התנאי של ה-cron
  היה רחב מזה של ה-claim היינו מעירים Edge Function לשווא; אילו היה צר
  ממנו, ה-cron היה שותק כשיש עבודה.
- **החסד הוא זמן ולא סטטוס.** אחרת: שורה תקועה חוסמת → `ready()` מחזירה
  false → ה-cron לא מעיר → ה-`reconcile` שאמור לשחרר לא רץ לעולם.
  ‏`notification_push_reconcile()` רצה בפתיחת כל claim, אבל לרישום בלבד.
- **‏`max(created_at)` ב-`notification_push_due_agents` נשאר על כל השורות**,
  בשונה מהתזכורות. המרווח כאן הוא עשר דקות, ושורה תקועה שמעכבת עשר דקות
  היא בדיוק ההפוגה שרצינו בין שני ניסיונות. רק התקרה היומית מסוננת, כדי
  שכשלים לא יאכלו את שתים-עשרה ההודעות המותרות — ו-`notif_push_max_failures_24h`
  (3) עוצר ערוץ ששבור באמת.

#### למה Marketing ולא Utility — ולמה לא לנסות שוב

‏Utility היא הקטגוריה **הנכונה** מבחינת תוכן: ההודעה נוגעת אך ורק לחשבון
של הנמען/ת — הלידים שלו/ה, ההתאמות בקובץ שלו/ה, ההסכמים שלו/ה. היא גם
זולה יותר ואינה כפופה להסכמה שיווקית.

**המסווג האוטומטי של Meta סירב, שלוש פעמים.** הדיאלוג "הקטגוריה לא
תואמת" הופיע עם `Recommended: שיווק` ועם האזהרה "תבנית הודעה זו תידחה",
על שלושה נוסחים:

1. ‏`🔔 {{1}}, מה שחדש אצלך בשוק נדל״ן:` — "מה שחדש" נקרא כניוזלטר
2. ‏`🔔 {{1}}, יש עדכונים חדשים בחשבון שלך…` — עדיין אימוג'י ושם מותג בפתיח
3. ‏`שלום {{1}}, עדכון על הפעילות בחשבון הסוכן/ת שלך:` — בלי אימוג'י ובלי
   שם מותג, וגם זה לא עבר

מי שמגיע לכאן ומתפתה לנסות ניסוח רביעי: **נוסו כבר שלושה, כולל אחד נקי
לגמרי.** דייג'סט מקובץ נקרא למסווג כעדכון תקופתי ולא כאירוע עסקה יחיד,
וזה כנראה הגבול האמיתי.

**מה שנשאר לשים לב אליו ב-Marketing:** בוואטסאפ אפשר לבחור "הפסק לקבל
הודעות קידום מכירות", וזה חוסם תבניות שיווק ומשאיר Utility. סוכן/ת שיעשה
זאת יפסיק/תפסיק לקבל את ההתראות. זה **אינו כשל שקט**: ‏Meta מחזירה 131050,
‏`notification-push` מכבה את הערוץ באותו רגע ורושמת את הסיבה ב-
`notification_push_log.last_error` (ראו "ביטול מול Meta הוא ביטול" למטה).
מי שיראה ערוץ שכבה לבדו — שם התשובה.

> **פרמטר של תבנית אינו יכול להכיל תו שורה חדשה**, טאב, או יותר מארבעה
> רווחים רצופים — ‏Meta דוחה את השליחה. הגרסה הראשונה של `templateSummary`
> חיברה את ההתראות ב-`\n` כדי שהרשימה תיראה כמו רשימה, וזה היה נכשל בשליחה
> הראשונה **מחוץ** לחלון 24 השעות, כלומר בדיוק במצב היחיד שהתבנית קיימת
> בשבילו — ובתוך החלון הכול נראה תקין, כי שם יוצא טקסט חופשי.
>
> לכן `{{2}}` מגיע כשורה אחת, עם `•` בראש כל פריט כמפריד, ו-`\n` שמגיע
> מגוף התראה (ציטוט מביקורת, למשל) משוטח לפני השליחה. השורה הנפרדת של
> `{{2}}` **בתבנית** היא בסדר גמור: המגבלה חלה על הפרמטר, לא על הנוסח.

וכפתור אחד מסוג **Visit website → Dynamic**:

| שדה בטופס | ערך |
|---|---|
| הטקסט בלחצן | `ניהול ההתראות` |
| סוג כתובת URL | דינמית |

**שדה הדוגמה רוצה כתובת מלאה ולא את הסיומת** — הוא משלים `https://` לבד,

הפרמטר שהקוד שולח בזמן אמת הוא דווקא **הסיומת בלבד**

וסוכן/ת שמוצף/ת ולא מוצא/ת איך לעצור חוסם/ת את המספר.

### הפונקציות במסד שהעוזר קורא להן

כולן ב-`service_role` בלבד ולא נגישות ל-`authenticated`. זה לא הידוק מיותר:
פונקציה שמקבלת מזהה סוכן/ת בפרמטר ורצה `security definer` היא דלת עקיפה
ל-RLS אם היא פתוחה לדפדפן.

| פונקציה | למה היא קיימת |
|---|---|
| `agent_client_matches` | ‏`match_properties_for_client` גוזרת את הזהות מ-`auth.uid()`, ולעוזר אין JWT — כאן המזהה מפורש |
| `agent_client_match_counts` | ספירה + ההתאמה החזקה לכל לקוח/ה, בקריאה אחת |
| `agent_property_client_matches` | הכיוון ההפוך, שלא היה קיים בשום מקום |
| `agent_property_stats` | ספירות הנכסים במעבר אחד |

**מקור האמת לניקוד נשאר אחד:** שלוש הראשונות קוראות ל-`client_property_match`,
בדיוק כמו הפאנל בדשבורד וכמו התראות ההתאמה. נוסחה שמחושבת פעם שנייה הייתה
מתפצלת מהראשונה תוך חודש, והסוכן/ת היה מקבל/ת בוואטסאפ ציון אחר מזה שבמסך.

## בדיקה בלי Meta

`scripts/whatsapp_webhook_test.py` בונה payload בפורמט של Cloud API, חותם אותו
ב-HMAC-SHA256 בדיוק כמו Meta, ושולח אותו לפונקציה. זה מאפשר לבדוק את כל הזרימה
עוד לפני שהוובהוק מחובר. ספריית התקן של פייתון בלבד — אין מה להתקין.

מגדירים ב-`.env` את `SUPABASE_URL`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`
ו-`WA_TEST_FROM` (ראו `.env.example`), ואז:

```bash
# רצף בדיקות בטוח: לחיצת יד, דחיית חתימה שגויה, מספר לא מוכר, "שלום"
python scripts/whatsapp_webhook_test.py all --check

# בדיקה אמיתית של יצירת נכס
python scripts/whatsapp_webhook_test.py text "תעלה נכס באבן גבירול 10, 3 חדרים, 1.8 מליון" --check
```

**דגל `--check` הוא העיקר.** הפונקציה מחזירה 200 מיד וממשיכה לעבד ברקע, אז קוד
200 לבדו לא מוכיח כלום. עם `--check` הסקריפט קורא את `whatsapp_messages` ומראה
מי זוהה, מה הבוט ענה ואיפה זה נפל. הוא דורש `SUPABASE_SERVICE_ROLE_KEY` ב-`.env`.

| פקודה | מה נבדק |
|---|---|
| `verify` | לחיצת היד (GET) שמבצעת Meta בהגדרת הוובהוק |
| `badsig` | חתימה שגויה חייבת לחזור 401 — שכבת האבטחה היחידה של הפונקציה |
| `unknown` | מספר שאינו רשום → "איני מזהה את מספר הטלפון שלך" (או הבוט הציבורי, אם המתג דלוק) |
| `text "…"` | זרימה מלאה: זיהוי → LLM → כלים → תשובה |
| `image --media-id X` | דורש media id **אמיתי** — הפונקציה מורידה את הקובץ מ-Graph API |
| `all` | הרצף הבטוח, בלי יצירת נכסים |

שימו לב: `text` פועל מול הפרויקט החי. בקשה ליצירת נכס באמת תיצור נכס.

בנוסף, `whatsapp_messages.error` שומר כשל בתמלול, בשליחה או בהרצת ה-LLM.

## עלויות

- **Meta:** שיחות שהסוכן/ת יוזם/ת (service conversations) — חלון 24 שעות. תמחור מעודכן
  ב-[Meta pricing](https://developers.facebook.com/docs/whatsapp/pricing).
- **Anthropic:** קריאה אחת (או שתיים ויותר, כשמופעלים כלים) לכל הודעה.
  הפונקציה מוגדרת `effort: "medium"`. ‏`low` הספיק כשהמשימה הייתה חילוץ
  פרטי נכס מול חמישה כלים; עם שמונה-עשר כלים ושני מאגרים שצריך להצליב
  ביניהם, הבחירה בין `client_matches` ל-`property_matches` ו"קודם למצוא את
  המזהה" הן החלטות שבהן `low` טועה. אם הלטנטיות בצ'אט נעשית מורגשת — לחזור
  ל-`low` ולהצר את רשימת הכלים, לא לוותר על הדיוק.
- **דחיפת התראות:** הודעה אחת מקובצת, ובתוך חלון 24 השעות היא **טקסט חופשי
  ולכן חינמית**. מחוץ לחלון זו הודעת תבנית, חסומה מלמעלה ב-
  `notif_push_max_per_day` (ברירת מחדל 12 ליום, וזה תקרה ולא צפי).
- **OpenAI Whisper:** רק על הקלטות קוליות.
