# אימות כניסה (אימות דו-שלבי): וואטסאפ או אפליקציה

סוכן/ת מפעיל/ה ב-CRM, תחת "הגדרות חשבון" ← "אימות כניסה". מרגע ההפעלה,
כל כניסה חדשה (בסיסמה או ב-Google) מבקשת הודעה אחת לגבריאלה בוואטסאפ:
כפתור פותח את וואטסאפ עם הנוסח מוכן, `אימות כניסה 482193`, שולחים
וחוזרים לאתר. הדף בודק כל 3 שניות, ונפתח לבד.

**ולצד זה, למי שמעדיף/ה: אפליקציית אימות** (Google Authenticator וכדומה,
‏TOTP של Supabase Auth). שתי הדרכים שקולות. אפשר להפעיל אחת מהן או את
שתיהן, ובכניסה עוברים באיזו שנוחה: מסך האימות מציג את כפתור הוואטסאפ
תמיד, ושדה קוד למי שיש לו/ה אפליקציה. האפליקציה עובדת גם בלי קליטה.

| מי | מה |
| --- | --- |
| סוכן/ת | רשות. מפעילים ומכבים לבד |
| מנהל/ת משרד | **חובה** (מ-13.10.2026, `20270507090000`), אם יש נייד בכרטיס. בלי נייד - פטור עד שיתווסף, ומופיע/ה בסקירת ההרשאות (`docs/access-review.md`) |
| מנהל/ת פלטפורמה | **חובה.** בלי אימות אין הרשאות, והכיבוי חסום |

"מי חייב/ת מעצם התפקיד" מוגדר במקום אחד: `_mfa_role_required(uid)`. גם
`_mfa_pending_self()` וגם `mfa_status()` קוראות לה. תפקיד חדש שחייב אימות
נכנס לשם בלבד.

**למה הפטור למי שאין לו/ה נייד:** אימות הוואטסאפ צריך לאן לשלוח. בלי נייד,
`wa_login_start` מחזירה `no_phone` ומסך האימות ננעל בלי מוצא.

## למה הודעה נכנסת ולא קוד שנשלח

זה אותו דפוס של "אימות חתימה" בהסכמים (`_shared/agreement-wa-verify.ts`).
קוד שאנחנו שולחים מחוץ לחלון 24 השעות חייב תבנית AUTHENTICATION מאושרת
של Meta. הודעה שהסוכן/ת שולח/ת **אלינו** אינה צריכה תבנית. וזה חזק יותר
מקוד, לא חלש יותר: Meta מוסרת את המספר שממנו נשלחה ההודעה (`from`),
והאימות עובר רק כשהוא הנייד שבכרטיס (`phone_e164`). מי שגנב/ה את הסיסמה
ושלח/ה את ההודעה מטלפון אחר נדחה/ית.

האימות הוא **לכל session**, לפי ה-claim `session_id` שב-JWT. הוא נשמר
לאורך חידושי הטוקן, כלומר מאמתים פעם אחת בכל כניסה ולא בכל טעינה.

| חלק | איפה |
| --- | --- |
| מי הפעיל/ה | `agent_wa_2fa` |
| בקשות ואימותים | `wa_login_verifications` (קוד בן 6 ספרות, 10 דקות, 10 בקשות ב-10 דקות) |
| יצירת קוד | `wa_login_start(p_enable)`. ‏`p_enable` = ההפעלה מההגדרות, שנכנסת לתוקף רק אחרי הודעה |
| קליטת ההודעה | `whatsapp-webhook` ← `wa_login_verify(nonce, from)`, לפני זיהוי הסוכן/ת |
| כיבוי | `wa_2fa_disable()`, רק מתוך session מאומת |

**האפליקציה** היא כולה של Supabase Auth (`sb.auth.mfa.enroll`,
‏`challengeAndVerify`, `unenroll`). קוד ממנה מעלה את ה-JWT ל-`aal2`,
ו-`mfa_pre_request` מדלג/ת עליו בשורה הראשונה. **מלכודת אחת:** Supabase
Auth מתיר להסיר אפליקציה רק מ-session שנכנס עם קוד ממנה. מי שנכנס/ה
בוואטסאפ ומנסה לכבות אותה מקבל/ת `insufficient_aal`, וה-CRM מסביר לצאת
ולהיכנס עם הקוד.

## המסך אינו המנעול

מי שמחזיק/ה סיסמה גנובה יכול/ה לפנות ל-API ישירות בלי לעבור במסך, ולכן
האכיפה יושבת בשרת, בשלוש שכבות:

| שכבה | איפה | מה קורה למי שחייב/ת אימות ולא אימת/ה |
| --- | --- | --- |
| Data API (טבלאות ו-RPC) | `mfa_pre_request` (pre-request של PostgREST) | ה-claims מתאפסים לאלה של אורח/ת: `auth.uid()` הוא `null` |
| Storage | policy מגבילה `mfa required for storage` על `storage.objects` | אין קריאה, העלאה או מחיקה דרך ה-API (קישורים ציבוריים לא נפגעים) |
| Edge Functions | `_shared/mfa-gate.ts`, מיד אחרי `getUser` | ‏403 `mfa_required` |

**למה איפוס ולא שגיאה:** ה-session משותף לכל הדפים באותו דומיין. טלפון
שנשאר מחובר היה מקבל דף בית שבור. כך הוא מקבל את האתר הציבורי כמו
אורח/ת, ושום דבר פרטי. לפני ההחלה נבדק שאין policy של `authenticated` עם
`using (true)` ב-`public` או ב-`storage`. policy כזו הייתה דולפת דרך
האיפוס, ולכן **אסור להוסיף אחת כזו**.

"מי חייב/ת אימות ועוד לא אימת/ה" בנתיב הרגיל של `mfa_pre_request` נבדק
לפי היקף, כל מקור בבלוק משלו: תפקיד (`_mfa_role_required_self`, שקוראת
ל-`_mfa_role_required`), הרשמה (`_mfa_enrolled`: וואטסאפ או TOTP מאומת),
ואז session מאומת (`_mfa_session_verified`). `_mfa_pending_self()` נשארת
ההגדרה המאוחדת, ומתג `_mfa_break_glass()` (כבוי כברירת מחדל) חוזר אליה.
‏`mfa_status()` מחזירה ל-CRM ולפונקציות ה-Edge `pending`, `enabled`
(וואטסאפ), `totp` (אפליקציה), `required`, `admin`, `manager`,
ו-`check_error` (true כשה-pre-request או חיפוש ב-`mfa_status` נתקלו
בשגיאה; אבחון, לא גייט).

## הזרימה ב-CRM

1. כניסה רגילה לא משלמת כלום: `loadDashboard` שולף את הכרטיס כרגיל.
2. חשבון שחייב אימות נראה במסד כאורח/ת, ולכן `loadDashboard` לא מוצא
   כרטיס. רק בענף הזה `mfaGateOnMissingAgent()` שואל/ת את `mfa_status`,
   ומציג/ה את מסך האימות.
3. הקוד נוצר כשהמסך עולה, כדי שהכפתור יהיה קישור `wa.me` אמיתי ולא
   `window.open` אחרי `await` (שנחסם כחלון קופץ).
4. אחרי הלחיצה: בדיקה כל 3 שניות ומיד בחזרה ללשונית. כש-`pending` יורד,
   ניתוב מחדש עם `force`.
5. **רשת ביטחון:** אם בכל זאת הגענו ל-`join-agency` (בזיהוי האוטומטי או
   ב"חיבור לכרטיס הקיים שלי"), והוא ענה `mfa_required` - מוצג מסך
   האימות, ולא "מי את/ה?".

### מה קרה ב-12.10.2026

מיד אחרי הפריסה, מנהל/ת הפלטפורמה נחת/ה במסך "מי את/ה?", וכל ניסיון
להזין מספר רישיון החזיר "הבקשה נכשלה". המסד עבד נכון: הכרטיס הוסתר
(`pending: true`), ו-`join-agency` ענה `mfa_required`. אבל ביומני
Supabase אין אף קריאה של הדפדפן ל-`mfa_status`, כלומר בדיקה 2 לא רצה,
כנראה מגרסה ישנה של `crm.js` בטלפון. המסך לא ידע לקרוא את `mfa_required`
ולכן לא הוביל לשום מקום. מכאן סעיף 5.

**כך משחררים חשבון תקוע ידנית,** בלי DDL: שורה מאומתת ל-session הנוכחי.
ה-session לפי `auth.sessions` (זה עם `updated_at` האחרון):

```sql
insert into public.wa_login_verifications (user_id, session_id, nonce, verified_at)
values ('<user_id>', '<session_id>', 'manual', now());
```

זה עוקף את האימות **ל-session אחד בלבד**, ולכן רק אחרי זיהוי מלא של
הפונה.

## כשלים: סגור לפי היקף, וסגור ב-Edge

מ-`20271027150000` ה-pre-request נכשל **סגור לפי היקף**. הכשל הפתוח
(‏`exception when others` ואז `return`) הורד: שגיאה בבדיקה כבר אינה
מכניסה מנהל/ת עם גישת `authenticated` מלאה.

- אם כל בדיקות ההיקף הצליחו ואומרות "לא בטווח" - הבקשה עוברת. סוכן/ת
  רגיל/ה לא נפגע/ת.
- אם מקור אומר "בטווח", או שהבדיקה זרקה - נדרש session מאומת. אין אימות,
  או שגם הבדיקה הזו זרקה - ה-claims מתאפסים לאורח/ת. `shuk.mfa_pending_sub`
  נשמר (כדי ש-`mfa_status()` ו-`wa_login_start()` ומסך האימות ימשיכו
  לעבוד), ו-`shuk.mfa_check_error` = `1`.
- `mfa_status()` מבודדת כל חיפוש. טבלה שבורה עדיין מחזירה `pending`
  (נקרא מ-`shuk.mfa_pending_sub`, בלי גישה לטבלה) ו-`check_error: true`.
  ‏`_shared/mfa-gate.ts` קורא את `.pending` ולא שינה התנהגות: `pending`
  הוא 403 `mfa_required`, וקריאה שנכשלה ל-`mfa_status` היא 503
  `mfa_check_failed`.
- `QUERY_CANCELED` (`statement_timeout`) אינו נתפס ב-`WHEN OTHERS` ומבטל
  את הבקשה ממילא.
- המתנה למנעול בתוך פונקציות העזר חסומה ב-2 שניות (`lock_timeout` ברמת
  הפונקציה). שאר הבקשה שומר את ה-timeout הרגיל.

המחיר של סגירה, אם בדיקה נשברת:

- `agent_wa_2fa` או `auth.mfa_factors` (בדיקת ההרשמה), וגם
  `agency_members` בבדיקת התפקיד - השגיאה נספרת כ"אולי בטווח". כל מי
  שאינו `aal2` ובלי session מאומת הופך/ת לאורח/ת עד האימות. מנהל/ת בלי
  נייד ננעל/ת בלי מוצא.
- `wa_login_verifications` - בדיקת ה-session נחשבת "לא מאומת". מי שבטווח
  (או שההיקף לא ודאי) יורד/ת לאורח/ת, ולא יכול/ה להשלים אימות.
- עד כארבעה בלוקי `exception` קטנים לבקשה. לא נמדד בעומס.

המוצא באירוע הוא מתג ה-break-glass למטה, לא פתיחה שקטה.

## נייד שהוחלף, או טלפון שאבד

אצל מי שהפעיל/ה, ההודעה חייבת להגיע מהנייד שבכרטיס, ואת הכרטיס אי אפשר
לערוך לפני האימות. התמיכה מאמתת את הזהות ומעדכנת את `agency_members.phone`,
או מוחקת את השורה של המשתמש/ת ב-`agent_wa_2fa`. שניהם במיגרציה או
בפעולת תמיכה מתועדת, לא ב-DDL. אפליקציה בטלפון שאבד: Supabase Dashboard
← Authentication ← Users ← המשתמש/ת ← מחיקת ה-factor. מי שהפעיל/ה את
שתי הדרכים פשוט נכנס/ת בשנייה.

## מה עוד לא מכוסה

- **הבוט של הסוכן/ת בוואטסאפ (גבריאלה) וקליטת המייל** מזהים לפי מספר
  טלפון או שולח מאומת, ולא לפי סיסמה. אימות הכניסה אינו חל עליהם.
- **Realtime** אינו עובר ב-pre-request, אבל אינו בשימוש. מי שמוסיף/ה
  `channel()` על טבלה פרטית צריך/ה policy מגבילה כמו זו של Storage.
- **חובה לכל סוכני המשרד** (הגדרה של מנהל/ת המשרד) עוד לא קיימת. המקום
  להוסיף אותה הוא `_mfa_role_required()`: ה-pre-request קורא לה דרך
  `_mfa_role_required_self`, ו-`_mfa_pending_self()` (מתג החירום) קוראת
  לה גם היא. את אותו תנאי צריך לשקף גם ב-`mfa_status()`, שמחשבת
  `required` בעצמה.

## ביטול חירום

**מתג break-glass**, `public._mfa_break_glass()`. כבוי כברירת מחדל
(`select false`). רק הבעלים מגדיר/ה אותו מחדש; `authenticated` יכול/ה
רק להריץ. כשהוא דלוק, ה-pre-request חוזר להתנהגות הישנה (פתוח בכשל,
דרך `_mfa_pending_self()`), מהבקשה הבאה, בלי `reload`. מתג GUC
(`alter role authenticator set shuk.mfa_fail_open`) נבדק ב-27.10.2026
ואינו עובד ב-Supabase: postgres אינו superuser, ו-supautils מתיר רק
`pgrst.*` וכדומה (‏42501).

הדלקה, ב-SQL editor כ-postgres. זו החלפת גוף של פונקציה קיימת, לא
`apply_migration` ולא שורה ב-`schema_migrations`:

```sql
create or replace function public._mfa_break_glass() returns boolean
  language sql stable set search_path = '' as $f$ select true $f$;
```

כיבוי, אותו משפט עם `select false`. אחרי האירוע מכבים: מתג דלוק מחזיר
את החולשה שהמיגרציה סגרה.

**כיבוי מלא של ה-hook**, אם גם המתג אינו מספיק. מיגרציה חדשה, לא דרך
הדשבורד (`CLAUDE.md`, "אין להחיל DDL מחוץ לצינור"):

```sql
alter role authenticator reset pgrst.db_pre_request;
notify pgrst, 'reload config';
```
