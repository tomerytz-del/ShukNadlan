# תכנית: מנוע מדיה (ffmpeg) - Reels, חיתוך קליפים, תמונת פתיחה ודחיסה

**סטטוס: תכנית, טרם מומשה.** המסמך מתאר את הארכיטקטורה ואת סדר העבודה.
מי שמממש/ת שלב מעדכן/ת כאן ובמסמך של היכולת (`property-marketing-video.md`,
`facebook-auto-publish.md`) באותו PR.

## למה בכלל צריך מנוע משלנו

היום כל עיבוד הווידאו רץ אצל fal.ai, כי ל-Edge Function של Deno אין ffmpeg
(`_shared/property-video.ts`). שלושה דברים חסרים בגלל זה:

| מה חסר | הסיבה |
| --- | --- |
| **Reels** לאינסטגרם ולפייסבוק עם מחיר ולוגו | ל-fal אין שכבת טקסט או לוגו. הפרסום היום הוא תמונות בלבד |
| **סצנות קצרות מ-5 שניות** בסרטון השיווקי | נמדד: fal אינו יודע לחתוך (`property-marketing-video.md`, "אורך הסצנה") |
| **תמונת פתיחה ודחיסה** לסרטונים באתר | אין עמודת poster. הסרטון שוקל עד 50MB, ו-`property.js` משתמש בתמונה הראשונה בגלריה כ-poster |

שלושתם אותו כלי: מכונה עם ffmpeg ודפדפן. לכן זו תשתית אחת ולא שלוש.
התבניות שהיא מרנדרת ישמשו בהמשך גם לקמפיינים, למודעות ממומנות ולתמונות
סטטיות.

## החלטה 1: הטקסט נבנה ב-HTML ולא ב-`drawtext`

**נבדק בפועל, לא הונח.** ffmpeg של אובונטו נבנה עם `libfribidi` ו-`libharfbuzz`,
ובאמת מצייר עברית עם אותיות תקינות. אבל שורה שמערבבת עברית ומספרים יוצאת
**בסדר הפוך**: `4 חד׳ · ₪2,450,000` רונדרה כ-`חד' · 2,450,000₪ 4`, כלומר ה-4
קפץ לקצה השמאלי. זו בדיוק שורת המפרט שכל Reel נושא. ffmpeg לא מדווח על שום
שגיאה במקרה הזה.

אותה שורה כדף HTML עם `dir="rtl"`, שצולם ב-Chromium headless לרקע שקוף
והולבש על הווידאו ב-`overlay`, יצאה נכונה: `4 חד׳ · 110 מ״ר · קומה 3`.

לכן:

- **כל שכבה גרפית היא דף HTML** ב-`media/templates/`: מחיר, מפרט, לוגו, כרטיס
  סיום. Chromium מצלם אותה ל-PNG שקוף, ו-ffmpeg רק מרכיב.
- **הגופן נשמר בריפו** (Heebo, רישיון OFL) ב-`media/fonts/`, ולא נטען מ-Google
  Fonts. כך הרינדור לא תלוי ברשת, ומה שנבדק הוא מה שיוצא.
- **הלוגו הוא `assets/logo-shuknadlan.png`** (512x610) ולא ה-SVG: ב-SVG האות
  "ש" כתובה כ-`<text>` ב-Heebo, ובלי הגופן היא יוצאת בגופן חלופי.
- **התבניות הן טקסט שמוצג לגולשים**, ולכן `check_long_dash.py` חייב לסרוק את
  `media/templates/` (להוסיף לרשימה שלו בשלב 0).

## החלטה 2: המחרוזות נבנות בשרת, והמנוע רק מסדר אותן

עיצוב המחיר כבר קיים ב-`_shared/marketing-copy.ts`: `nis()` ו-`priceLine`
יודעים להוסיף "לחודש" בשכירות ו-"+ מע״מ" בנכס מסחרי. עותק בפייתון במנוע היה
מתפצל מהם, ו-Reel היה מציג מחיר אחר מהפוסט שעולה לצדו.

לכן ה-Edge Function שפותחת את הבקשה מחשבת את כל השורות, מעבירה אותן ב-
`noLongDash()`, ושומרת אותן ב-`input` של הבקשה. המנוע לא יודע מה זה מחיר.

## החלטה 3: איפה ffmpeg רץ

| אפשרות | בעד | נגד |
| --- | --- | --- |
| **GitHub Actions** (`workflow_dispatch` מ-Supabase) | אין תשתית חדשה. ffmpeg ו-Chromium כבר על ה-runner, והמנועים האחרים כבר רצים שם | 30-60 שניות עלייה לכל ריצה, ומכסת דקות אם הריפו פרטי |
| Cloud Run / Fly.io עם קונטיינר | עלייה מהירה, אין מכסת דקות | שירות חדש לתחזק, לנטר ולשלם עליו |
| ffmpeg.wasm בדפדפן של הסוכן/ת | אפס שרת | כ-30MB הורדה, איטי מאוד בטלפון, ולא מתאים לפרסום אוטומטי |
| שירות רינדור (Creatomate, Shotstack) | תבניות מוכנות | תשלום לכל רינדור, ותמיכה ב-RTL שצריך לבדוק |

**ההמלצה: GitHub Actions בשלב הראשון**, מאחורי ממשק שלא תלוי בו: טבלת בקשות
ו-callback. כשהנפח יצדיק, מעבירים לקונטיינר בלי לגעת במי שקורא. הפקת סרטון
כבר לוקחת דקות, ולכן חצי דקה של עלייה לא מורגשת.

## הארכיטקטורה

```
CRM / בוט / cron ─> media-render-create (Edge)
                     │  זכאות, חישוב המחרוזות, שורה ב-media_renders + webhook_token
                     └─> POST workflow_dispatch ל-GitHub (טוקן עם actions:write בלבד)

GitHub Actions (media_render.yml)
   │  מוריד קלט, Chromium מצלם את התבניות, ffmpeg מרכיב, ffprobe מאמת
   └─> POST media-render-callback?job=&token=   (העלאה ל-Storage דרך URL חתום)

media-render-callback (Edge, verify_jwt = false)
   └─> complete/fail, התראה, והפעולה הבאה (פרסום, החלפת video_url)

pg_cron כל 5 דקות, רק כשיש בקשה פתוחה ─> reconcile של בקשות תקועות
```

שלוש החלטות שמועתקות מהסרטון השיווקי, כי כבר שילמנו עליהן שם:

- **ל-runner אין `service_role`.** הוא מקבל URL העלאה חתום ו-`webhook_token`
  לבקשה אחת. ריפו שדולף לא פותח את המסד.
- **ה-reconcile חובה.** ריצה של Actions יכולה ליפול בלי לקרוא ל-callback.
  בקשה בתשלום שנתקעת מזכה את הארנק, בדיוק כמו ב-`fail_property_video_job`.
- **בקשה פתוחה אחת לכל נכס ולכל סוג** (אינדקס ייחודי), כדי שלחיצה כפולה לא
  תפיק פעמיים.

### הטבלה `media_renders`

| עמודה | מה |
| --- | --- |
| `kind` | `poster`, `compress`, `reel`, `merge` (ובהמשך `campaign`) |
| `property_id`, `agent_id` | |
| `status` | `queued`, `rendering`, `done`, `failed` |
| `input` jsonb | כתובות מקור, המחרוזות המוכנות, תבנית, יחס מסך |
| `output_url`, `output_meta` jsonb | הקובץ, ומה ש-ffprobe מדד: אורך, ממדים, משקל |
| `fingerprint` | ל-Reel: md5 של מה שמוצג בו (ראו "Reel מתיישן") |
| `webhook_token`, `attempts`, `last_error`, חותמות זמן | |

כל זה במיגרציה (`new-migration`). הפונקציות החדשות דרך `new-edge-function`,
כולל `verify_jwt = false` ל-callback ב-`config.toml`.

## שלבי העבודה

### שלב 0 - התשתית, עם המשימה הפשוטה ביותר

הטבלה, `media-render-create`, `media-render-callback`, `media_render.yml`,
ה-reconcile, והסוד `GITHUB_DISPATCH_TOKEN` ב-Supabase. **משימה ראשונה: `poster`**
(פריים אחד מהסרטון), כי היא מוכיחה את כל הצינור כמעט בלי סיכון.

בדיקה ב-CI: רינדור של קלט לדוגמה ובדיקה ב-ffprobe של ממדים, אורך ומשקל.

### שלב 1 - תמונת פתיחה ודחיסה לסרטונים באתר (כלי 3)

- **עמודה `properties.video_poster_url`**. ‏`property-card.js` ו-`property.js`
  משתמשים בה כ-`poster`, ונופלים לתמונה הראשונה כשאין.
- **דחיסה ו-`faststart`.** קידוד מחדש ל-H.264, ‏720p לאתר, ‏`-movflags +faststart`.
  בלי `faststart` הדפדפן צריך את סוף הקובץ לפני שהוא מתחיל לנגן. סרטון שהסוכן/ת
  העלה/תה, או שהתקבל מ-fal, עובר את זה אוטומטית אחרי השמירה.
- **ההחלפה בטוחה רק אחרי אימות.** הקובץ החדש מחליף את הישן רק אם האורך שלו
  זהה (`measureMp4Seconds` כבר קיים). הישן נמחק אחרון, כמו ב-`previous_video_url`.
- **מילוי למפרע** לסרטונים הקיימים, בקצב נמוך.
- **כמה זה חוסך נמדד ולא מוערך** (`perf-measure`): משקל לפני ואחרי, וזמן
  עד הפריים הראשון באריח ובדף הנכס.

### שלב 2 - Reel עם מחיר ולוגו

**המבנה** (1080x1920, ‏30fps, ‏15-30 שניות):

| זמן | מה בתמונה |
| --- | --- |
| 0-2 שנ' | השוט הראשון, עם **המחיר והעיר כבר במסך**. ב-Reels מחליטים בשנייה הראשונה, ולכן אין פתיח של לוגו |
| לאורך כל הסרטון | לוגו קטן בפינה, ושורת מפרט (חדרים, מ"ר, קומה) |
| 2-3 שנ' אחרונות | כרטיס סיום: לוגו, הקישור הקצר (`shuknadlan.co.il/p/1162`), שם הסוכן/ת והמשרד |

**המקור:**

- **יש `video_url`** (סרטון שיווקי או שהועלה): הוא הבסיס. אם הוא 16:9, הוא
  מוצב על רקע מטושטש של עצמו במקום חיתוך לרוחב, כדי שלא ייחתכו חלקים מהנכס.
- **אין סרטון:** מצגת עם תנועה איטית (`zoompan`) על 5-6 תמונות, בסדר של
  `pickScenes()`. **זה נותן Reel לכל נכס בלי עלות של fal**, וזה הרווח הגדול
  של השלב.

**אזורים בטוחים:** הממשק של אינסטגרם מכסה כ-14% עליונים וכ-20% תחתונים. המחיר
והמפרט יושבים ברצועה שביניהם, והתבנית מגדירה אותה פעם אחת.

**Reel מתיישן.** המחיר צרוב בתמונה, ולכן **ה-Reel לעולם לא נכתב ל-`video_url`**:
כשהמחיר יורד, דף הנכס היה ממשיך להציג את הישן. הוא קובץ נפרד ב-`media_renders`,
עם טביעת אצבע של מחיר, סוג עסקה, חדרים, שטח, קומה ועיר (כמו
`property_marketing_fingerprint()`). Reel שהטביעה שלו לא תואמת אינו מתפרסם,
ומרונדר מחדש לפני כן.

**איפה זה לא נכנס:** במיניסייט ללקוח/ה (`client-showcase`) הנכסים חייבים להיות
בלי מיתוג, ולכן Reel ממותג לא נשלח לשם לעולם.

**ב-CRM:** כפתור "Reel לאינסטגרם" בכרטיס הנכס, עם תצוגה מקדימה והורדה, כדי
שסוכנים יעלו גם לחשבונות של עצמם.

### שלב 3 - פרסום אוטומטי של Reels

- **ערוצים חדשים `instagram_reel` ו-`facebook_reel`** ב-`property_publications`
  (מיגרציה שמרחיבה את ה-check). ערוץ נפרד ולא שינוי של `instagram`, כי
  `unique(property_id, channel)` היה מונע Reel מכל נכס שכבר קיבל פוסט תמונות.
- **אינסטגרם ב-Graph:** `media_type=REELS` עם `video_url` ו-`cover_url`. העיבוד
  אצל מטא לוקח דקות, ולכן ההמתנה של 30 שניות שקיימת היום לא מספיקה. הפרסום
  מתפצל לשני סבבי cron: יצירת container, ובסבב הבא בדיקת `FINISHED` ופרסום.
  מזהה ה-container נשמר על השורה.
- **Make:** ענף חדש בכל תרחיש לפי `media_type`, ו-`video_url` בגוף הבקשה.
- **כל כללי הכפילות נשארים:** `claim_property_publication`, ‏`[make-unconfirmed]`
  בלי ניסיון חוזר, והקפאה לפני חקירה (`social-publish`).
- תקרה יומית נפרדת לערוצי ה-Reel.

### שלב 4 - חיתוך בסרטון השיווקי (כלי 1)

המיזוג עובר מ-`fal-ai/ffmpeg-api/merge-videos` למנוע: כל קליף של Kling נחתך
ל-`clip_seconds` (למשל 3 שניות מתוך 5), ובין הקליפים יש מעבר רך. כך
`clip_seconds` יכול סוף סוף להיות קטן מ-`source_seconds`, והסרטון קצבי יותר
**באותה עלות**, כי fal גובה לפי קליף ולא לפי שנייה.

המעבר נעשה מאחורי משתנה `MERGE_ENGINE=fal|worker`, כדי שאפשר יהיה לחזור בלי
פריסה. כישלון של המנוע עובר דרך `fail_property_video_job`, כלומר הסוכן/ת מקבל/ת
החזר כמו היום. הסעיף "⛔ אורך הסצנה" ב-`property-marketing-video.md` מתעדכן.

### שלב 5 - קמפיינים

אותן תבניות ואותו מנוע, עם קלט אחר:

- "חדש השבוע בעפולה": Reel של כמה נכסים מאותו שוק.
- Reel ממותג במשרד (`agencies.logo_url`, `agencies.colors`) לחשבונות של הסוכנים.
- **תמונות סטטיות** למודעות ממומנות ולסטורי: אותו צילום Chromium, בלי ffmpeg.
- גרסאות 1:1 ו-4:5 לפיד.

## החלטות שמחכות לך

1. **מוזיקה.** Reel שקט מקבל פחות חשיפה, אבל ה-API לא יכול להוסיף את המוזיקה
   של אינסטגרם. האפשרויות: בלי מוזיקה, או ספרייה קטנה של רצועות ברישיון חופשי
   בריפו.
2. **מי משלם.** Reel מתמונות כמעט לא עולה כסף. האם הוא פתוח לכל המסלולים, או
   יכולת במסלול (`new-tier-capability`)?
3. **מיתוג בחשבון שלנו.** ההנחה כאן: לוגו שוק נדל״ן בלבד, ושם הסוכן/ת והמשרד
   בכרטיס הסיום. לוגו של משרד רק בגרסה שהסוכן/ת מוריד/ה לעצמו/ה.
4. **הריפו פרטי?** אם כן, צריך לבדוק את מכסת הדקות של Actions. הערכה גסה: Reel
   הוא 1-2 דקות ריצה.
