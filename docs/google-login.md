# כניסה ל-CRM עם Google

הכניסה לאיזור הסוכנים (`crm.html`) נעשית בשתי דרכים — אימייל וסיסמה, או
Google OAuth דרך Supabase Auth. המסמך הזה מתאר את מסלול ה-Google: מה קורה בכל
שלב, איפה הוא נשבר בעבר, ומה חייב להיות מוגדר בצד Supabase ו-Google כדי שהוא
יעבוד.

## המסלול המלא

1. הסוכן/ת לוחצ/ת על "התחברות עם Google" ב-`crm.html`.
2. `sb.auth.signInWithOAuth({ provider:'google', options:{ redirectTo } })`
   מנתב את הדפדפן ל-Google. הכפתור ננעל ומציג "מעבירים ל-Google…" — כדי
   שלחיצה שנייה לא תפתח ניתוב מקביל.
3. Google מחזיר את הדפדפן לכתובת שב-`redirectTo`, עם התשובה בכתובת עצמה:
   `#access_token=…` בהצלחה (flow מסוג implicit) או `?code=…` (PKCE), ובכישלון
   `error` / `error_description`.
4. `supabase-js` קורא את התשובה מהכתובת בזמן האתחול שלו, שומר את ה-session,
   ומשדר `INITIAL_SESSION` ואחריו `SIGNED_IN`.
5. `routeAfterAuth()` ב-`crm.html` מנקה את התשובה מהכתובת, מציג מסך המתנה,
   ומחליט לאן להמשיך:

| מצב | מסך |
| --- | --- |
| יש שורת `agency_members` לחשבון | הדשבורד |
| אין שורה (חשבון Google חדש) | "פתיחת משרד" (`#createAgencyScreen`) |
| השאילתה נכשלה | "לא הצלחנו לטעון את החשבון" + כפתור נסיון נוסף |
| חזרה עם שגיאה מ-Google | מסך הכניסה, עם הסבר מה קרה |

## מה נשבר קודם ולמה

התלונה הייתה שהכניסה "קופצת" — מסכים שמופיעים ונעלמים, וחזרה פתאומית לטופס
הסיסמה. אלה היו הסיבות, וכולן תוקנו ב-`crm.html`:

**‏1. טופס הסיסמה נצבע ראשון בכל טעינה.** ל-`#loginScreen` לא הייתה
`display:none`, אז הדפדפן צייר את כרטיס הכניסה מיד — לפני שבדיקת ה-session
(שהיא אסינכרונית) הספיקה לרוץ. גם מי שכבר היה מחובר, וגם מי שחזר/ה מ-Google,
ראו הבזק של טופס הסיסמה לפני הדשבורד. היום המסך הראשון הוא כרטיס המתנה
(`#bootCard`), וטופס הסיסמה מוצג רק כשידוע שאין חיבור פעיל.

**‏2. שני ניתובים במקביל על אותה כניסה.** גם `onAuthStateChange` וגם `boot()`
קראו ל-`routeAfterAuth()`, ושתי טעינות דשבורד רצו זו על זו וציירו את המסך
פעמיים. היום `routeAfterAuth()` שומר את ההבטחה של הניתוב הרץ, וקריאה נוספת
מצטרפת אליו.

**‏3. ‏`SIGNED_IN` חוזר גם בלי התחברות.** ‏`supabase-js` משדר אותו מחדש בחזרה
ללשונית ובחידוש אסימון. כל חזרה ללשונית טענה מחדש את כל הדשבורד באמצע העבודה.
היום `routedUserId` מסמן מי כבר מוצג/ת, ואירוע חוזר על אותו משתמש נבלע.

**‏4. ‏`await` של supabase בתוך ה-callback של `onAuthStateChange`.** ה-callback
רץ בתוך הנעילה הפנימית של הלקוח, וקריאה כזו מתוכו עלולה לתקוע את הדף. היום
העבודה נדחית ב-`setTimeout(0)` וה-callback מסתיים מיד.

**‏5. תשובת Google נשארה בכתובת.** ה-`#access_token` נשאר בשורת הכתובת
ובהיסטוריה, ורענון או "חזור" ניסו לעבד שוב תשובה שכבר נוצלה. היום
`cleanAuthParamsFromUrl()` מוריד אותה מיד אחרי שה-session בידינו.

**‏6. חזרה עם שגיאה מ-Google לא הוסברה.** הסוכן/ת פשוט מצא/ה את עצמו/ה מול
טופס הסיסמה. היום `error_description` נקרא מהכתובת ומוצג במסך הכניסה, עם
ניסוח נפרד לביטול (`access_denied`).

**‏7. חריגה בטעינת הדשבורד החזירה למסך הכניסה.** ה-`try/catch` של `boot()`
עטף גם את הניתוב, אז כל תקלה בבניית המסך — אחרי שההתחברות כבר הצליחה — נראתה
כמו "אינך מחובר/ת". היום ה-`try` עוטף רק את בדיקת ה-session; תקלה בטעינה
מגיעה למסך השגיאה עם כפתור נסיון נוסף, ואם הדשבורד כבר מוצג היא רק מעלה
הודעת toast ולא מוחקת אותו.

**‏8. סיבוב רשת מיותר לפני כל מסך.** `routeAfterAuth()` קרא ל-`getUser()`
(קריאת רשת) ואז שאל את `agency_members`, ו-`loadDashboard()` חזר על שניהם.
היום ה-user מגיע מה-session שכבר בידינו, ו-`agency_members` נשאל פעם אחת.

## מה חייב להיות מוגדר מחוץ לקוד

חלק מהתקלות במסלול הזה לא נמצאות ב-`crm.html` אלא בהגדרות, ולכן כדאי לוודא
אותן כשמשהו מתנהג מוזר:

**Supabase → Authentication → URL Configuration**

- **Site URL** — כתובת הבסיס של האתר. אליה Supabase מנתב כשה-`redirectTo`
  שהתבקש **לא** נמצא ברשימה המותרת. זה ההסבר הקלאסי ל"פתאום נחתתי בדף הבית"
  אחרי כניסה עם Google.
- **Redirect URLs** — חייבת להכיל את הכתובת המלאה של ה-CRM, למשל
  `https://<הדומיין>/crm.html`. הקוד שולח `origin + pathname` בלי query
  בכוונה, כדי שהכתובת תהיה זהה בדיוק לזו שברשימה. אם עובדים גם מקומית, יש
  להוסיף גם את כתובת הפיתוח (`http://localhost:<port>/crm.html`).

**Supabase → Authentication → Providers → Google**

- הספק מופעל, עם ה-Client ID וה-Client Secret מ-Google Cloud.

**Google Cloud → APIs & Services → Credentials → OAuth client**

- **Authorized redirect URI** חייב להיות ה-callback של Supabase עצמו:
  `https://obookujgolazrwycsiyn.supabase.co/auth/v1/callback` — לא כתובת
  האתר. Supabase הוא זה שמקבל את התשובה מ-Google ורק אחר כך מנתב ל-`crm.html`.
- מסך ההסכמה (OAuth consent screen) מפורסם. כל עוד הוא ב-Testing, רק חשבונות
  שנוספו ידנית כ-Test users יצליחו להיכנס; השאר יקבלו `access_denied` —
  שנראה בדיוק כמו "ההתחברות בוטלה".

## חשבון Google שנכנס בפעם הראשונה

התחברות עם Google יוצרת משתמש ב-`auth.users`, אבל **לא** שורה ב-
`agency_members`. חשבון בלי שורה כזו **אינו** נשלח עוד ישירות למסך "פתיחת
משרד": קודם רץ זיהוי (`join-agency`) שמנסה אסימון הזמנה, ואז התאמת אימייל מול
כרטיס ממתין. ראו `docs/agent-invitations.md`.

רק אם שניהם לא תפסו מוצג מסך **"מי את/ה?"**, ובו שתי אפשרויות: חיבור לכרטיס
קיים לפי מספר רישיון (באישור מנהל/ת המשרד), או פתיחת משרד חדש.

זה בדיוק המקרה שבו כתובת ה-Google שונה מהכתובת שעל שורת ה-`agency_members` —
עד היום הוא הוביל למסך "פתיחת משרד" ולמשרד כפול מיותר, ועכשיו הוא נפתר בתוך
הממשק בלי לגעת במסד.
