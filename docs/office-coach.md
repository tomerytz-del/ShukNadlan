# מאמן ה-AI השבועי ("סיכום השבוע")

פעם בשבוע, ביום ראשון בבוקר, כל מנהל/ת משרד מקבל/ת בדאשבורד המשרד כרטיס
"סיכום השבוע": כותרת אחת ושלוש נקודות על השבוע שהסתיים. מה עבד, מה תקוע,
ועל מה לשים את השבוע הזה ומי מוביל/ה את זה.

ההמלצות הקבועות בדאשבורד (`buildOfficeAdvice`) הן כללים: הן נדלקות לפי
ספים. המאמן קורא את כל המספרים יחד, משווה לשבוע הקודם ולנקודות שכתב אז,
ובוחר מה הכי חשוב השבוע. הדאשבורד עצמו: [`office-dashboard.md`](office-dashboard.md).

## איך זה בנוי

| חלק | איפה |
| --- | --- |
| המיגרציה | `supabase/migrations/20270407090000_office_coach.sql` |
| הפונקציה | `supabase/functions/office-coach/index.ts` |
| מה יוצא למודל ומה נשמר | `supabase/functions/office-coach/payload.ts` |
| הבדיקה | `scripts/office_coach_test.ts` (רצה ב-CI, ב-`edge_types.yml`) |
| הכרטיס | `odCoachHtml()` ב-`assets/crm-office-dashboard.js` |

1. **pg_cron** (`office-coach`, ‏`10 5-9 * * 0` ב-UTC, כלומר ביום ראשון
   מ-8:10 עד 12:10 בשעון קיץ, ושעה מוקדם יותר בחורף) קורא לפונקציה, ורק כשיש משרד שעוד מחכה
   (`office_coach_due(1)`). חמש הרצות ולא אחת: Edge Function נעצרת אחרי
   150 שניות, והמשרדים שלא הספקנו נלקחים בשעה הבאה.
2. **`office_coach_due()`** מחזירה משרדים שיש בהם מנהל/ת פעיל/ה, שהייתה
   בהם תנועה ב-30 הימים האחרונים (ליד חדש או נכס שעודכן), ושעוד אין להם
   סיכום לשבוע הזה. משרד שלא זז חודש לא מקבל סיכום: אין מה לסכם, וכל קריאה
   עולה כסף.
3. **לכל משרד** הפונקציה מחשבת את המספרים דרך `_office_dashboard_core` פעמיים:
   לשבוע שהסתיים (ראשון עד שבת) ול-30 הימים האחרונים. זו אותה פונקציה שמזינה
   את הדאשבורד, ולכן המאמן מדבר על המספרים שהמנהל/ת רואה/ה. מצטרפות גם
   הנקודות של הסיכום הקודם, כדי שלא יחזור על עצמו.
4. **Claude** מחזיר JSON לפי סכמה (`SUMMARY_SCHEMA`). ‏`cleanSummary()` מחליפה
   מקף ארוך, חותכת לשלוש נקודות ולאורך סביר, וזורקת תשובה ריקה או שבורה.
5. **השמירה** ב-`office_coach_summaries`, שורה אחת למשרד לשבוע
   (`unique (agency_id, week_start)`), עם המודל ומספר הטוקנים.

`week_start` הוא יום ראשון של השבוע שבו הסיכום נכתב, בשעון ישראל
(`office_coach_week_start()`). הסיכום עצמו מכסה את שבעת הימים שלפניו.

### ‏`_office_dashboard_core` ו-`office_dashboard`

הגוף של `office_dashboard()` עבר ל-`_office_dashboard_core(p_agency, p_from,
p_to)`, שמקבלת משרד ואינה בודקת תפקיד. היא `security invoker` ופתוחה ל-
`service_role` בלבד. ‏`office_dashboard()` נשארה בדיוק עם אותה חתימה: היא
בודקת שהקורא/ת מנהל/ת (‏42501 אחרת) וקוראת לליבה עם המשרד של הקורא/ת. כך
אין עותק שני של החישוב, והמאמן לא יכול לסטות מהדאשבורד.

## פרטיות: מה יוצא למודל

**אגרגטים ושמות סוכנים בלבד.** ‏`compactPeriod()` בונה את מה שנשלח מרשימה
סגורה של מדדים (`keep`), ולכן שדה חדש שיתווסף ל-`office_dashboard` מחר לא
יוצא למודל מעצמו.

| יוצא | לא יוצא |
| --- | --- |
| שם הסוכן/ת ותפקיד | אימייל, טלפון ותמונה של הסוכן/ת |
| לידים, זמני תגובה, גיוסים, בלעדיות, הסכמים, פגישות, עסקאות, עמלות (הערכה), יעד | שם, טלפון או טקסט של פונה או לקוח/ה |
| בלעדיות שפוקעת: תאריך, ימים בשוק, הצגות, מחיר | כותרת הנכס, כתובת ומזהה |
| מקורות לידים | מזהי סוכנים, לידים ונכסים |

`scripts/office_coach_test.ts` בודקת בדיוק את זה, על נתונים שמכילים את כל
השדות האסורים. מי שמוסיף/ה מדד ל-`keep` בודק/ת שהוא מספר ולא טקסט.

**מי קורא/ת את הסיכום:** ‏RLS על `office_coach_summaries` מתיר `select` רק
למנהל/ת של אותו משרד. אין הרשאת כתיבה ל-`authenticated` בכלל. הסיכום כותב
שמות של סוכנים, ולכן הוא לא מוצג לסוכנים בדשבורד האישי שלהם.

## עלות

קריאה אחת למשרד בשבוע. הפרומפט נשמר במטמון בין המשרדים של אותה הרצה,
והנתונים של משרד הם כמה אלפי טוקנים. ההערכה היא סנטים בודדים למשרד בשבוע.
**את העלות האמיתית קוראים מהטבלה**, שבה נשמרים `input_tokens` ו-
`output_tokens` לכל סיכום:

```sql
select week_start, count(*), sum(input_tokens), sum(output_tokens)
  from office_coach_summaries group by 1 order by 1 desc;
```

המודל נקבע בסוד `OFFICE_COACH_MODEL` (ברירת המחדל `claude-opus-5-5`). מודל
קטן יותר יחסוך, ומה שמתקבל הוא ניסוח פחות חד. זו החלטת איכות ועלות, ולכן
היא סוד ולא קבוע בקוד.

**גיבוי בשרת:** הקריאה מבקשת `fallbacks: "default"`. אם המודל מסרב (סיווג
בטיחות שגוי על נתוני מכירות), השרת מעביר באותה קריאה למודל הגיבוי, במקום
שהמשרד יישאר בלי סיכום. סירוב של כל השרשרת מדלג על המשרד השבוע.

## הכרטיס בדאשבורד

`loadOfficeCoach()` נטענת פעם אחת, במקביל לדאשבורד ובלי לעכב אותו, ומביאה
את הסיכום האחרון (RLS מחזיר רק את המשרד של המנהל/ת). הכרטיס יושב מתחת
לשישה המדדים ואינו תלוי בתקופה שנבחרה.

- **אין עדיין סיכום:** "הסיכום הראשון יגיע ביום ראשון בבוקר".
- **הטעינה נכשלה** (למשל לפני שהמיגרציה רצה): הכרטיס לא מוצג, והדאשבורד
  עובד כרגיל.
- **יש סיכום:** הכותרת, שלוש נקודות עם "מוביל/ה", והשבוע שהסיכום מכסה.
  ליד השבוע כתוב שהסיכום נכתב אוטומטית ושכדאי לבדוק לפני שפועלים.

## הרצה ידנית

הפונקציה מקבלת את הסוד של pg_cron (`x-alert-cron-secret`) או מפתח
`service_role` (`_shared/cron-auth.ts`, נכשלת סגור).

```sh
# ניסיון בלי לשמור, למשרד אחד
curl -X POST "https://obookujgolazrwycsiyn.supabase.co/functions/v1/office-coach?dry_run=1&agency=<uuid>" \
  -H "Authorization: Bearer $SERVICE_ROLE_KEY"
```

- `?dry_run=1`: מחשב ומחזיר את הסיכום, בלי לשמור.
- `?agency=<uuid>`: משרד אחד בלבד, גם אם אינו ברשימת ה-due (למשל משרד שכבר
  קיבל סיכום השבוע). בלי `dry_run` הסיכום נשמר ומחליף את הקיים של השבוע.

## תקלות אפשריות

| מה רואים | למה |
| --- | --- |
| הכרטיס לא מופיע בכלל | הטעינה מ-`office_coach_summaries` נכשלה. לרוב: המיגרציה טרם רצה. |
| "הסיכום הראשון יגיע ביום ראשון" אחרי יום ראשון | המשרד לא עבר את `office_coach_due`: אין מנהל/ת פעיל/ה, או שלא הייתה תנועה ב-30 יום. או שהקריאה נכשלה - התשובה של הפונקציה מפרטת `error` לכל משרד, וגם יומן הפונקציה (`office-coach failed`). |
| `anthropic_not_configured` (‏503) | חסר הסוד `ANTHROPIC_API_KEY` בפונקציות. |
| `error: refusal` | כל שרשרת המודלים סירבה. המשרד ידולג השבוע; אפשר להריץ ידנית עם `?agency=`. |
| `error: rate_limited` | עומס ב-API. ההרצה בשעה הבאה תיקח את המשרד שוב. |
| `error: empty_summary` / `bad_json` | התשובה לא עברה את `cleanSummary`. לא נשמר כלום; ההרצה הבאה תנסה שוב. |
| pg_cron לא קורא לפונקציה | חסר הסוד `alert_cron_secret` ב-vault, או ש-pg_cron אינו מותקן. המיגרציה מדפיסה הודעה במקרה השני. |
| מספר בסיכום שונה מהדאשבורד | הסיכום מכסה את השבוע שהסתיים (ראשון עד שבת), והדאשבורד את התקופה שנבחרה בבורר. |
