# רישום זמנים לתור של גבריאלה

**למה:** בדוח האבחון p90 של זמן התגובה הוא 25-33 שניות, ו-17% מההודעות הקוליות מעל 30 שניות, בלי פירוק.
בלי לדעת אם הזמן הולך להמתנה לרצף, לתמלול, למודל או לכלים, קיצור הפרומפט (כ-55K טוקנים לקריאה)
הוא ניחוש.

## מה נרשם

שורה אחת לתור בטבלה `gabriela_turn_timings` (מיגרציה `20271201110000`), במילישניות:

| עמודה | מה היא מודדת |
| --- | --- |
| `wait_ms` | מהגעת ההודעה (בלי התמלול) עד תחילת התור: חלון איסוף הרצף ונעילת הסוכן/ת |
| `transcribe_ms` | הורדת ההקלטה מ-Meta ותמלול. רק בהודעה קולית או קובץ שמע |
| `prep_ms` | בתוך `runAgentTurn`, עד הקריאה הראשונה למודל: פרופיל, כלים והיסטוריה |
| `llm_ms`, `llm_calls` | סכום זמני המודל וכמות הקריאות |
| `tool_ms`, `tool_calls`, `tool_names` | סכום זמני הכלים, וכמה. שמות בלבד |
| `in_tokens`, `cache_read`, `cache_write`, `out_tokens` | סכום הטוקנים בתור |
| `send_ms` | שליחת התשובה |
| `total_ms` | מהגעת ההודעה עד שהתשובה יצאה |

`kind` הוא `text`, `voice`, `audio_file`, `image`, `document`, `button`, `email` או `other`; `outcome` הוא
`ok`, `error` או `aborted`.

**אין בטבלה תוכן הודעה, טלפון או טקסט.** מזהה הסוכן/ת בלבד. לכן הרישום דולק מההתחלה.

## איך קוראים

```sql
select * from gabriela_turn_timing_report;   -- 30 יום, לפי סוג תור: p50, p90, אחוז מעל 30 שניות, ופירוק
```

התצוגה סופרת רק `outcome = 'ok'`. תורים שנכשלו או נקטעו נשארים בטבלה לבדיקה ידנית.

## מגבלות

* `wait_ms` ו-`transcribe_ms` נשמרים בזיכרון של הפעלת הפונקציה (`setTurnClock`), לפי סוכן/ת. כשהתור רץ
  בהפעלה אחרת מזו שקלטה את ההודעה, או שעברו יותר מ-3 דקות, הם `null` ו-`kind` הוא `other`.
  `total_ms` נמדד אז מתחילת התור.
* רצף של כמה הודעות נמדד מהראשונה, והתמלול נצבר.
* **תור מייל** (`kind = 'email'`, `email-intake.ts`): `wait_ms` נמדד מתחילת הטיפול במייל (אחרי ה-claim) ולא משליחתו,
  כי ה-cron רץ כל שתי דקות. `transcribe_ms` הוא קריאת הקבצים המצורפים (PDF והקלטות). מייל שחזר מ-`lock_wait` מתחיל מדידה
  חדשה. תור מייל מסונן בכלים (`EMAIL_TOOLS`), ולכן אל תשוו אותו לתור וואטסאפ בלי לסנן לפי `kind`.
* `prep_ms` מחושב מזמן הקריאה הראשונה, ולכן כולל גם את שליחת הבקשה עד תחילת המדידה (זניח).

## כיבוי

`update pricing_config set value = 0 where key = 'gabriela_turn_timing_enabled'` עוצר כתיבה בתוך כמה דקות
(מטמון של חמש דקות לכל הפעלה), בלי דיפלוי. שמירה: 90 יום, `docs/data-retention.md`.

## שאלה חוזרת אחרי תשובה קצרה (`gabriela_reask_report`)

**למה:** ב-25.11.2026 נמצאו שלושה מקרים (שני סוכנים) שבהם הסוכן/ת ענה/תה ("עפולה", "2%") וגבריאלה שאלה שוב את אותה שאלה.
מקרה כזה אינו שגיאה, ולכן אי אפשר לתפוס אותו בלוג: הוא נראה רק בקריאת השיחה. התיקון (`answersLastQuestion`, #1426) הוא על
סימפטום, והשאלה אם הוא עזר נענית רק מספירה לאורך ימים.

```sql
select * from gabriela_reask_report;   -- לפי יום, 14 יום: תשובות קצרות לשאלה, כמה מהן קיבלו שוב את אותה שאלה, ואחוז
```

**איך נספר:** הודעה נכנסת של עד 20 תווים אחרי הודעה יוצאת עם סימן שאלה, כשהודעה יוצאת נוספת באה בתוך 40 שניות וחמש מילים
עבריות או יותר (3 אותיות ומעלה) חופפות בסופי שתי ההודעות היוצאות. **זו הערכה לפי חפיפת מילים:** היא עלולה לפספס ניסוח שונה
לגמרי ולספור שאלה דומה שנשאלה בכוונה, ולכן משתמשים בה למגמה ולא לספירה מדויקת. ספירות בלבד, בלי תוכן, טלפון או מזהה סוכן/ת.

**קו בסיס:** 25.11.2026 = 3 מתוך 15; 22-24.11 = 0 מתוך 17. אחרי התיקון הציפייה היא ירידה. ירידה לא מוכיחה שהתיקון עזר
(המדגם קטן), ועלייה היא סימן לבדוק את הנחיית המערכת (#1415).

## KPI שבועי (`gabriela_weekly_kpi`)

**למה:** האבחון של אוקטובר-נובמבר 2026 נמדד בשאילתות שאינן בריפו, ולכן כל השוואה בין שבועות נעשתה בהגדרה קצת אחרת.
ה-view קובע הגדרה אחת (מיגרציה `20271204110000`), ספירות בלבד, `service_role` בלבד. מנהלי/ות פלטפורמה מחוץ לכל העמודות.

```sql
select * from gabriela_weekly_kpi;   -- ראשון-שבת בשעון ישראל, 8 שבועות, השבוע הנוכחי חלקי
```

| עמודה | מה |
| --- | --- |
| `agents`, `inbound` | סוכנים שכתבו והודעות נכנסות, בלי מנהלי/ות פלטפורמה (כולל לחיצות כפתור) |
| `pushes`, `read_pct`, `failed_pct`, `fail_131049` | התראות שיצאו בוואטסאפ, קריאה וכשל מתוך אלה עם סטטוס מסירה, וכשלי 131049 |
| `agent_calls`, `agent_usd`, `unpriced_calls`, `usd_per_inbound` | קריאות בתורים (וואטסאפ ומייל) ועלות העוזרת לסוכנים (כולל חימום). התמחור כמו `ai_usage_costs` בפאנל "עלויות" (`docs/platform-costs.md`), אבל לפי שורה: `unpriced_calls` > 0 אומר שמודל חסר ב-`ai_model_prices` והעלות חלקית. מי שמשנה את התמחור שם משנה גם כאן |
| `prefix_tokens` | גודל הקידומת הקבועה (כלים + `SYSTEM_STATIC`) לפי קריאות החימום |
| `text_*`, `voice_*`, `pct_over_30s` | זמני תגובה מהטבלה למעלה (מ-24.11.2026) |
| `match_relevant`, `match_not_relevant` | משוב על התאמות מהוואטסאפ (`client_match_feedback`) |

**הקידומת היא רוב העלות:** ב-11.2026 היא כ-94% מכל קריאה (62K מתוך 66K טוקנים), וגדלה מ-39.7K (שבוע 18.10) ל-62K
(שבוע 22.11). הגדילה בין 6.11 ל-28.11 (כ-13.9K תווים) היא חמישה כלים חדשים (לידים, ייבוא לידים, דף המשרד),
הרחבה של `agenda_add`, `client_matches` ו-`agenda_update`, ועוד 4.8K תווים ב-`SYSTEM_STATIC`. כלי או הוראה חדשים
מגדילים את כל הקריאות, לא רק את אלה שמשתמשות בהם - ולכן `prefix_tokens` הוא העמודה לבדוק אחרי PR שמוסיף כלי.
