# התקנת האתר כאפליקציה (PWA)

האתר ניתן להתקנה: דפדפן יודע להניח אותו על מסך הבית של הטלפון עם אייקון
משלו, ולפתוח אותו במסך מלא בלי סרגלי הדפדפן. אין כאן חנות אפליקציות, אין
קובץ להוריד, ואין גרסה שצריך לעדכן — מה שמותקן הוא האתר עצמו, וכל מיזוג
ל-`main` מגיע אליו תוך שניות בדיוק כמו לדפדפן.

**הבעיה שהכפתור פותר:** כל זה היה קיים גם קודם, אבל הדרך אליו הוסתרה
בתפריט שלוש הנקודות של כרום — "התקנה ויצירת קיצור דרך". מי שקיבל/ה קישור
בוואטסאפ לא ידע/ה שהאפשרות שם, ובאייפון היא עוד יותר מוסתרת. עכשיו
ההצעה עולה בתוך הדף.

## מה יש בריפו

| קובץ | תפקיד |
| --- | --- |
| `manifest.webmanifest` | המניפסט של האתר הציבורי. נפתח על דף הבית |
| `app-crm.webmanifest` | המניפסט של האזור האישי. נפתח על `/crm` |
| `sw.js` | ‏Service Worker מינימלי, בלי מטמון. קיים כדי שכרום יאפשר התקנה |
| `assets/pwa-install.js` | הרצועה, ההסבר לאייפון, הרישום וה-API לדף |
| `assets/icon-192.png` ו-`icon-512.png` | אייקוני האפליקציה |
| `assets/icon-maskable-*.png` | אותו ציור עם שוליים, לחיתוך של אנדרואיד |
| `assets/apple-touch-icon.png` | אייקון מסך הבית של אייפון (180px) |
| `scripts/build_app_icons.py` | בונה את חמשת ה-PNG-ים מהגאומטריה של הלוגו |
| `scripts/check_pwa.py` | הבדיקה שרצה ב-CI |

## שלוש מציאויות, שלוש התנהגויות

### כרום, אדג' וסמסונג (אנדרואיד ומחשב) — התקנה אמיתית בלחיצה

הדפדפן יורה `beforeinstallprompt` כשהדף עומד בתנאי ההתקנה. הקובץ עוצר את
האירוע (`preventDefault`, אחרת כרום מציג באנר משלו), שומר אותו, ומציג את
הרצועה שלנו. לחיצה על "התקנה" מריצה `prompt()` — **אותו דיאלוג התקנה של
המערכת**, בלחיצה אחת מתוך הדף.

האירוע ניתן לצריכה **פעם אחת בלבד**. לכן הוא מתאפס אחרי `prompt()`,
ולחיצה שנייה לא תעשה דבר עד שהדפדפן ייתן אירוע חדש.

### אייפון ואייפד — הסבר, כי אין API

**אפל לא מימשה את `beforeinstallprompt`, ואין שום דרך לפתוח את ההתקנה
מקוד.** הדרך היחידה היא כפתור השיתוף של ספארי ← "הוספה למסך הבית". לכן
באייפון הכפתור פותח הסבר עם שלושה שלבים ועם האייקונים שרואים במסך.

זו אינה עצלות ואין מה לחפש ספרייה שתפתור: כל ספרייה שמבטיחה "התקנה
בלחיצה" באייפון מציגה בדיוק את אותו הסבר. מה שכן בידינו הוא שההסבר יהיה
מדויק — ולכן הוא מתפצל:

| מצב | מה ההסבר אומר |
| --- | --- |
| ספארי | כפתור השיתוף ← "הוספה למסך הבית" ← "הוספה" |
| כרום/פיירפוקס/אדג' באייפון | אותו מסלול בתפריט השיתוף שלהם, ואם אין — לפתוח בספארי |
| דפדפן פנימי של אפליקציה (פייסבוק, אינסטגרם) | שם אין הוספה למסך הבית **בכלל**. קודם "פתח בדפדפן", ויש כפתור להעתקת הקישור |

המקרה השלישי אינו נדיר — הוא בדיוק מה שקורה לקישור שמשותף באינסטגרם.

### ספארי במק — "הוספה ל-Dock"

בספארי 17 ומעלה: תפריט **קובץ ← הוספה ל-Dock**. שם **אין רצועה
אוטומטית** — במחשב זה רעש — ורק לחיצה על כפתור בדף פותחת את ההסבר.

## מתי הרצועה מופיעה, ומתי לא

* לא כשהאפליקציה כבר פתוחה כאפליקציה (`display-mode: standalone`).
* לא אחרי התקנה (הדפדפן מדווח `appinstalled`, והדגל נשמר).
* לא במשך שבועיים אחרי ✕, וגם לא אחרי "לא עכשיו" בדיאלוג של המערכת —
  תשובה שלילית היא תשובה, ורצועה שחוזרת בדף הבא היא הטרדה.
* לא לפני 2.6 שניות מטעינת הדף. באנר שקופץ תוך כדי טעינה נסגר ברפלקס.
* לא בדפי תהליך — `checkout`, `sign`, `agreement`, `review-request` —
  שנושאים `data-no-auto`. הפרעה באמצע תשלום או חתימה עולה יותר ממה
  שהתקנה שווה. הכפתור בתפריט עדיין עובד שם.

## הכללה בדף

שורה אחת, וזה הכול:

```html
<script defer src="assets/pwa-install.js"></script>
```

ובדף שיש בו אלמנטים קבועים בתחתית המסך:

```html
<script defer src="assets/pwa-install.js" data-bottom="124px"></script>
```

`data-bottom` הוא המרווח שהרצועה מתרוממת מעל תחתית המסך. ב-`crm.html`
הוא `124px` ולא גובה סרגל הניווט (כ-60px), כי מעל הסרגל יש עוד אלמנט צף:
כפתור ההחתמה, שיושב ב-`bottom: 74px` וגובהו 56px. רצועה שמכסה את כפתור
הפעולה המרכזי של המסך היא בדיוק מה שהיא לא אמורה לעשות.

### כפתור קבוע בדף

כל אלמנט עם `data-pwa-install` הופך לנקודת כניסה: לחיצה עליו מתקינה, או
פותחת את ההסבר באייפון. המודול **מסתיר אותו לבד** כשאין מה להציע
(אפליקציה מותקנת, דפדפן שלא תומך), ולכן הוא נולד `hidden`:

```html
<button type="button" data-pwa-install hidden>התקנת האפליקציה</button>
```

כך בנוי הפריט בתחתית תפריט הבורגר של ה-CRM. התפריט נבנה מחדש בכל פתיחה,
ולכן הוא קורא `window.ShukPWA.refreshTriggers()` אחרי הבנייה — הכפתור
שהמודול חיבר אליו מאזין קודם כבר אינו ב-DOM.

### ה-API

```js
ShukPWA.canInstall()       // האם יש מה להציע כאן ועכשיו
ShukPWA.mode()             // 'prompt' | 'ios' | 'ios-other' | 'in-app' | 'mac-safari' | null
ShukPWA.install(source)    // התקנה, או פתיחת ההסבר במקום שאין התקנה
ShukPWA.showHelp(source)   // ההסבר בלבד
ShukPWA.refreshTriggers()  // אחרי בנייה מחדש של תפריט
```

## שני המניפסטים, ולמה לא אחד

לאפליקציה מותקנת יש **נקודת פתיחה אחת**, וזו שאלה שאין לה תשובה אחת כאן:
גולש/ת שמתקין/ה מדף נכס רוצה להיפתח בדף הבית; סוכן/ת שמתקין/ה מה-CRM
רוצה להיפתח ב-CRM. מניפסט אחד היה מכריח את אחד מהם.

| | `manifest.webmanifest` | `app-crm.webmanifest` |
| --- | --- | --- |
| `id` | `/` | `/crm` |
| `start_url` | `/?src=pwa` | `/crm?src=pwa` |
| שם במסך הבית | שוק נדל״ן | אזור אישי |
| מי מצביע אליו | כל הדפים | `crm`, `developer-crm`, `professional-manage` |

ל-`id` שונה יש משמעות: הוא מה שמבדיל בין שתי אפליקציות מותקנות. ה-`scope`
של שניהם הוא `/`, כלומר ניווט לכל דף באתר נשאר **בתוך** האפליקציה ולא
קופץ החוצה לדפדפן. זו הסיבה שכל דף באתר נושא קישור למניפסט — גם דף שאיש
לא יתקין ממנו.

`?src=pwa` ב-`start_url` נספר במדידה כמו כל `src` אחר (ראו
[`analytics-events.md`](analytics-events.md)), וכך אפשר לדעת כמה פתיחות
מגיעות מהאייקון במסך הבית ולא מהדפדפן.

## ה-Service Worker — ולמה הוא ריק

כרום יורה `beforeinstallprompt` רק לדף שיש לו מניפסט **וגם** ‏Service
Worker רשום עם מאזין `fetch`. זו כל הסיבה שהקובץ קיים.

**הוא לא שומר מטמון, וזו לא השמטה.** שמות הקבצים באתר אינם נושאים חתימת
תוכן, ו-`_headers` מסביר למה HTML/JS/CSS מקבלים אימות מחדש ולא מטמון
ארוך: מטמון ארוך היה מגיש גרסה ישנה אחרי מיזוג. ‏Service Worker שמגיש
מהמטמון הוא אותו כשל, רק חמור יותר — הוא חי בדפדפן של המשתמש/ת גם אחרי
שהשרת כבר מגיש את החדש, ולא נעלם ברענון. סוכן/ת שרואה לוח מחוונים ישן לא
מדווח/ת על באג; הוא/היא מפסיק/ה לסמוך על המספרים.

המחיר המודע: אפליקציה מותקנת בלי רשת מציגה את שגיאת הרשת הרגילה של
הדפדפן, ולא מסך "אין חיבור" משלנו.

**להסרת Worker שכבר נרשם לא מוחקים את הקובץ** — קובץ חסר מחזיר 404
והדפדפן משאיר את הגרסה הישנה רשומה. מפרסמים במקומו Worker שמבטל את עצמו;
הנוסח נמצא בהערה בראש `sw.js`.

## האייקונים

חמישה קבצים, כולם נבנים מאותה גאומטריה של הלוגו:

```sh
mkdir -p ~/.fonts && curl -L -o ~/.fonts/Heebo-ExtraBold.ttf \
  "https://fonts.gstatic.com/s/heebo/v28/NGSpv5_NC0k9P_v6ZUCbLRAHxK1ECSuccg.ttf"
fc-cache -f
pip install cairosvg
python3 scripts/build_app_icons.py
```

הסקריפט נעצר אם Heebo אינו מותקן: בלעדיו האות ש מרונדרת בגופן אחר,
והאייקון ייראה *כמעט* נכון — וזה הסוג הגרוע, כי מגלים אותו כשהוא כבר על
מסך הבית של אנשים.

**`any` מול `maskable`:** אנדרואיד חותך מהאייקון צורה (עיגול, טיפה) ומבטיח
רק את 80% המרכזיים. אייקון בלי גרסת `maskable` מקבל ריבוע לבן סביבו;
אייקון שהוא `maskable` בלבד נראה קטן מדי במקומות שלא חותכים. לכן שניהם.

**שינוי בלוגו נכנס גם ל-`build_app_icons.py`**, כמו שהוא נכנס לשלושת
קובצי ה-SVG (ראו [`logo.md`](logo.md)), ואז מריצים את הסקריפט ומכניסים
לגיט את ה-PNG-ים שיצאו. ‏Netlify מפרסם קבצים סטטיים — מה שלא בגיט לא
קיים באתר.

## דף חדש

דף חדש בשורש נושא את בלוק ה-PWA, בדיוק כמו שהוא נושא את תגיות ה-GTM,
ומאותה סיבה: לאתר אין תבנית משותפת. הבלוק יושב ב-`<head>` מיד אחרי
`<link rel="icon">`, ואפשר להעתיק אותו מ-`index.html` כלשונו.

`scripts/check_pwa.py` חוסם ב-CI דף חסר, מניפסט הפוך (דף אישי שמצביע
למניפסט הציבורי ולהפך), ואייקון שמופיע במניפסט ואינו קיים בריפו — אייקון
חסר הוא 404, וכרום פוסל בגללו את ההתקנה **כולה**.

```sh
python scripts/check_pwa.py
```

## מה לבדוק אחרי שינוי

1. **אנדרואיד/כרום:** לפתוח את האתר, לחכות שלוש שניות, לוודא שהרצועה
   עולה ושלחיצה עליה פותחת את דיאלוג ההתקנה של המערכת.
2. **אייפון:** לוודא שהרצועה עולה ושההסבר מדויק למסך שלפניך.
3. **אחרי התקנה:** לפתוח מהאייקון ולוודא שהדף עולה במסך מלא, שהרצועה
   **לא** מופיעה, ושניווט לדף אחר באתר נשאר בתוך האפליקציה.
4. **‏DevTools ← Application ← Manifest:** אין אזהרות, והאייקונים נטענים.
