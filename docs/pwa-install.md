# התקנת האתר כאפליקציה (PWA)

האתר ניתן להתקנה: דפדפן יודע להניח אותו על מסך הבית של הטלפון עם אייקון
משלו, ולפתוח אותו במסך מלא בלי סרגלי הדפדפן. אין כאן חנות אפליקציות, אין
קובץ להוריד, ואין גרסה שצריך לעדכן — מה שמותקן הוא האתר עצמו, וכל מיזוג
ל-`main` מגיע אליו תוך שניות בדיוק כמו לדפדפן.

**הבעיה שהכפתור פותר:** כל זה היה קיים גם קודם, אבל הדרך אליו הוסתרה
בתפריט שלוש הנקודות של כרום — "התקנה ויצירת קיצור דרך". מי שקיבל/ה קישור
בוואטסאפ לא ידע/ה שהאפשרות שם, ובאייפון היא עוד יותר מוסתרת. עכשיו
ההצעה עולה בתוך הדף.

## מה יש בריפו

| קובץ | תפקיד |
| --- | --- |
| `manifest.webmanifest` | המניפסט של האתר הציבורי. נפתח על דף הבית |
| `app-crm.webmanifest` | המניפסט של האזור האישי. נפתח על `/crm` |
| `sw.js` | ‏Service Worker מינימלי, בלי מטמון. קיים כדי שכרום יאפשר התקנה |
| `assets/pwa-install.js` | הרצועה, ההסבר לאייפון, הרישום וה-API לדף |
| `assets/icon-192.png` ו-`icon-512.png` | אייקוני האפליקציה |
| `assets/icon-maskable-*.png` | אותו ציור עם שוליים, לחיתוך של אנדרואיד |
| `assets/apple-touch-icon.png` | אייקון מסך הבית של אייפון (180px) |
| `scripts/build_app_icons.py` | בונה את חמשת ה-PNG-ים מהגאומטריה של הלוגו |
| `scripts/check_pwa.py` | הבדיקה שרצה ב-CI |

## שלוש מציאויות, שלוש התנהגויות

### כרום, אדג' וסמסונג (אנדרואיד ומחשב) — התקנה אמיתית בלחיצה

הדפדפן יורה `beforeinstallprompt` כשהדף עומד בתנאי ההתקנה. הקובץ עוצר את
האירוע (`preventDefault`, אחרת כרום מציג באנר משלו), שומר אותו, ומציג את
הרצועה שלנו. לחיצה על "התקנה" מריצה `prompt()` — **אותו דיאלוג התקנה של
המערכת**, בלחיצה אחת מתוך הדף.

האירוע ניתן לצריכה **פעם אחת בלבד**. לכן הוא מתאפס אחרי `prompt()`,
ולחיצה שנייה לא תעשה דבר עד שהדפדפן ייתן אירוע חדש.

### אייפון ואייפד — הסבר, כי אין API

**אפל לא מימשה את `beforeinstallprompt`, ואין שום דרך לפתוח את ההתקנה
מקוד.** הדרך היחידה היא כפתור השיתוף של ספארי ← "הוספה למסך הבית". לכן
באייפון הכפתור פותח הסבר עם שלושה שלבים ועם האייקונים שרואים במסך.

זו אינה עצלות ואין מה לחפש ספרייה שתפתור: כל ספרייה שמבטיחה "התקנה
בלחיצה" באייפון מציגה בדיוק את אותו הסבר. מה שכן בידינו הוא שההסבר יהיה
מדויק — ולכן הוא מתפצל:

| מצב | מה ההסבר אומר |
| --- | --- |
| ספארי | כפתור השיתוף ← "הוספה למסך הבית" ← "הוספה" |
| כרום/פיירפוקס/אדג' באייפון | אותו מסלול בתפריט השיתוף שלהם, ואם אין — לפתוח בספארי |
| דפדפן פנימי של אפליקציה (פייסבוק, אינסטגרם) | שם אין הוספה למסך הבית **בכלל**. קודם "פתח בדפדפן", ויש כפתור להעתקת הקישור |

המקרה השלישי אינו נדיר — הוא בדיוק מה שקורה לקישור שמשותף באינסטגרם.

### ספארי במק — "הוספה ל-Dock"

בספארי 17 ומעלה: תפריט **קובץ ← הוספה ל-Dock**. שם **אין רצועה
אוטומטית** — במחשב זה רעש — ורק לחיצה על כפתור בדף פותחת את ההסבר.

## מתי הרצועה מופיעה, ומתי לא

* לא כשהאפליקציה כבר פתוחה כאפליקציה (`display-mode: standalone`).
* לא אחרי התקנה (הדפדפן מדווח `appinstalled`, והדגל נשמר).
* לא במשך שבועיים אחרי ✕, וגם לא אחרי "לא עכשיו" בדיאלוג של המערכת —
  תשובה שלילית היא תשובה, ורצועה שחוזרת בדף הבא היא הטרדה.
* לא לפני 2.6 שניות מטעינת הדף. באנר שקופץ תוך כדי טעינה נסגר ברפלקס.
* לא בדפי תהליך — `checkout`, `sign`, `agreement`, `review-request` —
  שנושאים `data-no-auto`. הפרעה באמצע תשלום או חתימה עולה יותר ממה
  שהתקנה שווה. הכפתור בתפריט עדיין עובד שם.

## הכללה בדף

שורה אחת, וזה הכול:

```html
<script defer src="assets/pwa-install.js"></script>
```

ובדף שיש בו אלמנטים קבועים בתחתית המסך:

```html
<script defer src="assets/pwa-install.js" data-bottom="124px"></script>
```

`data-bottom` הוא המרווח שהרצועה מתרוממת מעל תחתית המסך. ב-`crm.html`
הוא `124px` ולא גובה סרגל הניווט (כ-60px), כי מעל הסרגל יש עוד אלמנט צף:
כפתור ההחתמה, שיושב ב-`bottom: 74px` וגובהו 56px. רצועה שמכסה את כפתור
הפעולה המרכזי של המסך היא בדיוק מה שהיא לא אמורה לעשות.

### כפתור קבוע בדף

כל אלמנט עם `data-pwa-install` הופך לנקודת כניסה: לחיצה עליו מתקינה, או
פותחת את ההסבר באייפון. המודול **מסתיר אותו לבד** כשאין מה להציע
(אפליקציה מותקנת, דפדפן שלא תומך), ולכן הוא נולד `hidden`:

```html
<button type="button" data-pwa-install hidden>התקנת האפליקציה</button>
```

כך בנוי הפריט בתחתית תפריט הבורגר של ה-CRM. התפריט נבנה מחדש בכל פתיחה,
ולכן הוא קורא `window.ShukPWA.refreshTriggers()` אחרי הבנייה — הכפתור
שהמודול חיבר אליו מאזין קודם כבר אינו ב-DOM.

### ה-API

```js
ShukPWA.canInstall()       // האם יש מה להציע כאן ועכשיו
ShukPWA.mode()             // 'prompt' | 'ios' | 'ios-other' | 'in-app' | 'mac-safari' | null
ShukPWA.install(source)    // התקנה, או פתיחת ההסבר במקום שאין התקנה
ShukPWA.showHelp(source)   // ההסבר בלבד
ShukPWA.refreshTriggers()  // אחרי בנייה מחדש של תפריט
```

## שני המניפסטים, ולמה לא אחד

לאפליקציה מותקנת יש **נקודת פתיחה אחת**, וזו שאלה שאין לה תשובה אחת כאן:
גולש/ת שמתקין/ה מדף נכס רוצה להיפתח בדף הבית; סוכן/ת שמתקין/ה מה-CRM
רוצה להיפתח ב-CRM. מניפסט אחד היה מכריח את אחד מהם.

| | `manifest.webmanifest` | `app-crm.webmanifest` |
| --- | --- | --- |
| `id` | `/` | `/crm` |
| `start_url` | `/?src=pwa` | `/crm?src=pwa` |
| שם במסך הבית | שוק נדל״ן | אזור אישי |
| מי מצביע אליו | כל הדפים | `crm`, `developer-crm`, `professional-manage` |

ל-`id` שונה יש משמעות: הוא מה שמבדיל בין שתי אפליקציות מותקנות. ה-`scope`
של שניהם הוא `/`, כלומר ניווט לכל דף באתר נשאר **בתוך** האפליקציה ולא
קופץ החוצה לדפדפן. זו הסיבה שכל דף באתר נושא קישור למניפסט — גם דף שאיש
לא יתקין ממנו.

`?src=pwa` ב-`start_url` נספר במדידה כמו כל `src` אחר (ראו
[`analytics-events.md`](analytics-events.md)), וכך אפשר לדעת כמה פתיחות
מגיעות מהאייקון במסך הבית ולא מהדפדפן.

## באפליקציה המותקנת הדף פרוש מקצה לקצה — ‏`viewport-fit=cover`

‏`display: standalone` פירושו שאין דפדפן סביב הדף, ובאנדרואיד המודרני
פירושו גם שהמערכת פורשת את הדף **מתחת לסרגלים שלה**: שעון המערכת למעלה,
וסרגל הניווט (שלושת הכפתורים או פס המחוות) למטה. ‏`bottom: 0` הוא קצה
המסך, לא קצה השטח הפנוי.

הדרך לדעת כמה מקום לפנות היא `env(safe-area-inset-*)` — **והיא מחזירה 0
כל עוד ה-`<meta name="viewport">` אינו מצהיר `viewport-fit=cover`.**
זה הכשל שהיה כאן: ל-`crm.html` היו שלושה `env(safe-area-inset-bottom)`
במקומות הנכונים (סרגל הניווט התחתון, הכפתור המרחף, ריפוד תחתית התוכן),
ההצהרה לא הייתה, ולכן **שלושתם היו 0 בכל מצב**.

מה שנראה בפועל: ‏`.bn-tab` הוא אייקון ומעליו תווית, ‏53px של רצועה. בלי
הריפוד ‎24px‎ מהתחתית שלה יושבים מאחורי סרגל המערכת — כלומר בדיוק שורת
התוויות. "ראשי", "נכסים", "לידים" נעלמו, ומכיוון שהמגרעות משתנות תוך
גלילה הרצועה גם נראתה זזה.

**למה זה לא נראה בדפדפן:** שם הדפדפן מכווץ את החלון מעל סרגל המערכת
ממילא, ואז `env()` שווה 0 **וגם** אין מה לפנות. הפער בין שתי ההתנהגויות
הוא כל הסיפור, ולכן בדיקה בדפדפן לא יכולה לתפוס אותו.

### הכלל שנגזר מזה

‏`viewport-fit=cover` הוא הצהרה שחלה על **כל** הדף, ולכן מרגע שהיא שם
**כל אלמנט שנוגע בקצה המסך חייב להוסיף את המרווח המתאים.** ארבעה
משתנים ב-`:root` של `crm.html` מרכזים את זה:

```css
--sa-top / --sa-bottom / --sa-start / --sa-end
```

‏`start`/`end` ולא `left`/`right`, כי הדף RTL ותחילת השורה היא ימין.
מי שנוגע בהם: הכותרת הדביקה, שלוש השכבות במסך מלא (`#cmaOverlay`,
‏`.pm-overlay`, `.imp-overlay`), ההודעה הצפה (`.toast`), סרגל הניווט
התחתון, הכפתור המרחף וריפוד תחתית התוכן.

| | מגרעות 0 (דפדפן/מחשב) | מגרעות 28/24 (אפליקציה) |
| --- | --- | --- |
| ‏padding-top של הכותרת | 12px | 40px |
| גובה סרגל הניווט | 53px | 77px |
| מרווח מתחת לתווית "ראשי" | 7px | 31px |
| ‏`.toast` bottom | 20px | 44px |

העמודה הראשונה זהה בדיוק למה שהיה לפני השינוי — זו הנקודה: בדפדפן שום
דבר לא זז.

**וההצהרה היא ב-`crm.html` בלבד.** ל-`developer-crm.html` ול-
‏`professional-manage.html` אין אף `position:fixed`, כלומר אין בהם
אלמנט שנוגע בקצה המסך ואין מה לפנות בשבילו. דף שיוסיפו לו סרגל תחתון
או שכבה במסך מלא צריך את ההצהרה ואת ארבעת המשתנים יחד — אחד בלי השני
הוא או ריפוד שלא נכנס לתוקף, או תוכן מתחת לשעון המערכת.

## ה-Service Worker — ולמה הוא ריק

כרום יורה `beforeinstallprompt` רק לדף שיש לו מניפסט **וגם** ‏Service
Worker רשום עם מאזין `fetch`. זו כל הסיבה שהקובץ קיים.

**הוא לא שומר מטמון, וזו לא השמטה.** שמות הקבצים באתר אינם נושאים חתימת
תוכן, ו-`_headers` מסביר למה HTML/JS/CSS מקבלים אימות מחדש ולא מטמון
ארוך: מטמון ארוך היה מגיש גרסה ישנה אחרי מיזוג. ‏Service Worker שמגיש
מהמטמון הוא אותו כשל, רק חמור יותר — הוא חי בדפדפן של המשתמש/ת גם אחרי
שהשרת כבר מגיש את החדש, ולא נעלם ברענון. סוכן/ת שרואה לוח מחוונים ישן לא
מדווח/ת על באג; הוא/היא מפסיק/ה לסמוך על המספרים.

המחיר המודע: אפליקציה מותקנת בלי רשת מציגה את שגיאת הרשת הרגילה של
הדפדפן, ולא מסך "אין חיבור" משלנו.

**להסרת Worker שכבר נרשם לא מוחקים את הקובץ** — קובץ חסר מחזיר 404
והדפדפן משאיר את הגרסה הישנה רשומה. מפרסמים במקומו Worker שמבטל את עצמו;
הנוסח נמצא בהערה בראש `sw.js`.

## האייקונים

חמישה קבצים, כולם נבנים מאותה גאומטריה של הלוגו:

```sh
mkdir -p ~/.fonts && curl -L -o ~/.fonts/Heebo-ExtraBold.ttf \
  "https://fonts.gstatic.com/s/heebo/v28/NGSpv5_NC0k9P_v6ZUCbLRAHxK1ECSuccg.ttf"
fc-cache -f
pip install cairosvg
python3 scripts/build_app_icons.py
```

הסקריפט נעצר אם Heebo אינו מותקן: בלעדיו האות ש מרונדרת בגופן אחר,
והאייקון ייראה *כמעט* נכון — וזה הסוג הגרוע, כי מגלים אותו כשהוא כבר על
מסך הבית של אנשים.

**`any` מול `maskable`:** אנדרואיד חותך מהאייקון צורה (עיגול, טיפה) ומבטיח
רק את 80% המרכזיים. אייקון בלי גרסת `maskable` מקבל ריבוע לבן סביבו;
אייקון שהוא `maskable` בלבד נראה קטן מדי במקומות שלא חותכים. לכן שניהם.

**שינוי בלוגו נכנס גם ל-`build_app_icons.py`**, כמו שהוא נכנס לשלושת
קובצי ה-SVG (ראו [`logo.md`](logo.md)), ואז מריצים את הסקריפט ומכניסים
לגיט את ה-PNG-ים שיצאו. ‏Netlify מפרסם קבצים סטטיים — מה שלא בגיט לא
קיים באתר.

## מדידה — שני יעדים, ובכוונה

כל אירוע של הכפתור נדחף לשני מקומות: ל-`dataLayer` (ומשם GTM ל-GA4), ול-
טבלה `pwa_install_events` במסד שלנו.

**למה שניים.** ל-GA4 יש פילוח שאין למסד — קמפיין, מקור, קהל. אבל לשאלה
"כמה אנשים התקינו" הוא לא עונה כאן, משלוש סיבות:

1. **חוסם פרסומות מפיל את GTM**, ודווקא מי שמתקין אפליקציות נוטה שיהיה
   לו כזה. אלה לא נספרים שם כלל.
2. **דפי האזור האישי אינם טוענים את `events.js` במכוון** (ראו
   `CLAUDE.md`), ולכן **התקנה של סוכן/ת מה-CRM לא הייתה נספרת ב-GA4
   בכלל** — וזה הקהל שההתקנה נבנתה בשבילו.
3. **הדשבורד של מנהל/ת הפלטפורמה מציג את כל שאר המספרים במקום אחד.**
   יציאה לממשק אחר, של חשבון אחר, בשביל מספר אחד — היא יציאה שלא קורית.

לכן המספר במסד יהיה תמיד **גבוה** מזה של GA4, והוא הנכון מבין השניים
לשאלת "כמה התקינו". ההפרש בין השניים הוא, במקרה, מדידה לא רעה של שיעור
חוסמי הפרסומות בקהל.

### הטבלה

`pwa_install_events` — מונה, לא מעקב. **אין בה `user_id`, אין `agent_id`,
אין כתובת IP ואין `User-Agent`.** שורה היא שלושה שדות: איזה אירוע, איזה
מסלול התקנה הוצע, ומאיזה דף. `occurred_at` נקבע בשרת ולא מגיע מהלקוח, כדי
שאי אפשר יהיה לשתול היסטוריה או לזייף דוח משעון מוטה במכשיר.

הכתיבה פתוחה ל-`anon` — מי שגולש/ת אינו/ה מחובר/ת — בדיוק כמו
`property_views` שכבר עובדת כך. מה שמצמצם אותה: `check constraint` על
כל אחד משלושת השדות, ו**כתיבה־בלבד בשתי שכבות בלתי תלויות**:

| שכבה | מה היא עושה |
| --- | --- |
| ‏`RLS` | policy אחת בלבד, של `insert`. קריאה מחזירה רשימה ריקה |
| ‏`GRANT` | ל-`anon` ול-`authenticated` יש `insert` **בלבד** על הטבלה |

השכבה השנייה אינה כפילות. ברירת המחדל של Supabase נותנת לכל טבלה חדשה
`select`, `update`, `delete` ו-`truncate` לשני התפקידים האלה, וה-RLS הוא
שמצמצם אותם — אבל **`RLS` אינו חל על `truncate` כלל**, ו-policy אחת
שתתווסף בטעות (או `disable row level security` של מי שמנפה באגים) פותחת
את הטבלה כולה. אחרי צמצום ההרשאות, גם אז אין קריאה.

הקריאה כולה עוברת דרך `platform_pwa_report()`, שהוא `security definer`
בבעלות `postgres` — ולכן אינו מושפע מההרשאות של `anon` — עם בדיקת
`current_is_platform_admin()` בשורה הראשונה.

⚠️ **הכתיבה תלויה ב-`Prefer: return=minimal`.** ל-`anon` אין `select`,
ולכן `return=representation` היה גורם ל-PostgREST להוסיף `returning`
ולהיכשל ב-401. הכותרת הזו ב-`assets/pwa-install.js` אינה אופטימיזציה.
(‏`id` הוא `generated always as identity` ולא `serial`, ולכן אין צורך
בהרשאה על רצף — עם `serial` הצמצום הזה היה שובר את הכתיבה בשקט.)

המיגרציות: `20261124090000_pwa_install_events.sql` (הטבלה והדוח)
ו-`20261125090000_pwa_events_grants.sql` (צמצום ההרשאות).

### בדשבורד

הבלוק **"האפליקציה במסך הבית (PWA)"** יושב בתחתית פאנל מנהל/ת הפלטפורמה
ב-`crm.html`, ונטען אחרי הדוח החודשי. חלון הזמן שלו נגזר מבורר החודשים
של הפאנל (3 / 6 / 12 חודשים → 90 / 180 / 360 יום), כדי שלא יהיה במסך
אחד בורר שני שאומר משהו אחר.

מה שרואים שם:

| | |
| --- | --- |
| כותרת | סך ההתקנות מאז ומתמיד, ובחלון הנבחר |
| משפך | ראו את ההצעה ← לחצו ← פתחו הסבר ← אישרו ← הותקנו |
| לפי מסלול | אנדרואיד/כרום, אייפון־ספארי, אייפון־דפדפן אחר, דפדפן פנימי |
| לפי דף | מאיפה לוחצים בפועל — זה מה שקובע לאן כדאי להחזיר את הכפתור |

**באייפון "הותקנו" יהיה תמיד אפס, וזו לא תקלה.** הדפדפן שם אינו מדווח על
"הוספה למסך הבית" בשום צורה. הקצה של המדידה באייפון הוא "פתחו הסבר",
ולכן הוא טור נפרד בטבלה ולא חלק מאותו משפך. ההשוואה הנכונה באייפון היא
בין "ראו" ל"פתחו הסבר".

**התקנה נספרת פעם אחת לכל מכשיר, ולא פעם אחת לכל לשונית.** ‏`appinstalled`
אינו אירוע של הדף שבו נלחץ הכפתור אלא של ההתקנה עצמה, והוא מגיע לכל דף
פתוח של האתר. ההתקנה האמיתית הראשונה בפרודקשן (18.9.2026) נרשמה בגלל זה
**שלוש פעמים** — פעמיים תוך עשר שניות ופעם חמש דקות אחרי. מאז, הדגל
`shukPwaInstalled` ב-`localStorage` (משותף לכל הלשוניות) הוא המנעול:
הראשונה שרושמת סוגרת את הדלת בפני השאר.

הטעות הזו הייתה מושכת **תמיד כלפי מעלה** — ככל שפתוחות יותר לשוניות, כך
המונה מנופח — וזה הסוג שקשה לתפוס אחר כך, כי מספר התקנות גבוה נראה כמו
הצלחה.

שני גבולות שנשארו, במכוון:

* **התקנה חוזרת באותו מכשיר אינה נספרת שוב.** מי שהתקין/ה, הסיר/ה
  והתקין/ה שוב — הדגל כבר שם. המונה סופר מכשירים ייחודיים, וזה גם
  המספר המעניין.
* **שתי לשוניות שיקבלו את האירוע באותה מילישנייה** עדיין יכולות שתיהן
  לרשום. זהו מרוץ שאי אפשר למנוע מהדפדפן, והחלון שנשאר הוא מילישניות
  במקום דקות.

### ‏GTM — מה שצריך לעשות פעם אחת בממשק

דחיפה ל-`dataLayer` לבדה **אינה** מגיעה ל-GA4: לכל אירוע צריך טריגר ותגית
ב-GTM. הקובץ `docs/gtm-pwa-import.json` מכיל את כולם מוכנים — שישה
טריגרים, שש תגיות GA4 ושלושה משתני Data Layer.

**הייבוא:** ‏GTM ← **Admin** ← **Import Container** ← בחירת הקובץ ←
‏Workspace קיים ← **Merge** ו-**Rename conflicting tags and triggers**
(‏*לא* Overwrite) ← Confirm ← **Submit → Publish**.

‏`Merge` + `Rename` הוא מה שהופך את הייבוא לבטוח: הוא רק **מוסיף**, ואינו
נוגע בתגית קיימת. אם משהו נראה לא נכון אחרי הייבוא, אפשר לחזור לגרסה
הקודמת ב-**Versions**.

אם הייבוא נדחה — גרסאות GTM משנות לעיתים את סכמת הייצוא — אלה אותם
הגדרות ביד:

| רכיב | סוג | ערכים |
| --- | --- | --- |
| טריגר × 6 | ‏Custom Event | שם האירוע בדיוק: `pwa_banner_shown`, `pwa_install_click`, `pwa_install_result`, `pwa_help_open`, `pwa_installed`, `pwa_banner_dismiss` |
| משתנה × 3 | ‏Data Layer Variable | `mode`, `outcome`, `page_type` |
| תגית × 6 | ‏GA4 Event | שם האירוע כנ״ל, Measurement ID ‏`G-40ZLLXSRFY`, ופרמטרים: `mode` (או `outcome` ב-`pwa_install_result`) ו-`page_type` |

ואז **Preview** ב-Tag Assistant, לחיצה על הרצועה באתר, ווידוא ב-**Realtime**
של GA4. ובסוף — **Publish**, אחרת שום דבר מזה אינו חי.

⚠️ פרמטר מותאם (`mode`, `outcome`) אינו מופיע בשום דוח ב-GA4 עד
שרושמים אותו כ**מימד מותאם**, והרישום אינו למפרע. ראו "המלכודת האחרונה"
ב-[`analytics-events.md`](analytics-events.md).

**הדשבורד אינו תלוי בכל זה.** גם בלי טריגר אחד ב-GTM, המונה במסד עובד
והבלוק בדשבורד מציג מספרים.

## דף חדש

דף חדש בשורש נושא את בלוק ה-PWA, בדיוק כמו שהוא נושא את תגיות ה-GTM,
ומאותה סיבה: לאתר אין תבנית משותפת. הבלוק יושב ב-`<head>` מיד אחרי
`<link rel="icon">`, ואפשר להעתיק אותו מ-`index.html` כלשונו.

`scripts/check_pwa.py` חוסם ב-CI דף חסר, מניפסט הפוך (דף אישי שמצביע
למניפסט הציבורי ולהפך), ואייקון שמופיע במניפסט ואינו קיים בריפו — אייקון
חסר הוא 404, וכרום פוסל בגללו את ההתקנה **כולה**.

```sh
python scripts/check_pwa.py
```

## מה לבדוק אחרי שינוי

1. **אנדרואיד/כרום:** לפתוח את האתר, לחכות שלוש שניות, לוודא שהרצועה
   עולה ושלחיצה עליה פותחת את דיאלוג ההתקנה של המערכת.
2. **אייפון:** לוודא שהרצועה עולה ושההסבר מדויק למסך שלפניך.
3. **אחרי התקנה:** לפתוח מהאייקון ולוודא שהדף עולה במסך מלא, שהרצועה
   **לא** מופיעה, ושניווט לדף אחר באתר נשאר בתוך האפליקציה.
4. **‏DevTools ← Application ← Manifest:** אין אזהרות, והאייקונים נטענים.
